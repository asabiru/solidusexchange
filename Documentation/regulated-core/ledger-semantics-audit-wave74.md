# JavaScript Ledger Semantics Audit — Wave 74 — Proposed

- Status: Proposed
- Scope: `packages/financial-core/src/ledger.mjs` — the in-package double-entry ledger engine: posting validation, digest derivation, idempotent replay, journal storage, projections and the trial balance. Wave 70 audited JS-versus-PostgreSQL representation parity; waves 59/62 pinned store-divergence classes. This wave audits the engine's own semantics end to end, independent of the SQL twin. Everything is dev-only and synthetic — no production paths, no live data, no money movement.
- Production effect: none

Hunt list applied: double-entry enforcement in the JS core itself (bigint exactness at scale, postings that bypass the rule engine, negative or zero legs, cross-asset without a rate leg), command-digest totality (which fields feed the digest, missing-field collisions, replay conflict semantics), journal integrity (envelope-field shadowing of engine-owned stamps, sequence continuity, replay determinism), account lifecycle (definition pinning, unknown accounts, asset mismatch), atomicity of multi-leg failure, registry bounds and clock totality, and JS-versus-SQL posting-rule grammar divergence against the `validate_posting_rule()` trigger. Every finding was probed against a live `createInMemoryLedger` first (repro-fail), fixed, then pinned by a regression in the same change.

## Defects found and fixed

1. **Timestamps could denote instants beyond the persisted range (the wave-70 totality gap reopened).** Wave 70 pinned every persisted timestamp column to `['0001-01-01 00:00:00+14:00', '9999-12-31 23:59:59.999999-14:00']` and asserted the JS grammar denotes exactly that interval — but `assertDateTime` never computed the denoted instant at all. Its grammar admits up to nine fractional digits, so `9999-12-31T23:59:59.9999999-14:00` (instant `10000-01-01T13:59:59.9999999Z`, past the upper bound) passed validation and posted a journal the SQL layer would refuse. Probes on the pre-fix engine: `9999-12-31T23:59:59.9999995-14:00`, `...999999999-14:00`, a clock returning the same beyond-bound literal, and an account `created_at` of the same shape — all stored. Millisecond-precision `Date.parse` hides the excess: the literal parses to a finite millisecond that appears in range. Fixed in `assertDateTime`: the denoted instant is now reconstructed at nanosecond precision (parsed milliseconds plus the sub-millisecond fraction residue as BigInt) and must lie inside `[MIN_INSTANT_NANOSECONDS, MAX_INSTANT_NANOSECONDS]` — the exact bounds migration 0013 pins. The inclusive edge literals (`9999-12-31T23:59:59.999999-14:00`, `0001-01-01T00:00:00+14:00`) and valid offsets still pass; the check covers every date-time the engine consumes (`effective_at`, the clock output, `created_at` on configuration accounts).
2. **Unbounded runtime registries (the standing bounds rule).** `post()` grew `journals`, `idempotency` and `postedEntryIds` without any ceiling — a long-lived dev engine could be driven to arbitrary memory growth, unlike its siblings (`callback-inbox` `maxSubjects`, `IdempotencyRegistry{maxEntries}`, `OIDC_MAX_PENDING_CODES`, `MAX_FILL_NUMBER`). Probe on the pre-fix engine stored hundreds of journals with no ceiling. Fixed: `createInMemoryLedger` takes `maxJournals` (default `MAX_JOURNALS = 10_000`, a positive safe integer enforced at configuration, `LEDGER_CONFIGURATION_INVALID` otherwise); once `journals.size` reaches the cap, a new post is refused with `LEDGER_CAPACITY_EXCEEDED`. The check runs after dedupe and duplicate-entry checks, so an idempotent replay still resolves at capacity while no new journal can commit — and the other two registries are transitively bounded (`idempotency` has one row per journal, `postedEntryIds` at most `MAX_ENTRIES` per journal).
3. **Trial-balance ordering depended on runtime collation.** `getTrialBalance` sorted rows with `localeCompare` — ICU-version-dependent and divergent from the canonical byte order (`COLLATE "C"`) the rest of the engine and the SQL layer use: `rebuildProjectionSnapshot` and the posting-rule pattern already sort by code unit, and SQL `ORDER BY` on these tables uses the C collation. On the identifier charset, hundreds of pairs order differently (e.g. `entity-A2` precedes `entity-a` in byte order but follows it under collation), so the same journal set could return rows in different order on different runtimes — a determinism divergence for a report that is supposed to be a stable projection. Fixed: rows now sort by `compareCodeUnits`, matching `.sort()` defaults and the C collation.

## Verified clean (with negative pins)

- **Double-entry enforcement is in the engine, not delegated to the rule registry**: `validateCommand` sums each entry's minor units as BigInt per asset and requires `debits === credits` exactly (no float, no rounding path, scale-bounded by `parseAmount` ≤ 18). Every asset present in the command must independently satisfy the full `entry_pattern` signature and balance to zero — a multi-asset command cannot smuggle an unbalanced leg under a single-asset rule, and there is no cross-asset tolerance for a missing rate leg: any second asset must itself net to zero against the pattern. Negative or zero legs are unreachable — `DECIMAL_PATTERN` admits only canonical positive decimals (`parseAmount` rejects `0`, signs, exponents, leading zeros). Probes confirmed: 1000-leg maximums balance or refuse; a leg with `amount = "0"` never reaches the balance check.
- **Postings cannot bypass the rule engine**: every command passes `validateCommand` before any storage; `post()` never mutates state on a validation failure (the candidate is normalized and deep-cloned first, then the whole command — keys, UUIDs, timestamps, account existence, entity and asset binding, per-asset pattern and balance — is verified, and only then written). There is no lower-level write path: `journals`/`postedEntryIds`/`idempotency` are only touched after all checks and the clock stamp pass.
- **Command digest is total over the command**: `sha256` of `canonicalize`d JSON covers every `COMMAND_KEYS` field including ordered entries — `assertExactKeys` makes a missing or extra field unrepresentable, so two distinct commands cannot collide via an omitted field. UUIDs are lowercase-normalized before digesting, so case variants produce one digest rather than two. Reordered identical legs produce a different canonical form — recorded as an observation, not a defect.
- **Idempotent replay semantics are strict**: the namespace is `(legal_entity_id, idempotency_key)`; an identical command replays the stored journal (dedupe), and the same key with any different command — including a reorder — is refused `LEDGER_IDEMPOTENCY_CONFLICT`, never silently coalesced. A rejected post consumes neither key nor capacity (existing pin re-verified against the new bound).
- **Envelope-field shadowing is closed (the wave-59 class)**: the stored journal adds exactly two engine-owned fields — `command_digest` and the acceptance timestamp — and `assertExactKeys` on `COMMAND_KEYS`/`ENTRY_KEYS` refuses any payload carrying those names, `seq`, `at` or `type`. `sequence_number` is assigned per entry at write time, not taken from the command.
- **Atomicity**: `post()` performs zero mutations before the clock stamp and the three registry writes; a command whose third leg of five fails leaves no trace (verified — `listJournals()` stays empty, key unconsumed). `freezeDeep` on stored records prevents post-write mutation; projections recompute from journals rather than caching deltas.
- **Account lifecycle**: `definition_code` must resolve in the pinned chart (`chart_version = 1`, required categories, normal-side map); postings to unknown `account_id` refuse `LEDGER_ACCOUNT_NOT_FOUND`; the account's `legal_entity_id` must equal the command's, and its `asset_code` must equal the leg's — cross-entity and asset-mismatch legs refuse. `owner_reference` follows the definition's scope (`required`/`forbidden`/`optional` grammar).
- **Clock totality**: the clock result passes `assertDateTime` — including the new instant bound — before stamping, so a drifting or malformed clock cannot store an out-of-range or malformed acceptance timestamp; a throwing clock fails the post before mutation.
- **Posting-rule grammar parity**: `buildPostingRuleRegistry` and `validate_posting_rule()` (migration 0013) enforce the same grammar — `registry_version = 1`, distinct `allowed_actor_types`, legs of exactly `{definition_code, side}` with a chart-resident code, a `CREDIT`/`DEBIT` side, no repeated `code|side` signature, minimum two legs. A registry loadable here is writable there and vice versa; no divergent grammar was found.
- **Plain-data boundary**: `snapshotPlainData` rejects proxies, cycles, functions, symbols, non-enumerable members and extra array properties at configuration time; the same wall guards the posting command, so digest inputs are always enumerable plain data.

## Observations (recorded, not defects in this slice)

- **Entry order is part of the digest**: two commands with the same legs in different order have different digests, so a key reuse after a reorder conflicts rather than deduping. Strict, and matches the byte-for-byte uniqueness contract; callers must resubmit byte-identical commands.
- **`sequence_number` contiguity is deliberately not an invariant** (wave 70 observation restated): entries keep insertion order; SQL pins range and presence only.
- **`maxJournals` is a caller-chosen bound**: the engine enforces whatever positive safe integer is configured; the standing rule requires a bound to exist, not a fixed value. Default `10_000` matches the sibling-capacity convention.
- **Configuration arrays are caller-bounded**: `accounts`, `assets`, `chart` and `postingRules` inputs arrive whole and are validated element-by-element — their size is the caller's responsibility, as with every sibling package; runtime growth is what this wave bounded.
- **`enabled_for_posting` remains a PG-only deny switch** (wave 70 observation): the JS asset shape is exactly `{code, scale}`; a disabled asset has no JS-side concept, by design.
- **The task's `npm run typecheck` does not exist in this package**: `.mjs` with strict `checkJs`, no tsconfig. `npm run check`, `npm test` and `npm run verify` are the gates and all pass.

## Test additions

- `tests/ledger.test.mjs` — "timestamps denote only instants inside the persisted range": beyond-bound `effective_at` literals (nanosecond overflow, second 60, year 0), in-bound edge literals (both inclusive bounds, valid high fractions), a beyond-bound clock, and a beyond-bound account `created_at` — each pinned to `LEDGER_VALIDATION_FAILED`.
- `tests/ledger.test.mjs` — "journal capacity is bounded and replays never exhaust it": `maxJournals` rejects non-positive and non-integer values (`LEDGER_CONFIGURATION_INVALID`), a second journal past the cap refuses `LEDGER_CAPACITY_EXCEEDED`, an idempotent replay still resolves at capacity, and a rejected post consumes no capacity.
- `tests/ledger.test.mjs` — "trial balance rows sort in canonical byte order": entities chosen so byte order and collation order disagree (`entity-A2` vs `entity-a`), posted in reverse, asserting byte-order output.
- `src/ledger.mjs` — `MAX_JOURNALS` default cap, `MIN_/MAX_INSTANT_NANOSECONDS` instant-range check in `assertDateTime` (nanosecond-precision reconstruction), `compareCodeUnits` canonical ordering, and the `maxJournals` configuration validator.
- Every defect regression was observed failing on the pre-fix engine and passes on this branch; every clean-class pin passes by design.
