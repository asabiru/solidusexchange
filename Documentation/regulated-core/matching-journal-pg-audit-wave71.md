# Matching-Core PostgreSQL Journal Store Audit — Wave 71 — Proposed

- Status: Proposed
- Scope: `packages/matching-core/` durable journal seam — `src/postgres-journal-store.mjs` (`createPostgresJournalStore`), `src/journal-store.mjs` (`createMemoryJournalStore`, the `MatchingJournalStore` contract), `migrations/0001_matching_journal.sql` + the new `migrations/0002_journal_event_grammar.sql`, and the engine's `finish` write-behind boundary that calls `journalStore.append` without awaiting it. Wave-69's orderbook audit (#336) pinned the in-process seam itself (sealed batch, reentrancy guard, `operationAt` cleared in `finally`); wave-54 added the PG backend; this wave is the first dedicated pass on whether the PG backend's semantics match the memory backend's — the established store-divergence defect class (#301 string-seq cast, #310 replica-role trigger bypass, #331 JS↔PG representation). The journal is dev-only data (`posting: "none"` on every event) — no ledger postings, balances or custody state exist on this path.
- Production effect: none

Hunt list applied: append-contract parity (one batch one transaction, partial batches, sync-versus-async semantics under the engine's fire-and-forget `finish`); ordering and atomicity (concurrent writers interleaving stored `seq`, contiguity of the recorded tail); reconnect/replay parity (JSONB canonicalization, byte-identical snapshots); schema invariants (CHECK/trigger coverage of the event grammar — seq shape, `at` range, type enum, owner/id grammars, append-only with `ENABLE ALWAYS`, idempotent re-append); bounds (table unboundedness, payload size, pool exhaustion, hung writes); failure surfaces (PG lost mid-append, SIGKILL mid-batch, silent divergence between memory and durable streams); and the contract boundary (dev-only, no posting semantics).

## Defects found and fixed

1. **Storage-side batch rejections were swallowed, letting two histories diverge silently (`postgres-journal-store.mjs`).** A `22/23`-class rejection from `append_matching_journal` surfaced as a *non-latching* `StoreError` on the queued write; the engine's `finish` attaches a promise it never observes, so the rejection vanished entirely. A fresh engine pointed at a recorded namespace reproduced this live: its first batch (conflicting seqs) rejected silently, and its *second* batch then coincidentally continued the recorded tail — the durable stream became `e1:[1,2] + e2:[3,4]`, a valid-looking interleaved history belonging to no single engine, while `load()` and `close()` returned clean. The same hole dropped a second writer's whole stream in the two-engines-one-store case. Root cause: the "non-latching caller bug" carve-out was unobservable-by-construction — an engine cannot hear *any* settled rejection, and after one, every later batch can only arrive as a gap, so non-latching bought nothing anyway. Now every settled write rejection latches (`StoreUnavailableError`, DSN-free): `load()`/`close()` rethrow it, and the next `append` **throws it synchronously** — the engine's `finish` propagates that throw into the operation's caller, the loudest surface a swallowed promise could never provide. The diverging-second-engine case now throws `StoreUnavailableError` out of `submitOrder`, and the durable stream is never interleaved.
2. **Re-append after a lost response was non-idempotent and collided (`append_matching_journal`, both stores).** Retrying an identical batch after a timeout/answer-loss raised `23514` as if it were a conflicting write — a caller could not tell "my batch already landed" from "history diverged", the standard retry ambiguity for append-only stores. `append_matching_journal` now deduplicates: entries re-delivering already-recorded seqs must carry the *identical* recorded payload (jsonb deep equality, key-order-insensitive) and insert nothing; entries past the tail insert as before; a re-delivered seq carrying a conflicting event rejects. The memory backend mirrors the rule over canonical-JSON comparison, so the shared contract runs identical semantics on both backends.
3. **The payload document was nearly unconstrained — grammar-violating rows landed and poisoned the namespace forever (`0001` schema, fixed by `0002`).** Column checks enforced seq/at/type agreement but left the payload's grammar to the replay fold: nine probe payloads (posting `debit`, non-canonical `at`, string `"1"` seq, bogus order/fill ids, extraneous keys, unknown reject reasons, malformed decimals, year-0001 `at`) all *inserted cleanly*, then made `replayMatchingJournalStore` fail — an unrestoreable journal from a single bad write. `0002` adds `matching_core.valid_journal_event(payload)` mirroring the fold's envelope grammar — exact allowed+required key sets per event type, `ord_`/`fll_` id patterns, owner pattern, reject-reason enum, `quantity` presence tied to `self_trade`/`insufficient_liquidity`, `price` presence tied to `order_type=limit`, canonical decimal spelling, `seq` a positive safe-integer JSON number, `at` the canonical whole-second UTC spelling, `posting = 'none'` — as a `CHECK`, plus `matching_journal_at_js_range` bounding `at` to the JS-representable range (year-0001 is PG-finite but unrepresentable) and `matching_journal_payload_size` capping payload documents at 64KiB of canonical jsonb text. All nine vectors now reject at insert. Existing poisoned namespaces surface loudly at migration time: the new `CHECK`s validate pre-existing rows.
4. **A blocked append hung forever — and hung `load()`/`close()` with it (`postgres-journal-store.mjs`).** The serialized write tail had no timeout anywhere: holding the namespace's advisory lock left `append`, `load` and `close` pending indefinitely (verified live — `pg_advisory_lock` on another session froze all three). The pool now sets `lock_timeout: 5000` (server-side bound on blocked statements, covers the advisory-lock wait inside `append_matching_journal`), `query_timeout: 15000` (client-side bound covering a dead or blackholed server mid-query) on top of the existing `connectionTimeoutMillis` acquire bound — every write path now fails within a bounded window and latches loudly.
5. **Operations before/without initialization queued into a latent failure (`postgres-journal-store.mjs`).** `append` before `initialize()` enqueued a write that later threw `StoreUnavailableError` inside the tail — latched, but discovered only at the next awaited op; `initialize()` was not single-flight, so a concurrent second call built a second pool that leaked on schema-check failure. `append` now throws `StoreUnavailableError` synchronously until the schema check passes (`ready`), `close()` marks the store closed, and `initialize()` is single-flight behind one promise — concurrent callers share the same pool.

## Verified clean

- **Batch atomicity.** One append = one statement inside the function's implicit transaction: a batch either lands whole or not at all (partial rows impossible — the SIGKILL-mid-batch case dies inside the transaction and rolls back); the advisory `pg_advisory_xact_lock` serializes concurrent writers per namespace, so stored seqs can never interleave.
- **Recorded-stream integrity below the store.** `UPDATE`/`DELETE`/`TRUNCATE` reject on the table's `ENABLE ALWAYS` triggers (replica role cannot bypass — the #310 class pin holds); direct `INSERT` still runs the seq-continuation trigger and all `CHECK`s; `schema_migrations` is append-only with version-sequenced rows.
- **Round-trip parity.** `load()` returns jsonb payloads; the wave-59 byte-identical snapshot pin passes through durable rows (canonicalized key order is value-equal by construction — deepEqual, not string equality).
- **Replay remains the semantic gate.** Schema now blocks envelope-grammar violations, but registry membership, per-instrument scale, fill-pair bookkeeping and ordering semantics stay the replay fold's — a well-formed event naming an unknown instrument still lands and still fails replay as designed (schema cannot and should not encode the instrument registry).
- **Failure surfaces.** Unreachable DSN → `StoreUnavailableError` at `initialize()`; client-side contract violations (non-array, non-integer/non-contiguous seqs) → synchronous `StoreError`, non-latching, identical to memory; storage failures and diverged-history rejections → latched `StoreUnavailableError` on every later op including `close()`.
- **Contract boundary.** The journal stores event data only — `posting` is pinned to the `none` literal in the payload grammar `CHECK` (`p_event ->> 'posting' IS DISTINCT FROM 'none'` rejects); nothing on this path writes ledger postings or order state outside the journal table.
- **DSN hygiene.** `unavailable()` maps every failure to `StoreUnavailableError` — the connection string never appears in error paths.

## Observations (recorded, not defects in this slice)

- The engine's write-behind seam means the *first* rejected append of a diverging writer still settles invisibly (the operation's events are already in the in-memory journal) — inherent to the `finish` contract the engine owns; the fix narrows it to one silent op instead of an unbounded silent fork: every subsequent op throws synchronously, `load`/`close` refuse, and no coincidental interleaving ever lands.
- Two engines on one namespace remains an unsupported configuration — now a loudly-unsupported one. The dedupe rule exists for one writer's retry after a lost response, not for sharing a namespace.
- The journal table is intentionally unbounded (dev-only groundwork; no TTL or archival applies); boundedness lives on each payload document (64KiB cap) — recorded in a `COMMENT ON TABLE` on the migration.
- `query_timeout` is a per-query bound; a server that opens connections but wedges every statement still surfaces within ~15s, then latches. `idleTimeoutMillis` reaping stays unchanged.
- The memory backend's redelivery check compares canonical JSON (sorted keys, `undefined` dropped); the SQL side compares jsonb equality — equivalent for all engine-emitted payloads (decimals travel as strings, integers as JSON numbers).
- `initialize()` after `close()` is not a supported revival path — `close()` is terminal (`ready`/`closed` flags make the outcome deterministic rather than order-dependent).

## Test additions

- `tests/journal-store-contract.mjs` (shared, both backends): identical re-append dedupes; prefix-replay batch lands only its tail; conflicting re-delivered seq rejects.
- `tests/postgres-journal-contract.mjs` (+10 cases): conflicting re-append latches with sync-throw on the next `append` and rethrows on `load`/`close`; fresh-engine-on-recorded-namespace diverges loudly (second `submitOrder` throws `StoreUnavailableError`; durable stream untouched); append-before-initialize synchronous throw; concurrent `initialize()` single-flight; advisory-lock-blocked write fails inside the lock timeout instead of hanging; nine grammar-violating payloads rejected at insert; `at` outside the JS range rejected; oversized payload rejected; identical redelivery after a lost response.
- `tests/snapshot-replay-audit.test.mjs`: the untouched-stream case now exercises a *conflicting* re-delivery (identical redelivery dedupes under the new contract).
- Repro-verified failing on `origin/main`: memory arm — 2 shared-contract dedupe cases; postgres arm — 6 cases fail plus the blocked-write case hangs indefinitely (the suite could not complete — the hung-append defect demonstrated directly); and all nine hostile payloads were observed to *insert cleanly* on the old schema in a live probe before replay rejected them.
