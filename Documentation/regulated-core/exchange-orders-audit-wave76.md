# Exchange-Orders, Postgres Store and Contract Machinery Audit — Wave 76 — Proposed

- Status: Proposed
- Scope: `packages/customer-api/src/exchange-orders.mjs` — the second-largest customer-api module, previously unaudited; it serves `/customer/exchange-orders` (collection + member), `/customer/trades`, `/customer/markets` and `/customer/markets/{instrument}/depth`, the order read surface wired through miniapp OrdersSheet. Plus `postgres-store.mjs` (the PostgreSQL persistence seam for rate-limit buckets and auth sessions — the session stores were audited in wave-62, the data store here) and `contract.mjs` (the module-level contract machinery: OPERATIONS, metadata, gap statuses), cross-checked against `app.mjs` dispatch, `store.mjs`, the `matching-core` engine and `postgres-journal-store.mjs` for the wave-338 comparison. Everything is dev-only and synthetic — no production paths, no live data, no execution surface exists anywhere.
- Production effect: none

Hunt list applied: view derivation (status/side/type literals, scale-canonical decimals, id grammar, timeline coherence, cross-subject isolation, sort stability); the store-divergence class vs journal-store's wave-338 fixes (latched vs swallowed writes, idempotent redelivery, canonical equality on overlap, `lock_timeout`/`query_timeout` pins, single-flight init, schema pinning); contract drift blindness and silently skipped validators; pagination/cursor binding; capability gating and deny-before-open order; uniform query grammar; hostile ids/instruments/scales/unicode/oversized inputs.

## Defects found and fixed

1. **Fill-event drift was silently under-reported across every projection (`exchange-orders.mjs`).** `orderTrails`, `projectExchangeTrades`, `projectExchangeOrderDetail`'s fills loop and `lastFillsByInstrument` each dropped a malformed `partially_filled`/`filled` event: a subject fill missing its price, quantity, fill id or leg ids produced a contract-valid but incomplete view — the trades list returned an empty array, the detail read returned fewer legs, and the markets/depth reads silently lost the instrument's `last_trade` (all repro'd on drifted stub engines — an empty list rather than a refusal). The module's own convention is fail-closed (unknown scenario ops throw `TypeError`); every fold now throws on journal drift and the `OrderTrail` leg typedef is non-nullable, so no projection can emit a view that quietly lost one of the subject's executions.
2. **The member-read validator let market orders sit in non-terminal states (`exchange-orders.mjs`).** The collection guard pins `order_type === "market"` to `status === "rejected"`, but `validExchangeOrderDetailView` carried no market-status pin at all: a drifted detail with `order_type: "market", status: "open"` (or `cancelled`/`expired`) passed every check — exact keys, recomputed amounts, coherent timeline (repro'd). A market order never rests and is never cancelled or expired; the detail pin now admits only `"rejected"` and `"filled"` for market types, the only two outcomes the projection can honestly emit.
3. **`close()` racing `initialize()` resolved success on a dead rate-limit store (`postgres-store.mjs`).** `openOnce` drained the orphan pool on a close race but returned normally, so startup reported a healthy store whose every later consume can only fail — the auth-session store in the same file already threw `StoreUnavailableError` on the identical race (repro'd live: `close()` during the probe resolved `initialize()` cleanly). The rate-limit arm now throws the same way after draining, and a later sequential `initialize()` still reopens cleanly.
4. **Neither pool pinned `lock_timeout` (`postgres-store.mjs`).** journal-store's wave-338 hardening bounds lock waits at 5 s so a statement waiting on another session's lock fails instead of stalling; here the rate-limit consume waited on a peer's bucket-row upsert lock and the auth-session store's tail-serialized writes waited on `pg_advisory_xact_lock` — both bounded only by the 15 s client-side `query_timeout` (repro'd live: a held `FOR UPDATE` row lock stalled the consume ~15 s, a held session-level `pg_advisory_lock` stalled the issue ~15 s). `lock_timeout: 5_000` is now pinned on both pools; post-fix both fail at ~5 s.

## Verified clean (with negative pins)

- **View derivation is contract-exact end to end**: every order/trade/market row recomputes quote/fee/total at the declared scales with the same rounding modes the simulator uses; statuses, sides, types, liquidity and pair literals are allowlisted; ids pin `ord_|trd_` + 24 lowercase hex; `isIsoTimestamp` reserializes and bounds `Date.parse` totality; open orders stamp `updated_at === created_at`; the collection and trades validators pin unique ids; markets emit in canonical `ORDER_PAIRS` order; depth rows stay strictly side-sorted, cap at 16 levels and never cross the book. Pair definitions drift-check against matching-core `INSTRUMENTS` at module load — a mismatched instrument, asset or scale throws at import.
- **Cross-subject isolation is structural**: intents, owners and ids all derive from the subject digest; `orderFor`/`depthFor` return `null` on foreign members → the pinned 404; every directory rebuilds scenario and engine per call — nothing is retained or memoized across subjects or requests.
- **Write-failure latching matches the wave-338 class where it matters**: the auth-session store tail-serializes every write and latches `failure` on any non-`StoreError` rejection; SQLSTATE 22/23 map to deterministic `StoreError` without latching; reads join the tail then rethrow the latch; `initialize` is single-flight, resets `closed`/`failure`/`tail` and reopens cleanly; `close` drains the pool and rethrows the latch; the schema probe pins `schema_version = 2` plus a rolled-back issue/refresh/get probe.
- **The consume path needs no latch**: the rate-limit consume is one atomic statement whose rejection the caller observes synchronously — unlike a tail-serialized append it cannot diverge history silently. Its single-flight `initialize`, schema probe and pool drain-on-failure match the sibling arm's posture after fix 3.
- **Redelivery semantics mirror the memory backend exactly**: session issue conflicts resolve through the CTE conflict check → deterministic `StoreError` (issue is not idempotent by design on either backend); refresh/bind/revoke/sweep/list reproduce the memory model field-for-field including tombstone bounds and monotonic `GREATEST` fields.
- **The contract machinery cannot silently skip validation**: every dispatch arm validates the view before `send`, the pipeline ends in `throw new Error("No dispatch arm exists for the matched operation")`, `OPERATIONS` statuses are enforced by the conformance and coverage suites, `API_METADATA.contract_version` matches api-contracts `info.version` (`"1.0.0-draft"`), and `CONTRACT_GAP_STATUSES` reuse the 400/404 envelope so internal-guard failures never escape the declared shape.
- **Deny-before-open order is pinned**: body/shape headers → device-id rule → request-id → metadata → client-version/platform → rate limit → bearer + audience → capability — a malformed request 400s before auth and an unauthenticated one 401s before any capability 403/404, matching the wave-333 order. The orders surface gates on `customer.exchange-orders.read` (collection and member), trades on `customer.trades.read`, markets and depth on `customer.markets.read`.
- **Query grammar is uniform**: `queryOperation` admits only `getOperatorQueue`/`getOperatorAudit`; any query string on the orders/trades/markets/depth routes is the pinned contract 404 (openapi.yaml declares no query params for them); the two query ops run strict allowlists — an unknown key, a duplicated parameter or an out-of-enum value answers 400, never 500.
- **Pagination is absent by design on this surface**: the order/trade/market collections declare no cursor or limit, so no foreign-cursor acceptance or unstable page boundary exists; the operator audit cursor machinery that does exist runs a strict allowlist elsewhere.
- **Hostile inputs stay outside the grammar**: member order ids pin `ord_[0-9a-f]{24}` (non-matching ids are 404s before any lookup); `{instrument}` segments match a single-decoded `[A-Z0-9]{2,8}/[A-Z0-9]{2,8}` template — lowercase, malformed escapes and encoded slashes all 404; `{orderId}` matches `[a-z][a-z0-9_-]{2,127}` without decoding, so unicode, dots and raw `%` never reach the directory; an `X-Device-Id` on customer routes still 400s before auth (the wave-67 pin).

## Observations (recorded, not defects in this slice)

- **`decimal()` assumes non-negative units**: a negative bigint would emit a malformed string — unreachable by construction (units are drawn and derived non-negative, and every caller's recompute is checked against the view), noted as a dead-code edge.
- **Per-subject order ids are 128-bit digest draws**: a deterministic collision would surface as a 500 through the unique-id validator rather than a wrong row — theoretical, recorded.
- **The auth-session probe covers issue/refresh/get only**: revoke/bind/sweep/list statements are unprobed at startup — they share the same table and all are exercised live by the contract suite; recorded as the intended partial-probe design.
- **A `lock_timeout` failure latches the auth-session store**: consistent with the wave-338 write-failure posture (a rejected write cannot prove it never landed); `close` plus `initialize` recovers it. The rate-limit consume carries no latch to trip — a single statement the caller observes.
- **journal-store's `initializing` is never reset after close**: a post-close re-init returns the stale resolved promise (inert — the pool is already null); out of scope for this package, noted for the matching-core slice.
- **Directory cost is O(scenario) per request**: the directories rebuild the whole scenario and engine per call — pinned deliberately: no retained engine, no cross-request state, the isolation guarantee itself.
