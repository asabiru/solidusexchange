# Miniapp Chain Arm Mutation Audit — Wave 78 — Proposed

- Status: Proposed
- Scope: `packages/e2e-dev/tests/miniapp-chain.test.mjs` — the last e2e arm never mutation-audited (resilience, oidc, dev-stack and operator-chain all got theirs in waves 70–77) — plus the shared harness floor it stands on: `tests/stack.mjs`, `tests/postgres-stack-contract.mjs`, `tests/postgres-journal-helper.mjs`, `tests/postgres-stack.sh`. Everything is dev-only and synthetic — no production paths, no live data.
- Production effect: none

Hunt list applied: mutation-test framing on every assertion cluster — for each contract axis (member-binding, exact-body vs shape-only asserts, session isolation, deny-path pins, query-param grammar, degrade→recover round-trip, idempotency on writes, readiness signals, persistence claims) the question was "if the product did this wrong, would the arm go red?". Every defect below was proven green-arm on the mutated product or harness before the fix landed; the mutations were introduced only as proofs and reverted — no product change ships in this slice.

## Defects found and fixed

1. **The session view was a shape-only assert (`miniapp-chain.test.mjs`).** The arm asserted `authenticated`/`source`/`kyc` on `/bff/session` but never the served subject identity — mutating the server to drop `customerRef` stayed green (proven). All three session kinds now pin the literal key set (`["authenticated","customerRef","displayName","expiresAt","kyc","source"]`), the constant `displayName`, the `SC-DEV-[0-9A-F]{5}` customerRef grammar and `expiresAt > Date.now()`.
2. **The fixture roster was never echoed verbatim.** The five checks came back through a loop over derived rows, so a store returning an extra fee field or a swapped `claimRule` stayed green — mutating the fixture to serve a rewritten row proved it. The roster test now pins the five literal check rows verbatim, and the screening/support member reads deep-equal their full documents (echo, resubmit, second submit and hostile bodies for screening; echo, second request and hostile bodies for support).
3. **The quote preview contract was status-plus-two-fields.** A `feeBps` drift of one basis point stayed green (proven). The preview now pins the arithmetic contract — `feeBps: 30`, `spreadBps: 50`, `ttlSeconds: 30`, `feeAsset` per direction, net-out within five percent of `amountIn`/`rate` minus fee — plus the reverse pair (USDT→RUB), the gated-session pins (`insufficientBalance`, `executable: false`, `executionUnavailableReason: "dev_test_version"`) and a hostile battery with the correct per-class codes (`invalid_pair`, `invalid_amount`, `invalid_request`).
4. **The check preview had no hostile-grammar battery.** Its `?bogus` probe existed but the per-class codes did not: mutating the grammar to collapse the codes stayed green (proven). The preview now pins `invalid_asset` on a missing/bogus asset, `invalid_amount` on a missing/bogus/negative/zero amount and `invalid_request` on extra keys, alongside the verbatim constants (`CHK-[0-9A-F]{12}`, `feeBps: 30`, `ttlSeconds: 259200`, `claimRule: "personal"`, `expiresAt - issuedAt = ttl·1000`).
5. **The KYC status read was never bound to the upstream view.** `/bff/kyc/status` serves the upstream contract view on a configured stack, but the arm asserted nothing against it — a route leaking the local submitted state stayed green (proven by the resubmit path drifting). The lifecycle test now deep-equals the view against `expectedKycView(telegramUpstreamSubject)` before and after the local submit, pinning that local writes do not leak into the upstream-derived surface.
6. **Mark-read had no truth battery.** `unread` was asserted once, so a mark-read reporting a count without decrementing, a remark that mutated rows, a foreign-session mark or a phantom id each stayed green (proven: a mark-read that reported `marked: 1` without changing state). The test now pins `marked: N→0`, a 0-op remark, a foreign session marking zero of this subject's ids, a phantom id as a 0-op, and hostile bodies (`null`, string, `{ids:"x"}`, non-array members, over-long arrays) answering `400 {error:"invalid_request"}`.
7. **Session revocation pinned nothing.** `/bff/sessions` serves upstream `sess_[0-9a-f]{24}` ids while `/bff/sessions/revoke` requires local `ses_[0-9a-f]{32}` HMAC handles that are never served — the route is unreachable by design, and a `revoke-others` that silently skipped siblings stayed green (proven). The test now pins the grammar boundary (upstream-shape handle → `400`, well-formed `ses_*` → `404 not_found`), then drives `revoke-others` on a verified dev session, asserts the sibling cookie answers `401`, and re-mints the gated session it evicts (all dev logins share one synthetic subject).
8. **KYC resubmit did not pin idempotency.** Mutating the store to return `created: true` on a resubmit stayed green (proven). The second submit now pins `created: false` and a deep-equal view, and the write-lifecycle test ends on a `reapply` path answering `409 {error:"kyc_already_verified"}`.
9. **The hostile session-issuance battery was thin.** Wrong-token telegram logins were probed but the full grammar was not — a forged initData, a wrong KYC enum, a missing Origin, a cross-site POST or an extra body key each stayed green (proven). The battery now pins per-class codes: `invalid_hash`, `stale_auth_date`, `future_auth_date`, `invalid_user`, `missing_hash`, `duplicate_key`, `fetch_site_rejected` (403 on cross-site), `415` on non-JSON content types, `404` on an originless dev POST, and `set-cookie: null` on every forged attempt.
10. **POST/PUT/DELETE on read routes answered whatever the tail gate produced.** No battery asserted the deny, so letting an upstream POST fall through to GET handling stayed green (proven). The tampered-query test now runs a 13-route POST→`404` battery, PUT/DELETE/PATCH on `/bff/checks`→`404`, the hostile `?limit`/`?kind` forms→`400`, the upstream query battery→`CAPABILITY_DENIED`, and upstream POSTs to the check paths→`404 CAPABILITY_DENIED` with the `request_id` echoed as the issued UUIDv7.
11. **The degrade arm never verified recovery.** The outage path was pinned but the post-restart reads were not — a degraded latch that survived the upstream's return stayed green (proven: a latch throwing on the first transport failure after the outage kept every read degraded). Recovery now re-hits every previously degraded route with its exact contract: gated collections as `{mode:"test", kyc:"kyc-gated", [key]:[]}`, the five-check roster, member reads, `mode:"test"` notifications and activity, the quote constants (`feeBps: 30`, `insufficientBalance`, `executable:false`), the check-preview `mode:"test"` and `"10.000000"` amount, and the operations/markets member `404`s.
12. **`stack.mjs` `readJson` satisfied a bare content-type prefix.** A response served as `application/json-evil` passed a plain `includes("application/json")` check — mutating the BFF's `json()` to emit that content type left the whole arm green (proven: every test passed until the pin). `readJson` now requires `^application/json(?:;|$)` — a parameter boundary or end-of-string, never a prefix.
13. **`postgres-stack-contract.mjs` session statuses pinned only the status.** Every `/api/v1/customer/session` probe asserted `200`/`401`/`429` and nothing about the body — mutating the handler to serve a constant `expires_at` stayed green (proven). The `200` path now pins `subject`, `actor_type: "customer"`, a non-empty string `scopes` array, `expires_at` equal to the minted token's expiry as its canonical ISO instant, and `x-request-id` echoing the issued UUIDv7.
14. **`postgres-journal-helper.mjs` verify was count-plus-tail.** A store that rewrote an earlier row's payload on append still satisfied `stream.at(-1).seq === stream.length` — mutating `load()` to serve a corrupted earlier row kept the count-and-tail assertions green while the served history was wrong (proven). Verify now deep-equals the served stream against the restored engine's `journal()` — content parity, not just length and tail seq.

## Verified clean

- **POST→read-route mutation is double-gated.** The POST-block tail `404` and the `request.method !== "GET"` gate both stand between a POST and the GET handlers: mutating either alone stays green (verified — the other gate catches it), and opening both at once kills the arm outright. The 13-route battery pins the end-to-end contract regardless.
- **The screening resubmit is pinned.** Re-creating the screening on resubmit dies four ways on the pinned arm (roster member deep-equal, query battery, isolation, outage recovery) — no additional pin needed.
- **`postgres-stack.sh` waits on a real readiness signal.** The arm uses `docker compose up --wait`, which blocks on the compose healthcheck (a live `pg_isready`-style probe inside the container), not first-response or a timer; migrations then run against the reported port. Without docker it prints a loud skip notice and does nothing — the arm is unexercised there, not failed, which is the documented degrade.
- **The contract cannot pass half-dead.** It drives rate-limit persistence across a customer-api restart and journal persistence across independent helper processes end-to-end; a store that cannot write fails the appends, and a store serving rewritten history now fails the content-parity verify.

## Observations (recorded, not defects in this slice)

- `/bff/sessions/revoke` is unreachable on the configured stack: the roster serves upstream `sess_*` ids while the route requires locally minted `ses_*` handles that are never served — dead code by design; the arm pins both boundaries rather than the unreachable happy path. `revoke-others` is the reachable eviction surface and is pinned.
- `initData` `too_large` is unreachable: the 4KiB JSON-body bound fires before the 16KiB initData check, so the class is covered by the body-grammar `400 invalid_request` pins.
- All dev logins share one synthetic dev subject, so `revoke-others` on one dev session evicts the others; the test re-mints what it needs rather than assuming isolation there.
- Envelope verification exists only on the backoffice BFF — the miniapp BFF emits bare JSON, so the envelope-verification class from earlier waves has no surface here; the equivalent pins are the content-type boundary in `readJson` plus exact-body deep-equals everywhere.
- The "3 check POSTs" exist only in the OpenAPI contract — customer-api serves a GET-only surface — so idempotency is exercised where writes exist (KYC submit resubmit, mark-read remark) and the check paths are pinned as upstream `404 CAPABILITY_DENIED` with `request_id` echo.
- The synthetic KYC directory marks every subject unverified, so `requiresVerifiedKyc` reads `403` by construction and the BFF degrades in place; the served checks list is always the kyc-gated derivation.

## Deviations

- Envelope verification (forged signature / wrong key / missing requestId / non-canonical issuedAt) could not be applied verbatim: the miniapp BFF has no envelope surface — that class exists only on the backoffice BFF, already pinned in wave 70. Its miniapp-side equivalents are the `readJson` content-type boundary and the exact-body deep-equals.
- The check POSTs are contract-only upstream, so there is no write surface to mutate; the deny-side battery (POST→`404 CAPABILITY_DENIED`, `request_id` echo) stands in for the idempotency sweep.
- The arm cannot drive a verified-KYC journey on this stack (the synthetic directory is unverified for all subjects); the verified session surface is exercised through the dev-session kinds, which mint verified sessions directly.
- The local postgres container for the contract arm was reused across runs to avoid the pinned-image registry pull; schema resets between runs were done via `DROP SCHEMA` + re-migrate rather than container teardown.

Every defect case above was proven green-arm on the mutated product or harness before the fix landed; all mutations were reverted, the arm plus the full `packages/e2e-dev` suite (147 tests) pass on the fixed harness, and the postgres contract arm passes against the live container.
