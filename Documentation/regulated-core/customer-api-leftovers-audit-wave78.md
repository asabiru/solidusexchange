# Customer-API leftovers audit — wave 78

- Status: Proposed

Wave 78 closes out the customer-api surface: waves 53/54/56/76/77 audited the dispatcher, capabilities, the operator surface, exchange-orders, the postgres store, the contract table, auth-session stores, token machinery and eleven served-read builders. What remained unaudited: the six remaining served-read builders (`users.mjs`, `profile.mjs`, `wallets.mjs`, `notifications.mjs`, `support.mjs`, `deposit-addresses.mjs`), the edge infra (`rate-limit.mjs`, `observability.mjs`, `auth.mjs`, `config.mjs`, `request-id.mjs`, `server.mjs`), and the only three mutating contract operations — `previewCustomerCheck`, `claimCustomerCheck`, `cancelCustomerCheck` — end to end: declared grammar in `packages/api-contracts`, adapter-side validation and lifecycle arithmetic in `packages/provider-simulators/src/checks.mjs`, envelope verification ahead of projection mutation in `callback-inbox.mjs`, and consistency with the served read. Every defect below was reproduced as a failing test before the fix landed in the same change.

## Defects found and fixed

1. **User accounts could be served with a creation date — and modification date — in the future.** `buildUserView` drew `created_at` from `BASE_MS` plus a 90-day window, so a quarter of subjects carried `created_at` ahead of the reader (measured 274/500 subjects, max 2026-11-14) and a third carried a future `updated_at`. Every sibling builder draws records only from the elapsed span of the synthetic epoch. The builder now draws registration the way the profile record does — inside the 90 days ahead of `BASE_MS` — and the bounded 30-day update window can no longer push `updated_at` past 2026-10-01, so a served account record never reports a future event.
2. **Metrics and log lines mislabeled query-bearing served requests as `unmatched`.** `routeOf` matched the raw request target — `?` included — so the two query-bearing operations (`getOperatorQueue`, `getOperatorAudit`) and every denied request carrying a query never matched their declared template: real traffic inflated the `unmatched` bucket while the route it hit went uncounted, and a query string on any declared route had the same effect. `routeOf` now splits the path from the query before matching; `unmatched` stays reserved for paths nothing declares.
3. **A served check charged a 0.3% fee the checks domain forbids.** `buildCheck` minted `fee_amount` as `ceil(amount * 30bps)` — nonzero on every served check — while the simulator pins `fee_amount` to zero in this slice and its callback validator refuses a nonzero fee outright: claiming the same check through the contract commands reports a different fee than the read shows. The served builder now emits the pinned zero fee and `validChecksView` fails closed on any nonzero fee, mirroring the outstanding-amount rule it already enforced.
4. **The notifications guard never bound `text` to the template dictionary and never pinned feed order.** `validNotificationsView` let any 1–128 character body pass next to a valid template — a drifted or cross-template body included — and any `created_at` order. The guard now requires `text` to be exactly the dictionary entry the template names and `created_at` strictly decreasing across the feed, like the operations and activity collections.
5. **The support guard never bound `topic`/`message` to the category dictionaries, ticket ids, or feed order.** `validSupportTicketsView` let drifted topics and messages through beside a valid category, along with duplicate `ticket_id`s and an ascending feed — shape-checked but not derived. The guard now binds `topic` and `message` to the category's dictionary entries verbatim, refuses duplicate ids, and pins strictly decreasing `created_at`.
6. **The deposit-addresses guard pinned the allowlisted pairs but not their order or mint instants.** `validDepositAddressesView` let a reversed list and arbitrary `created_at` values through — the builder emits the three custody-dev-v1 targets in declaration order at `BASE + index·1d`. The guard now pins exactly that order, the per-index mint instant, and unique `deposit_address_id`s, matching the strictness the support and screening guards already carry.
7. **The simulator's `idempotency_key` bound was looser than the declared contract.** `idempotencyKey` enforced `^[A-Za-z0-9._:-]{8,128}$` while the `IdempotencyKey` schema declares `{16,128}` — the last line of defense let keys through that the boundary forbids. The shared bound is now `{16,128}`; forty test fixtures that relied on shorter keys were lengthened without changing what they exercise.

## Verified clean

- **Rate-limit math and key handling.** `consumeFixedWindowBucket` denies at the limit with `retryAfter = ceil((resetAt − now)/1000)`, resets an expired bucket rather than accumulating, and fails closed at `maxKeys` (sweep stale keys, then deny) — pinned by the wave-78 isolation cases and the store contract suites. A non-finite clock denies instead of writing a NaN `resetAt`. The key is the caller's per-peer choice — IPv4 loopback collapses to `127.0.0.0/8` by comment — a service-level throttle, not a per-subject one (recorded below as an observation, not a defect). The store seam (`assertRateLimitConsumeCommand`) bounds key shape, window, limit, `maxKeys` and clock sanity, and the memory/postgres backends answer the same decision on the same sequence.
- **Observability hygiene.** `/metrics` requires a loopback peer plus a single loopback Host with no origin/forwarded/via/x-forwarded-*/x-real-ip and only an absent-or-"none" `sec-fetch-site`; labels are bounded to declared routes plus `unmatched` and escaped for Prometheus. Log lines carry only the fixed `LOG_KEYS` — no tokens, subjects, query strings, peer IPs or headers (the request id is a fresh `randomBytes(16)`, never the client's `x-request-id`), pinned end-to-end by the existing leak test.
- **Auth, config, request-id, server.** `auth.mjs` verifies the domain-separated `scdev1`/`sodev1` HMAC with `timingSafeEqual`, bounds TTL by expiry plus max, and returns null on a non-finite clock or anything but a single Bearer. `config.mjs` refuses `NODE_ENV=production`, loopback-binds, regex-pins port and rate-limit values, couples synthetic-auth and the token key in both directions, and pins the store to memory or a postgres DSN. `request-id.mjs` mints UUIDv7 with a bounded clock. `server.mjs` fails fast on store init, cleans up an owned store if auth-store init fails, and re-verifies the loopback bind after listen.
- **Check command surface.** The three POST operations stay declared-but-unserved: the dispatcher's `OPERATIONS` table has no arm for them, so any method hits the pinned 404 capability-denied envelope — no body validation to attack at this layer, verified by `checks.test.mjs`. Adapter-side, `snapshotRequest` does exact-member validation, member binding pins recipient-only claim and sender-only issue/cancel, the claim digest stores `sha256(claim_reference)` only (the secret never lands in the view), failed attempts lock at 25, and each operation family runs an exact-replay `IdempotencyRegistry` — same key plus same request returns the cached response, same key plus a different request returns `idempotency_conflict`. `validateChecksCallback` plus the domain-separated callback verifier gate every envelope before `callback-inbox` mutates the projection; the inbox dedups first, buffers out-of-order arrivals, enforces the transition map, and bounds subjects and event ids.
- **Remaining builders.** `profile.mjs` draws `registered_at` inside the elapsed span with pinned locales and ref/name grammars; `wallets.mjs` emits the fixed RUB/TON/USDT set, one wallet per asset, per-asset decimal scale, no timestamps; the deposit-address derivations produce correct TON (0x91-tag + workchain-0 + 32-byte digest + CRC16) and TRON base58check shapes. The simulated clock advances only forward through a validated safe-integer epoch — no per-call drift that could stamp an event past its deadline.

## Observations

- The rate-limit key is per-peer, not per-subject: on the loopback-only bind one subject's traffic can consume the shared bucket for every subject. That is the intended service-level throttle of a dev-only surface — recorded for the record, not fixed.
- `NODE_ENV` refuses exactly `"production"`; other deployment-flavoured values (`prod`, `live`) are not refused — the guard mirrors the Node convention rather than enumerating aliases.
- `getCheckStatus` advances lazy expiry and parked-callback promotion inside a read — a documented simulated-lifecycle step, not a silent mutation.
- The miniapp check parser tolerates any scaled-decimal `fee_amount`; the zero-fee pin therefore needed no downstream change — the served view and the mutation responses now agree.
- Support tickets, notifications and deposit addresses still tolerate the schema-valid-but-unpinned `text`/`topic`/`message` shapes in the miniapp parser — the upstream guard is strictly stronger, which is the intended direction.

Thirteen new cases in `packages/customer-api/tests/customer-api-leftovers-audit-wave78.test.mjs`, each written to fail on the unfixed code: the past-window user timestamp pin, the query-string route-label pin, the zero-fee served-check pin plus its validator mirror, the template-bound notification body and order pins, the category-bound support fields plus id-dedup and order pins, the deposit-address order and mint-instant pins, the contract-bound idempotency-key grammar, exact-replay/conflict idempotency, member binding on claim and cancel, and rate-limit key isolation plus deny semantics. Existing fixtures updated to the tightened rules: `checks.test.mjs` (zero-fee fixture plus a nonzero-fee rejection case), `support.test.mjs` (dictionary-bound message), `deposit-addresses.test.mjs` (per-index mint instants), `observability.test.mjs` (declared-route label for a query-bearing request), and forty short `idempotency_key` literals across the provider-simulators suite lengthened to the contract bound. The verification-integrity baseline gained the new file's pins and the lint script its `node --check` line.
