# Postgres/JS Ledger Consistency Audit — Wave 70 — Proposed

- Status: Proposed
- Scope: `packages/financial-core` — the JavaScript ledger core (`src/ledger.mjs`, `src/amount.mjs`) versus the PostgreSQL invariant layer (`migrations/0001`–`0013`, `tests/postgres-*.sql` catalog and integrity scripts). The wave-46 ledger-internals audit hardened the JS core; the wave-59/62 audits established the "store divergence" defect class (the database storing what memory rejects and vice versa). This audit checks whether every JS validator has an equivalent SQL twin in both directions. Everything is dev-only and synthetic — no production paths, no live data, no money movement.
- Production effect: none

Hunt list applied: double-entry parity (balanced legs per asset, entry count bounds, per-command uniqueness), canonical-decimal parity (scale bounds, leading/trailing zeros, sign, exponent, precision cap), immutability parity (append-only enforcement on every posting and configuration table), identity/digest binding (`command_digest` uniqueness, idempotency namespace shape, cross-namespace consume), sequence/timestamp parity (the #301 cast-divergence class, #325 `isIsoTimestamp` totality — can SQL store a date JS cannot represent), the trigger-bypass surface (`session_replication_role = replica`, `DISABLE TRIGGER`, trigger enablement policy), and rollback/atomicity (partial-state visibility when a multi-leg posting fails mid-apply). For every divergence a probe transaction was committed against the migrated database (repro-fail first), the same command was shown rejected by the JS core, and the fix landed in the same branch before the audit doc.

## Defects found and fixed

1. **Non-RFC 4122 UUIDs were storable in every `uuid` column (direct-SQL bypass).** The JS `UUID_PATTERN` admits only versions 1–8 with the 8/9/a/b variant; PostgreSQL `uuid` stores any well-formed value. Probe committed on the pre-fix schema: a complete journal with `correlation_id = '00000000-0000-0000-0000-000000000000'` (nil), `causation_id = 'ffffffff-ffff-ffff-ffff-ffffffffffff'` (wrong version nibble), a v9 `entry_id`, and a nil `ledger_accounts.account_id` — every row committed; the JS core rejects the same command with `LEDGER_VALIDATION_FAILED`. The outbox `payload ->> 'journal_id'` CHECK already pinned the RFC-variant regex — the exception that proved the column-level gap. Fixed in `0013_ledger_representation_guard.sql`: thirteen `*_rfc_shape` CHECKs now pin the identical regex on `ledger_accounts.account_id`, `ledger_journals.{journal_id, correlation_id, causation_id}`, `ledger_entries.{entry_id, journal_id, account_id}`, `ledger_idempotency_registry.journal_id`, `ledger_outbox_events.{outbox_id, journal_id}`, `ledger_outbox_delivery_attempts.{delivery_id, outbox_id}` and `ledger_journal_seals.journal_id`. (`uuid::text` renders lowercase canonically, matching the JS `normalizeUuid` lowercase.)
2. **Timestamps outside the JS-representable range were storable (the #325 totality gap).** `assertDateTime` denotes four-digit years 0001–9999 with a zone offset of at most ±14:00 — the instants that grammar can denote are `['0001-01-01 00:00:00+14:00', '9999-12-31 23:59:59.999999-14:00']`. Migration 0010 pinned finiteness but nothing stopped year 15000, BC years or year 0. Probe committed pre-fix: `effective_at = '15000-01-01 00:00:00+00'`; JS rejects the same literal. Fixed in 0013: thirteen `*_range` CHECKs bound every persisted timestamp column to the exact instant range the JS grammar can express — `schema_migrations.applied_at`, `ledger_assets.created_at`, `account_definitions.created_at`, `ledger_accounts.created_at`, all three `ledger_journals` timestamp columns, `ledger_entries.created_at`, `ledger_idempotency_registry.first_seen_at`, `ledger_outbox_events.created_at`, `ledger_outbox_delivery_attempts.attempted_at`, `posting_rule_registry.created_at`, `ledger_journal_seals.sealed_at`. Names sort after the existing `*_finite` constraints so the finite guard still fires first on `infinity` (`ledger_delivery_attempts_attempted_at_range` keeps the `attempts` prefix for that ordering).
3. **Posting-rule registry rows with no JS twin were writable.** `buildPostingRuleRegistry` requires `registry_version = 1`, distinct `allowed_actor_types`, and `entry_pattern` legs of exactly `{definition_code, side}` with a grammar-valid code present in the chart, a `CREDIT`/`DEBIT` side, and no repeated `code|side` signature. Probes committed pre-fix: `registry_version = 2`, `allowed_actor_types = {SERVICE, SERVICE}`, a leg with a grammar-broken `definition_code`, `side = 'SIDEWAYS'`, a leg carrying `{"unexpected": true}`, and a duplicated `{TREASURY_ASSET, DEBIT}` signature — each rejected by the JS loader. Fixed in 0013: `posting_rule_registry_version_singleton` pins `registry_version = 1`, and a `BEFORE INSERT` trigger `posting_rule_registry_validate` (`financial_core.validate_posting_rule()`, `ENABLE ALWAYS`, `REVOKE ALL FROM PUBLIC`) mirrors the leg-shape, actor-distinctness, signature-distinctness and chart-definition-existence checks — set semantics that CHECK constraints cannot express (no subqueries).
4. **`chart_version` values with no JS twin were writable.** `validateChart` requires `chart_version = 1` (status `draft`, required categories, normal-side map); `validateAccounts` enforces the same pinned version on account rows. Probe committed pre-fix: `account_definitions` with `chart_version = 2` plus a matching `ledger_accounts` row (the foreign key happily referenced it). Fixed in 0013: `account_definitions_chart_version_singleton` and `ledger_accounts_chart_version_singleton` CHECKs pin `chart_version = 1` on both tables.
5. **Config-table identity columns carried only text CHECKs where JS requires UUID.** Covered under defect 1 — `ledger_accounts.account_id` is now RFC-pinned like the journal/artifact columns.

## Verified clean (with negative pins)

- **Double-entry parity**: `assert_journal_complete()` (deferred constraint triggers, `ENABLE ALWAYS` since 0006) enforces 2–1000 entries, per-asset debit/credit equality, the posting rule's `entry_pattern` signature set, actor-type membership, legal-entity/asset/account binding and the `sequence_number` bounds — the same rules `validateCommand` applies to the JS command. The reject fixtures (`postgres-reject-incomplete.sql`, `postgres-reject-unbalanced.sql`, `postgres-reject-rule-*.sql`) and the ledger-integrity drift probes pin each arm.
- **Amount parity**: `DECIMAL_PATTERN` (canonical digits, no sign, no exponent, scale 0–18, ≤78 total digits, `minorUnits > 0`) maps exactly onto `numeric` + `isfinite`/`> 0`/scale CHECKs. Probes confirmed every numeric literal form (`+5`, `.5`, `5.`, `1e2`, ` 5 `, `-0.0`, `0005`, `0.000000`) normalizes to the same stored value the canonical JS string would produce — no persisted noncanonical form exists; the wire-grammar differences are read-side only and listed as observations.
- **Immutability parity**: append-only UPDATE/DELETE/TRUNCATE triggers cover every journal, entry, artifact and configuration table, all `ENABLE ALWAYS` (33 non-internal triggers, `tgenabled = 'A'` verified in `pg_trigger`). A direct-SQL UPDATE cannot mutate a posted entry under origin or replica roles — the JS freezeDeep model has its SQL twin.
- **Identity/digest binding**: `command_digest` is globally unique across `ledger_journals`, `ledger_idempotency_registry`, `ledger_journal_seals` and the outbox payload functional index (0012), matching the JS single-digest-single-command map. The idempotency namespace is `(legal_entity_id, idempotency_key)` in both layers; the JS replay-with-identical-digest path returns the prior journal, while the SQL path must reuse an already-committed digest — which the uniqueness constraints reject — so no namespace can consume another's key.
- **Trigger-bypass surface**: every invariant trigger is `ENABLE ALWAYS` (including the new `posting_rule_registry_validate`), so `session_replication_role = replica` keeps all of them firing alongside CHECK constraints — probes under replica rejected non-RFC UUIDs and out-of-range timestamps. Migration-owner `DISABLE TRIGGER`/`DROP CONSTRAINT` inside one transaction is the remaining drift path, and the integrity re-validator now detects that class for the new invariants too.
- **Rollback/atomicity**: JS `post()` snapshots, validates and freezes before mutating the journal maps — no partial state on rejection. PG commits journal+entries+artifacts in one transaction with deferred completeness triggers — no committed partial journal. Commit ordering is equivalent.
- **Migration integrity**: sequential version/name/applied-at guard, canonical source catalog and history manifest extended to version 13 and re-verified.

## Observations (recorded, not defects in this slice)

- **`entry.sequence_number` gaps are not an invariant in either layer**: a probe committed a complete journal with sequence 7 and 42. JS treats entries as an ordered array (no contiguity rule beyond the 1000-entry cap); SQL pins presence and range only. Order is still recorded; contiguity is a deliberate non-requirement, so no fix.
- **`ledger_assets.enabled_for_posting` is a PG-only deny switch**: the JS asset validator has no flag concept (`{code, scale}` exactly). It is a deliberate database-side kill switch the smoke fixture exercises; a JS command referencing a disabled asset has no equivalent gate, recorded as an intentional defense-in-depth asymmetry rather than a wedge — no valid JS command is blocked by it today.
- **Wire-vs-stored grammar differences normalize away**: `+15:00` offsets, leading/trailing-zero forms and unsigned numerics all land on values inside the JS-representable space — read-side flexibility, not a divergence.
- **`posting_rule_registry.entry_pattern` leg-definition binding now runs inside the INSERT trigger**: it reads `account_definitions` at write time, matching the JS registry build which validates against the chart snapshot. Rows written while the trigger was absent are flagged by the `rule_registry_shape` integrity arm.
- **The task's `npm run typecheck` does not exist in this package** (`.mjs` with strict checkJs, no tsconfig): `npm run check`, `npm test` and `npm run verify` are the equivalent gates and all pass; flagged per convention.
