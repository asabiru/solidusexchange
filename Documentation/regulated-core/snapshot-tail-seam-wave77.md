# Matching Core Snapshot+Tail Recovery Seam — Wave 77 — Proposed

- Status: Proposed
- Scope: `packages/matching-core/` recovery machinery — the seam between `src/snapshot.mjs` (canonical snapshots) and `src/replay.mjs` (`replayMatchingEngine`, `replayMatchingJournalStore`) the wave-75 audit (#351) recorded as missing, plus the atomicity of `engine.snapshot()` in `src/engine.mjs` and the bounded tail read on `src/journal-store.mjs`/`src/postgres-journal-store.mjs`.
- Production effect: none

Hunt list applied (from the wave-75 observation): no seam to apply `journal[N+1..M]` onto `snapshot(seq=N)` — snapshot and full-journal replay were two complete recovery paths, so recovery cost grew linearly with journal age. This wave makes them composable: `replayMatchingEngine({ events, base })` folds a tail stream onto a snapshot, and `replayMatchingJournalStore(store, { base })` reads only that tail from a store. Repro verified on `origin/main` before the change: every `base` call failed `unknown option: base`, no `loadAfter` existed on any backend, and the only restore path was seq-1 replay of the whole journal.

## Design

- **The fold seeds from the snapshot, then checks the tail identically.** `replayMatchingEngine({ events, base? })` validates `base` through `parseEngineSnapshot` — the same fail-closed check `restoreMatchingEngine` runs (unknown keys, wrong types, resting list out of book order, counters below the recorded orders, an older `version` → `unsupported snapshot version`) — and hydrates the fold's starting state through `hydrateEngineState`: tracked orders, books with intra-level FIFO, `next_seq`/`next_fill`/`last_at` counters, instrument registry. `base` and `instruments` are mutually exclusive (a snapshot already carries its registry). The tail's first `seq` must equal `base.next_seq` — a gap or an overlap rejects with `seq must continue the snapshot at N+1 with no gaps`, same `invalid event stream` family as a broken prefix stream. Every wave-75 grammar check is unchanged and now runs against snapshot state: operation atomicity, per-operation timestamp uniformity (seeded from `base.last_at`), earned rejections, mid-operation stream end.
- **Snapshot capture refuses mid-operation.** `engine.snapshot()` throws `RangeError("cannot snapshot inside a matching operation")` while an operation is open — inside `finish` the books are already mutated but the counters and journal batch are not committed, so mid-operation state matches no journal prefix a tail could continue. Refuse is the honest semantic: the only reachable in-operation call site is a store's `append` hook calling back, and waiting would deadlock the engine's synchronous pipeline. A probe store whose `append` calls `engine.snapshot()` pins the guard; capture at every other boundary stays legal.
- **Bounded tail read is an optional store capability.** `MatchingJournalStore` gains optional `loadAfter(seq)` — the recorded events with `seq > seq` in order, i.e. `journal[N+1..M]` without reading the prefix. A backend that cannot slice omits it and `replayMatchingJournalStore` falls back to `load()` filtered to the same seqs; the fold re-validates either way, so slicing changes cost, never correctness. The memory backend filters its frozen list; the postgres backend serves `LOAD_SQL` plus `AND journal.seq > $2` off the `(namespace, seq)` primary key — one index range scan, no new migration.
- **No snapshot format bump.** `version: 2` already carries every tracked order with its trail fields, the resting ids positionally (intra-level FIFO), the counters, and the instrument set — everything the fold needs to resume mid-invariants. `inFlight` needs no representation: operations are atomic, so a snapshot can only exist on a boundary where the live engine holds no in-flight order — the same boundary the tail stream's first event must open a fresh operation at. Older `schemaVersion` stays fail-closed by the existing `parseEngineSnapshot` version pin.
- **The journal a tail-restored engine reports is the tail.** `journal()` returns the folded tail stream (seq N+1..M), not the prefix — a snapshot carries state, not history, matching `restoreMatchingEngine`. `seq`/`fill_id` continue from `base.next_seq`/`base.next_fill`; the restored engine can be re-attached to the same store and keeps appending contiguously.

## Defects found and fixed

1. **`order_not_resting` earned-check ignored the submitted instrument (`src/replay.mjs`).** Wave 75 pinned `order_not_resting` to "a valid-pattern id on a non-resting or untracked order" — but the live `cancelOrder` resolves the id inside the *submitted* instrument's book only, so cancelling `order_7` (resting on TON/RUB) against `USDT/RUB` legitimately rejects `order_not_resting` while the fold rejected the stream as unearned. Repro surfaces on the *full replay* path too, not just the seam: any real journal containing a cross-instrument cancel folded as `invalid event stream`. The earned-check now also requires `echoed.instrument === event.instrument` — the live call site can only have echoed the instrument it was invoked with.

## Verified

- **Equivalence is byte-identical, not approximate.** `tests/snapshot-tail-seam.test.mjs` takes a live engine, snapshots it at every operation boundary, then replays the journal tail from each snapshot: `replay(journal[1..M]) ≡ replay(journal[N+1..M], snapshot(N))` on `JSON.stringify(engine.snapshot())`, on `bookSnapshot` per instrument, and on `orderStatus` for every known order — for the scripted wave-59 mixed scenario (crossed books, fills both directions, cancels, validation rejections, self-trade, every amend path, market orders, a second instrument) and for three seeded randomized deterministic streams (mulberry32; 80 operations across three instruments; all seven event types emitted — order-acceptance, `partially_filled`, `filled`, `resting`, `rejected`, `cancelled`, `amended`). The full-replay result and every tail-restored result are the same frozen bytes.
- **Edge seams hold.** A genesis-position snapshot (`next_seq = 1`) plus the whole journal ≡ full replay; a final snapshot plus an empty tail ≡ the live engine; a tail-restored engine keeps processing submissions with contiguous `seq`/`fill_id` and folds identically to the live engine on the next operation.
- **The grammar holds across the seam.** Tail starting at the wrong seq (gap or overlap) rejects; a tail whose first event is mid-operation (`resting`/`filled`/`cancelled` for a resting maker) rejects as `interleaved event while an order is in flight`; timestamp step-back from `base.last_at` rejects; rejection events unearned against the snapshot state reject.
- **Base validation mirrors the journal's fail-closed shape.** Malformed or foreign `base` objects throw `invalid engine snapshot`; `version: 1` throws `unsupported snapshot version`; a tampered resting list throws its positional check; `base` + `instruments` throws; a snapshot stays reusable — validation never mutates the frozen input.
- **Stores serve the tail correctly.** Memory `loadAfter(N)` returns exactly the recorded events with `seq > N`, frozen; a no-slice stub store restores identically through the `load()` fallback; a slicing stub is called with exactly `base.next_seq - 1` and replay performs zero appends (purity pinned). The postgres contract test round-trips writer → durable journal → tail-restore reader byte-identically, and `loadAfter` lands the same rows `load()` would.
- Repro cases verified failing on `origin/main` before the change: 28 of 29 seam tests fail there (`unknown option: base` on every seam path, no `loadAfter`, and the `order_not_resting` fold defect firing on honest full replays).

## Observations (recorded, not defects in this slice)

- **Cross-instrument cancels are rare but real.** The generator surfaced the `order_not_resting` hole only because it cancels resting orders against a random instrument — a caller that always cancels on the resting instrument could never produce the stream the fold rejected. Worth noting for any future fold grammar work: earned-checks must model the call site's resolution scope, not the global order space.
- **`loadAfter` reads a point-in-time tail.** Like `load()`, it reflects durability at call time; events appended later are not part of the restore. Live-engine appends remain journaled through `append` — the restore path reads a slice, never a subscription.
- **PG tail read is bounded by seq, not by row count.** `LOAD_AFTER_SQL` has no `LIMIT` — the tail is unbounded in the worst case (no snapshot ever taken). That is the honest bound: the call site asked for the tail and the fold must see all of it.
- **`RangeError` vs `TypeError`/`invalid ...` families is deliberate.** Mid-operation capture is a programming error in the caller (like `RangeError` on a malformed seq in `loadAfter`), not a malformed stream or snapshot — it keeps the fold's `invalid event stream`/`invalid engine snapshot`/`StoreError` vocabulary clean.

## Test additions

- `packages/matching-core/tests/snapshot-tail-seam.test.mjs` (27 cases): byte-identical seam equivalence at every boundary on the scripted scenario and three seeded random streams; genesis/empty-tail/continuation edges; grammar pins across the seam (seq gap/overlap, mid-operation first events, timestamp uniformity, earned rejections, fill-id continuation, mid-operation stream end); base validation (malformed, older version, tampered resting, mutual exclusivity); store tail reads (memory slice, no-slice fallback, exact `loadAfter` argument, replay purity); and the atomic-capture guard via an `append`-hook probe.
- `packages/matching-core/tests/journal-store-contract.mjs` (+2 cases): `loadAfter` returns exactly the recorded tail across boundary seqs, and rejects a malformed seq boundary with `StoreError` — both skipped on stores without the capability.
- `packages/matching-core/tests/postgres-journal-contract.mjs` (+1 case): a snapshot plus the durable tail restores byte-identically to the full replay on a real PostgreSQL 16 instance, with `loadAfter(0)` matching `load()` length.
- `packages/matching-core/tests/replay.test.mjs` and the wave-75 suite untouched — the seam extends, it does not change existing behavior.
