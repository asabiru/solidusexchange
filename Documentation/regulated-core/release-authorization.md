# Regulated Release Authorization Baseline — Proposed

- Status: Proposed
- Scope: future regulated-core build, deployment and rollback evidence
- Owners: SRE / Security / CTO
- Required approvers: CTO, Security, affected domain owner
- Production effect: none

## Purpose

This baseline defines the evidence and human authorization required before any regulated-core artifact can enter a production environment. It separates a reproducible build from permission to deploy and separates deployment from permission to enable customer, financial, provider or custody execution.

The existing repository deployment workflow is a legacy mechanism. Its presence, successful execution or access to deployment secrets does not approve it for regulated-core services, production data, provider credentials, financial commands, custody signing or customer launch.

## Release principles

1. Build once from an immutable reviewed commit and promote the same verified artifact.
2. A branch, tag, workflow run or passing CI check is not an approval by itself.
3. Every release is bound to architecture, security, finance, compliance and provider gates affected by its scope.
4. Missing evidence, stale approval or unverifiable provenance is a `NO-GO`.
5. Database history, ledger truth, audit evidence and custody evidence are never rewritten to simplify deployment.
6. Production credentials and signing material are not available to pull-request jobs or general CI.
7. Release, feature enablement, provider enablement and custody enablement are separate decisions.
8. Rollback never means reversing committed financial history or restoring an unverified stale database.

## Environment classes

| Environment | Permitted data and authority | Minimum boundary |
|---|---|---|
| Development | Synthetic data; no live provider or financial authority | Local/dev identities, no production secrets |
| Integration | Synthetic or approved masked fixtures; sandbox providers only | Isolated accounts, explicit egress and test credentials |
| Pre-production | Production-like topology with synthetic or legally approved minimized data | Separate identities, no production signing authority |
| Production | Only approved products, data, providers and commands | Protected environment, workload identity, immutable approval and monitored rollback |

Access to one environment grants no access to another. Production data must not be copied into lower environments as a release shortcut.

## Release identity

Every candidate must have one immutable release identity containing:

```text
release_id:
source_commit_sha:
source_repository:
build_workflow_id:
build_run_id:
builder_identity:
artifact_name:
artifact_digest:
sbom_digest:
provenance_digest:
configuration_schema_version:
database_migration_manifest_digest:
contract_version:
created_at_utc:
```

The release record stores references and digests, not secrets. Rebuilding from the same source creates a new candidate with a new build identity and requires new verification.

## Required evidence bundle

| Evidence | Requirement |
|---|---|
| Source review | Exact commit is reachable from the protected repository and all required reviews are immutable |
| CI | Required lint, typecheck, tests, build, audit and policy checks passed for the exact commit |
| Dependencies | Lockfiles reviewed; external actions/images immutable; unresolved critical/high findings block release |
| Artifact provenance | Artifact digest, builder identity, build workflow and source commit are cryptographically bound |
| SBOM | Machine-readable component inventory bound to the artifact digest |
| Configuration | Versioned schema, environment-specific values supplied outside the artifact, deny-by-default feature flags |
| Secrets | Workload identity or approved secret references; no secret values in artifacts, logs or approval records |
| Database | Exact reviewed migration manifest, backward/forward compatibility statement and verified recovery path |
| Contracts | API/event compatibility evidence and consumer impact |
| Financial | Ledger/posting/reconciliation evidence for every affected financial behavior |
| Custody | Intent/policy/approval/signer evidence for every affected custody behavior |
| Data/privacy | Classification, processor, location, retention and migration impact |
| Security | Threat IDs, abuse-case tests, privilege changes and residual risk |
| Operations | Monitoring, SLO, alert ownership, capacity and incident-response updates |
| Rollback | Technical rollback and business recovery criteria tested against the candidate |

Evidence must be generated by approved identities and retained independently from ephemeral CI logs.

## Change classification

| Class | Example | Additional gate |
|---|---|---|
| R0 — Documentation/internal evidence | No executable or policy effect | Repository review and CI |
| R1 — Non-regulated runtime | No customer money, restricted data, provider or operator-privilege effect | Service owner + SRE |
| R2 — Regulated read path | Customer/operator data, audit or reconciliation reads | Security + affected domain owner |
| R3 — Regulated command/control path | Policy, ledger, approvals, provider commands, data migration | CTO + Security + domain owner; Finance/MLRO/Legal as applicable |
| R4 — Custody/signing or systemic financial path | Signer, HSM/MPC, broadcast, opening balances, settlement finality | Explicit custody ceremony and full multi-domain go/no-go |

The highest affected class controls the release. Splitting commits does not lower the class when they are intended to deploy together.

## Approval matrix

| Scope affected | Required human approval |
|---|---|
| Architecture/trust-zone connection | CTO + Security |
| Identity, operator role or privilege | Security + system owner |
| Financial schema, posting or reconciliation | Finance + Financial Core + CTO + Security |
| AML/KYT, eligibility or case workflow | MLRO/Compliance + Security |
| Customer/PII processing or location | Legal/Privacy + Security |
| Provider/bank integration | Domain owner + Finance/MLRO/Legal as applicable + Security |
| Custody/signer/HSM/MPC | Custody owner + CTO + Security + Legal |
| Database migration/recovery | Data owner + SRE + Security; Finance for ledger scope |
| Production feature enablement | Product owner + every affected domain approver |

No agent, workflow, repository administrator or single engineer can substitute for a required domain approver.

## Release flow

### 1. Prepare

- define scope, change class, affected threat IDs and decision-register dependencies;
- identify affected services, data, providers, financial rules and custody boundaries;
- record explicit non-goals and disabled capabilities;
- name release owner, executor, verifier and rollback owner;
- set an approval expiry and deployment window.

### 2. Build

- build from the exact reviewed commit on an approved isolated runner;
- use immutable action, image and dependency references;
- produce artifact digest, SBOM and provenance;
- prevent build jobs from accessing production data, provider credentials or signing material;
- reject artifacts containing secret-like material or unapproved binaries.

### 3. Verify

- reproduce required tests and policy checks;
- verify provenance and artifact digest independently of the build job;
- verify configuration schema and deny-by-default values;
- apply migrations to an isolated representative target and run exact history/catalog checks;
- execute backup/restore, rollback and reconciliation evidence required by the change class;
- resolve or explicitly reject every material finding.

### 4. Authorize

The approval record must bind:

```text
release_id:
artifact_digest:
source_commit_sha:
environment:
change_class:
scope:
enabled_features:
disabled_features:
evidence_bundle_reference:
approver_identity:
approver_domain:
decision: APPROVE | REJECT
conditions:
expires_at_utc:
decided_at_utc:
```

Approval for a different digest, environment, scope or enablement state is invalid.

### 5. Deploy

- deploy the approved digest, never rebuild from a branch on the target;
- use short-lived workload identity and protected environment authorization;
- record executor identity, start/end time, target and observed artifact digest;
- stop on migration, configuration, privilege, health or provenance mismatch;
- keep regulated features disabled until their separate enablement approval is verified.

### 6. Verify after deployment

- attest running artifact and configuration versions;
- verify database migration history, catalog and runtime privilege profile;
- confirm audit-chain continuity and monitoring delivery;
- run read-only health and reconciliation checks;
- confirm disabled commands, providers and signer paths remain disabled;
- record release result and evidence before closing the window.

## Database and financial rollback

- Application rollback may select an older compatible artifact only when its schema and contract compatibility were verified before release.
- A database restore uses an isolated target, exact canonical-state attestation and approved RPO/RTO procedure.
- A structurally valid but stale backup is not a valid rollback.
- Committed ledger journals, audit events and custody evidence are not updated or deleted.
- Financial correction uses reversal or compensating journals under a separate approved command path.
- If compatibility or reconciliation cannot be proven, stop traffic and follow the incident-response baseline.

## Feature and provider enablement

Deployment does not enable:

- customer-money commands;
- production bank, liquidity, KYC/KYT or blockchain providers;
- operator approval or execution controls;
- custody signing, broadcast or mainnet assets;
- production data migration;
- Session D or any later approval-gated scope.

Each capability requires a versioned feature/configuration decision bound to the release and the applicable decision-register evidence. Missing or unknown flags must evaluate to disabled.

## Emergency changes

An emergency does not waive provenance, segregation of duties or evidence preservation.

Minimum emergency record:

- incident identifier and severity;
- exact proposed change and affected trust zones;
- reason normal timing is unsafe;
- source commit and artifact digest;
- available tests and explicitly missing evidence;
- Security and accountable domain approval;
- executor and independent verifier;
- expiry or revert condition;
- mandatory follow-up review and complete evidence deadline.

Direct edits on production hosts, unreviewed SQL, mutable branch deployments and manual secret copying remain prohibited.

## NO-GO conditions

Do not deploy or enable when:

- source, artifact, SBOM or provenance digest is missing or inconsistent;
- required CI, security, migration, recovery or reconciliation evidence failed;
- an approval is missing, expired, conditional on unmet work or bound to another digest;
- production secrets are exposed to build or pull-request jobs;
- the target would rebuild from a branch or fetch mutable dependencies;
- database compatibility, canonical recovery state or rollback criteria are unknown;
- unresolved critical/high vulnerability or threat-model finding affects the scope;
- required monitoring, on-call, incident response or provider escalation is absent;
- regulated functionality would become enabled by missing or implicit configuration;
- D-001 through D-018 dependencies applicable to the scope remain unapproved.

## Current repository boundary

The current `deploy.yml`:

- is manually dispatched;
- transfers deployment scripts and executes an SSH-based legacy deployment;
- uses repository/environment secrets configured outside this document;
- does not produce the regulated release identity, SBOM, provenance, multi-domain approvals or enablement evidence required above.

It must not be treated as a regulated-core production path. Changing or replacing it requires D-015, D-018, threat-model, incident-response and environment-specific Security/SRE approval.

Approval of this baseline authorizes only the release-control design. It does not approve the current deployment workflow, provision production access, enable a provider, migrate customer data, move money, sign transactions or launch the platform.
