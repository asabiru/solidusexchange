# OIDC Flow Adversarial Audit — Wave 65 — Proposed

- Status: Proposed
- Scope: `packages/provider-simulators/src/oidc.mjs` (the RS256 issuer: `/authorize`, `/token`, `/.well-known/jwks.json`, single-use TTL'd authorization codes bound to `client_id` + `redirect_uri` + `code_challenge` + `nonce` + `sub`), `miniapp/src/server/oidc.ts` (the BFF verifier and exchange), the login/callback wiring in `miniapp/src/server/server.ts`, and `packages/e2e-dev/tests/oidc.test.mjs`. Everything is dev-only and synthetic — no production paths, no live IdP traffic.
- Production effect: none

Hunt list applied: code replay atomicity under concurrent `/token` calls, expired-vs-consumed indistinguishability, post-mint binding of `redirect_uri`/`client_id`/`code_challenge`/`nonce`, pending-map eviction order on the 256 cap (expired vs LRU), error taxonomy and internals leakage, parameter length/charset bounds on every input including `login_hint`, multi-valued parameters, `state` reflection in `/authorize` error redirects; verifier-side JWKS handling (fetch bounds, `kid` selection, `alg` pinning, JWK member canonicality and RSA exponent floor), `at_hash` required-when-present, `azp` rules, `exp`/`iat`/`nbf` skew edges, `nonce` mismatch paths, `sub` derivation injection, pending-map bounds under parallel logins, cookie scoping and first-vs-last-cookie semantics; wiring-side 302 `Location` injection, `?error=` reflection, session mint bound to the right `sub`, byte-identical unconfigured 404s, `SEC_FETCH` behavior on auth routes; and an end-to-end hostile issuer arm.

## Defects found and fixed

1. **The issuer answered endpoint paths on any authority (`provider-simulators/src/oidc.mjs`).** `handle()` dispatched on `url.pathname` alone, so an absolute-form request target (`POST http://evil.example/token`) or a scheme-relative one (`//evil.example/.well-known/jwks.json`) parsed off-origin and was still served — proven on main, where a foreign-authority `/token` exchanged a minted code for an `id_token`. An issuer mounted under a path prefix (`{issuer}/base`) also answered `/authorize` outside its prefix. Requests are now refused unless the parsed origin equals the issuer origin and the pathname sits under the issuer path prefix; anything else is `not_found`. Wrong methods on real endpoints now answer `405` with an `Allow` header across the board (previously only `/token` did).
2. **`/token` admitted loose content types, and the duplicate-parameter sentinel could collide with a real client id (`oidc.mjs`).** The content-type check was a `startsWith`, so `application/x-www-form-urlencodedjunk` and `application/x-www-form-urlencoded-x` exchanged codes — proven on main. The media type is now matched exactly (case-insensitively) with parameters such as `; charset=utf-8` still permitted. Separately, `singleParam` returned the literal string `"duplicate"` for multi-valued parameters: a configured `client_id` equal to `duplicate` made every authorization unanswerable, and duplicated form fields fell into the generic exchange-denial bucket. The sentinel is now a `Symbol`; duplicated form parameters on `/token` — and a missing or repeated flow-type parameter — answer `invalid_request`, while a wrong single flow value keeps the spec's unsupported-type name.
3. **An oversized `state` was reflected unbounded into `/authorize` error redirects (`oidc.mjs`).** `fail()` copied `state` verbatim into the `Location`, and the 128-character bound ran only on the validation path — so `response_type`/`scope` failures echoed attacker-chosen state of any length back to the registered redirect URI — proven on main. `fail()` now reflects `state` only when its length is within `MAX_STATE_LENGTH`; the bound check itself keeps yielding `invalid_request` on the validation path, preserving the pinned redirect-style taxonomy including the `""`-state case.
4. **The verifier admitted weak RSA exponents and non-canonical JWK members (`miniapp/src/server/oidc.ts`).** `n`/`e` were checked only for `typeof string`, so padded, whitespace-embedded or otherwise non-canonical base64url members that `createPublicKey` normalizes away were admitted, and `publicExponent` values of 1 or 2 produced a working key — proven on main, where `e = "AQ"` (exponent 1) and `e = "Ag"` (exponent 2) both built keys the verifier used. `n`/`e` must now round-trip exactly through base64url decode/encode, and the exponent must be an odd `bigint` of at least 3 (the modulus ≥ 2048-bit floor is unchanged).
5. **`at_hash` was optional even when an `access_token` had been issued (`oidc.ts`).** The hash was compared only when the claim was present, so a hostile issuer could strip `at_hash` from the `id_token`, keep the `access_token`, and the exchange still verified — proven on main at unit level and end-to-end through the wired callback. `at_hash` is now required whenever an access token is present and must equal `base64url(SHA-256(access_token))[0:16]` exactly.
6. **The token response was not pinned to `token_type: "Bearer"` (`oidc.ts`).** A response carrying `token_type: "MAC"` or none at all resolved into a verified exchange — proven on main at unit level and end-to-end. The token response must now declare `token_type` exactly `Bearer`.
7. **Duplicate JSON members in fetched documents passed silently via last-wins `JSON.parse` (`oidc.ts`).** The token response and the JWKS document parsed normally, so a hostile issuer could serve `{"e":"AQ","e":"AQAB"}` and the verifier silently took the honest member — proven on main at unit level and end-to-end. `readBoundedJson` now runs the existing raw-text duplicate-member scanner on every bounded JSON document before parsing, and rejects on a repeated member.
8. **Cookie lookup was last-wins, letting a broad-path forgery shadow the transaction or session cookie (`miniapp/src/server/server.ts`).** `parseCookies` overwrote earlier pairs, but browsers order cookies most-specific-path first: a `Path=/` `solidchange_ma_oidc_tx` forgery appended after the real `Path=/bff/auth` cookie won the lookup — proven on main, where a valid callback carrying a trailing forged transaction cookie failed, and a session cookie followed by a forged sibling denied a request the real session should have served. Lookup is now first-wins, matching the user's actual cookie order, with `__proto__` skipped.

## Verified clean

- **Code lifecycle (issuer).** Consumption is atomic in-thread — `codes.get` + `codes.delete` run before any validation, so concurrent `/token` calls with the same code resolve exactly one `200` and one exchange-denial `400` (pinned under `Promise.all`). Expired, consumed and never-minted codes return byte-identical exchange-denial bodies (pinned). The binding tuple cannot be swapped post-mint: `client_id`, `redirect_uri`, `code_verifier`→`code_challenge` (constant-time compare) and `nonce` are all re-checked on exchange. On the 256-cap the sweep deletes expired entries before evicting the oldest live one — pinned by a 128-expired + 128-live + overflow scenario. The 120-second expiry boundary is exact (`119s` exchanges, `120s` rejects).
- **Parameter bounds and taxonomy (issuer).** Every query/form input goes through `singleParam` (multi-valued → `invalid_request`, including `nonce`, `state`, `code_challenge`, `login_hint`) plus per-field length/charset bounds; `login_hint` outside `^[a-z0-9][a-z0-9._:-]{0,127}$` — including overlong and control-char values — falls back to `defaultSubject` rather than erroring. Error bodies carry only `{error, state}` with OAuth vocabulary; `unauthorized_client`, `invalid_request`, `invalid_scope`, `unsupported_response_type`, `not_found`, and the spec's two exchange-path denial names — nothing leaks stack or internals.
- **Signature and header rules (verifier).** `alg` pinned to `RS256`; `kid` required non-empty and matching exactly one JWKS entry (zero or two matches both reject); `crit` refused wholesale and `jku`/`jwk`/`x5u`/`x5c`/`b64` rejected; JWK `kty`/`use`/`key_ops`/`alg` pins, no private members, modulus ≥ 2048 bits. All three JWT segments are canonical unpadded base64url; a raw-text duplicate-member scanner guards the header and claims; the token is capped at 16,384 characters.
- **Claims (verifier).** `iss` exact match; `aud` string-or-string-array with required membership; `azp` required whenever `aud` is multi-valued and must equal the client id; `exp > now`, `iat ≤ now + 60`, `nbf` finite and ≤ now + 60; `nonce` compared with `!==`; `sub` printable ASCII, 1–255 characters, and the derived subject is `dev-` + truncated HMAC-SHA256 over a namespaced preimage, so claim characters never reach storage verbatim.
- **JWKS fetch (verifier).** No cache: every verification fetches fresh, so issuer rotation needs no invalidation path; each fetch is bounded by `redirect: "error"`, an 8-second `AbortSignal.timeout`, and the 65,536-byte document cap.
- **Login/callback wiring.** `pendingOidcLogins` is an `ExpiringStore` capped at 2 pending flows per initiator and 256 globally, newest retained; the transaction cookie is `state.nonce`, `Path=/bff/auth; HttpOnly; SameSite=Lax; Max-Age=600`, single-use via `take`. The callback 302 `Location` is always the configured `allowedOrigins[0]` — no input-derived target — and `?error=` is folded into the generic `auth_failed` redirect without reflection (including `\r\n` payloads). Session mint happens only after signature + claims verify and binds to the verified `sub`; two concurrent callbacks racing on one pending entry produce exactly one success and one `auth_failed`. Unconfigured auth routes answer a byte-identical 404 to unknown routes. `SEC_FETCH` guards deliberately do not run on auth routes — the callback arrives cross-site and is bound by the transaction cookie — while `X-Device-Id` on an auth route still 400s.
- **e2e arm.** A hostile-issuer fixture (its own RSA key, echoing `state`, capturing `nonce`, minting arbitrary `id_token`s) drives the wired flow; `at_hash` absent/mismatched, `token_type: "MAC"`, nonce/issuer mismatch, foreign `azp`, and expired `exp` all fail closed with `auth_failed` and no session cookie, while an honest forged token still mints a session for its own `sub` only.

## Observations (recorded, not defects in this slice)

- `iat`/`nbf` have no lower bound, matching the wave-52-audited backoffice verifier: a token asserting issue/not-before deep in the past verifies. Recorded as consistency, not an auth hole.
- The verifier fetches JWKS on every verification (no cache/TTL); each call is bounded but a slow issuer stalls logins up to the 8-second deadline. Recorded as a deliberate freshness/latency trade.
- `handle()`'s mount contract is now enforced in-process (origin + path prefix); the node:http wrapper in tests/dev-stack forwards request targets verbatim, which is what the e2e absolute-form probe exercises.
- `HEAD`/`OPTIONS` on issuer endpoints answer `405` like any other wrong method; unregistered same-origin paths still answer `404` — uniform, no information beyond the OAuth vocabulary.
