# Customer-API Store Seam Audit — Wave 54 — Proposed

- Status: Proposed
- Scope: `packages/customer-api/src/store.mjs` + `src/postgres-store.mjs` + `migrations/0001_customer_api_store.sql` — the dev-only PostgreSQL persistence seam behind `CUSTOMER_API_STORE=postgres` merged in #275, plus its memory-backend counterpart, the shared consume contract, the config path that selects it and the server lifecycle that owns it. No production path exists; the seam persists only rate-limit buckets.
- Production effect: none

Hunt list applied: consume atomicity under concurrency (read-modify-write seeing pre-increment state on either backend), SQL safety (string interpolation vs parameterization of key/namespace/window), cross-namespace read/write leakage, caller-supplied-clock asymmetries (bucket starvation, resets, boundary windows), silent degradation to memory or a half-open store, pool lifecycle (leaks, unbounded clients, dead connections mid-request, `initialize`/`close` idempotency and races), migration catalog integrity vs the custody-core conventions (append-only guards, replay, drift detection), and byte-for-byte parity claims of the memory backend (error shapes, edge windows, `maxKeys` eviction).

## Method

Each suspect was reproduced as a live probe against a dev PostgreSQL instance and a memory instance, then encoded as a contract test: the shared `tests/store-contract.mjs` suite runs identical cases against both backends, and `tests/postgres-store-contract.mjs` pins backend-specific behavior (pool lifecycle, drift rejection, concurrency bounds). `tests/postgres-store.sh` now asserts the catalog's `ENABLE ALWAYS` guards on live statements the way custody-core's migration-history arm does. Every defect below failed on the pre-audit tree; the regression lines say how.

## Defects found and fixed

1. **An idle pooled client's death crashed the whole process (high).** `pg.Pool` forwards an idle client's error (server restart, `pg_terminate_backend`, network drop) as an `'error'` event; with no listener that is an unhandled `EventEmitter` error and Node throws it, killing the API regardless of the request-level try/catch — verified live: the process died on `57P01`. The pool now installs an `'error'` listener (the pool drops the dead client); per-request failures still surface as `StoreUnavailableError` through `pool.query`, and `query_timeout` bounds a consume stuck on a wedged connection. Regression: `the store survives an idle pooled client being killed` — on the pre-audit code the test process itself crashes before any assertion.

2. **`initialize()` verified the catalog version but not the consume surface (medium).** A `schema_migrations` row at version 1 said nothing about `rate_limit_buckets` actually being intact: renaming the table away or dropping its `(namespace, bucket_key)` primary key left `initialize()` resolving while every consume then failed at request time — and the dropped arbiter also silently voided the `ON CONFLICT` upsert semantics. Startup now runs the real consume statement inside a rolled-back transaction, so the entire SQL surface — table, every column, the conflict arbiter — must resolve before the server listens; a failed probe drains the pool so nothing half-open survives. Regressions: `initialize rejects when the bucket table drifted away`, `initialize rejects when the bucket primary key is dropped`, `initialize rejects a drifted migration history row` — pre-audit, each `initialize()` resolved.

3. **Racing `initialize()` calls leaked a pool (medium).** Two concurrent calls each built a `Pool`; only the second stayed referenced, so the first's clients were never ended — measured live: three connections after racing init, two still open after `close()`, and the process could not even exit on the orphaned sockets. `initialize()` is now single-flight (`opening ??=`), and a `close()` that races the open drains the freshly built pool. Regression: `concurrent initialize calls share one pool and close releases every client` — pre-audit, `pg_stat_activity` kept two backends alive after `close()`.

4. **Malformed consume commands diverged between backends and lied about the failure (medium).** The pg backend passed command fields straight into `bigint`/`text` parameters: fractional or negative `now`, fractional `windowMs`/`maxKeys`, oversized `key` each surfaced as `StoreUnavailableError` — a backend-fault label for a caller contract violation. The memory backend silently answered the same commands (`now: -100000` → `{allowed: false, retryAfterSeconds: 162}`; `windowMs: 1.5` → `retryAfterSeconds: 61`; a NUL byte in the key → allowed on both). `assertRateLimitConsumeCommand` now runs first on every backend: well-formed non-empty keys of at most 256 characters without NUL, and every numeric field a non-negative safe integer with `now + windowMs` in range — violations throw `StoreCommandError` identically on both. Regression: the shared contract case `malformed consume commands fail identically` (15-member matrix) — pre-audit, memory resolved every entry and pg threw the wrong error class.

5. **The memory backend ignored its own lifecycle (low).** `createMemoryStore()` answered consumes before `initialize()` and after `close()`, while the pg backend refused both — identical commands produced different answers depending on backend state. The memory backend now tracks readiness and throws `StoreUnavailableError` in the same situations, and `close()` returns it to the uninitialized state so a later `initialize()` re-opens it exactly like a fresh pg pool. Regressions: contract cases `a consume before initialize fails closed`, `a closed store refuses consumes`, `re-initializing after close restores consumes` — the first two pre-audit returned `{allowed: true}`.

6. **The `expired`-row delete ran eagerly, diverging from memory's lazy prune under regressive clocks (low).** The consume's `DELETE` removed every expired row on each statement; the memory map only evicts when a *new* key arrives at a full map. Under a backwards-moving caller clock a row pg had already deleted lost its accumulated count where memory would still hold it — a stored state the two backends disagreed about. The delete is now conditional on exactly the memory trigger (`NOT EXISTS(prior)` and total rows ≥ `maxKeys`), which is also strictly less write churn. No regression test is possible without a controllable server clock; the parity is pinned by keeping both backends' bound checks against live rows only (contract case `expired buckets do not count toward the key bound`).

7. **The catalog had no out-of-band guard verification like custody-core's (low).** `migrations/0001_customer_api_store.sql` ships `ENABLE ALWAYS` append-only and sequence triggers, but nothing exercised them: a superuser could `DISABLE TRIGGER` and rewrite history undetected. `tests/postgres-store.sh` now asserts live rejections of out-of-order, wrong-name, stale-`applied_at`, `UPDATE`, `DELETE`, `TRUNCATE` and `session_replication_role=replica` mutations, asserts replaying `0001` fails loudly and leaves the one-row catalog intact — a scaled-down custody `postgres-migration-history.sh` equivalent.

## Classes proven clean

- **Consume atomicity.** Twelve parallel consumes of one key under limit 3 resolved to exactly 3 allows and 9 denies — the `ON CONFLICT` upsert re-reads the row post-conflict so the write serializes on the bucket row like the memory map's single thread. Pinned by `concurrent consumes of one key serialize on the bucket row`.
- **SQL safety.** Every consume input flows through `$1`–`$5` parameters; namespace and DSN are validated at construction (`^[a-z0-9_-]{1,64}$`, postgres(s):// only). No interpolation of caller data exists anywhere in the statement.
- **Namespace isolation.** Rows, counts and the `maxKeys` bound are scoped by the composite primary key; a second namespace cannot see the first's buckets, fill level or key — pinned by `namespaces isolate buckets and the key bound from each other`.
- **Clock semantics.** `now` is the caller's injected clock end-to-end on both backends; nothing reads the database's wall clock for consume decisions (`updated_at` is observability only). Boundary consumes at the exact `resetAt` reset identically on both (contract retry/expiry cases).
- **Fail-closed config.** `CUSTOMER_API_STORE` unset → memory; `postgres` requires a postgres(s):// DSN; a DSN without postgres mode, unknown modes, `NODE_ENV=production` and non-loopback hosts all throw at startup — verified by `tests/store-config.test.mjs`; no path silently falls back to memory.
- **Server lifecycle.** `startCustomerApi` initializes the owned store before listening (fail-fast), closes it on server close, and never closes an injected store.
- **Error hygiene.** Backend failures surface only as `StoreUnavailableError`/`StoreCommandError` — the DSN never appears in any error.

## Observations

- **Distinct-key races can overshoot `maxKeys` by the pool size.** `occupancy` is a statement-start snapshot: up to `max` in-flight consumes can each see a pre-bound table and all insert, so a 24-way burst over a 4-client pool committed 5–9 rows at bound 5. The bound stays *bounded* (never unbounded) and every deny remains correct — pinned by `consumes for distinct keys stay bounded under concurrency` — but exactness would need per-namespace serialization (advisory lock or serializable retry), which is out of scope for this dev seam.
- **`assert.rejects` cannot catch the memory backend's synchronous throw** — the contract wraps consumes in `async () =>` so both backends present as rejections.

## Tests added

`tests/store-contract.mjs` — 4 new shared cases (lifecycle fail-closed ×2, re-open, 15-member malformed matrix) now running against both backends via the new `makeRawStore` hook. `tests/postgres-store-contract.mjs` — 7 new pg-only cases (kill survival, pool-leak guard, three drift rejections, same-key serialization, bounded overshoot, namespace isolation). `tests/postgres-store.sh` — the live catalog-guard and replay assertions. `tests/store.test.mjs` — the delegate case initializes its backend.

- `npm run typecheck` — clean (checkJs strict); `npm run lint` / `npm run check` — boundary and manifest checks pass; `npm run verify:migrations` — catalog and policy verifiers pass.
- Pre-audit reproduction: the kill probe crashes the old build; the drift, pool-leak and malformed-command probes each demonstrate the old behavior documented above; the new contract file fails on the pre-audit tree (it imports `StoreCommandError`, which the old seam does not export).
