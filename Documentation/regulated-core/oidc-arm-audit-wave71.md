# OIDC E2E Arm Adversarial Audit — Wave 71 — Proposed

- Status: Proposed
- Scope: `packages/e2e-dev/tests/oidc.test.mjs` — the arm that drives the login → callback → session flow through the simulated issuer (`packages/provider-simulators/src/oidc.mjs`) for both the miniapp and the backoffice BFFs — plus the OIDC helpers in `packages/e2e-dev/tests/stack.mjs`. Wave 70 (#332) hardened `verifyEnvelope` and the two chain arms against mutation-blindness; this slice applies the same mutation-test framing to the OIDC arm. Everything is dev-only and synthetic — no production paths, no live data.
- Production effect: none

Hunt list applied: for each contract axis — signature/JWKS verification strength, claim binding (`at_hash`, `aud`/`iss`/`exp`/`iat`/`nbf`/`azp`/`nonce`), flow binding (`state` echo, single-use `code`, PKCE verifier, tx-cookie consumption), session minting (`customerApiSubject(sub)` derivation, `previousSessionToken` rotation, the #321 device gate), failure-matrix exactness (generic `?error=auth_failed`, no inner reason, no session minted, ordering guarantees), bounds (`OIDC_MAX_PENDING_CODES` eviction, `idTokenClaims` 4096 cap), lifecycle hermetics — the question was "if the product did this wrong, would the arm go red?". Every defect below was proven green-arm on the mutated product or simulator before the fix landed; the mutations were introduced only as proofs and reverted — no product change ships in this slice.

## Defects found and fixed

1. **No test ever verified a minted id_token against the live JWKS.** The arm exercised signatures only through the hostile-issuer matrix, so a verifier accepting any well-formed JWT (or `verify()` dropped outright) stayed green on the happy path — proven for both BFFs. The arm now mints a real token at the issuer, extracts the advertised key set over HTTP, reconstructs the public key with `createPublicKey` and runs `verify()` itself, pinning `iss`, `aud`, `sub` (`SUBJECT_PATTERN` fallback), `nonce` echo, `exp - iat = 300` and the `at_hash` claim against the exact access_token the exchange returned.
2. **`kid` selection was covered in only one wrong-selection direction — and the naive mutation still failed closed.** Rewriting the verifier's key filter to ignore `kid` (`candidate => true`) stayed green because the `matchingKeys.length > 1` ambiguity guard rejected the multi-match anyway — a compensating control the arm never probed. Both files now pin both directions: a token signed under the second advertised key must verify (positive control), and a token advertising `kid=A` while signed under `kid=B` (and the mirror) must fail — `jwk = jwks.keys[0]` selection goes red on both apps.
3. **The callback chain ordering was unpinned — the exchange could happen before the guards that must precede it.** The failure matrix asserted final redirects but not that a denied path never touched the issuer: dropping the `?error=` early-exit, reordering the device gate after the exchange, or running the exchange before the `error` check all stayed green — proven via a `hits.token` counter on the evil issuer's `/token` endpoint. Both files now assert `hits.token === 0` on every guarded path (error-param-wins, device-gate-first, state mismatch, tx-cookie absence), so a reordering BFF that mints before it checks goes red.
4. **Claim checks on the verify path were unexercised.** `exp`, `iat`-future (`iat > now + 60`), `nbf`, `azp`-multi-audience, `sub` shape (`SUBJECT_PATTERN`) and `token_type`/`access_token` response binding had no matrix coverage — each single-point removal stayed green, proven on both dists. The hostile matrix now covers ~17 claim/response mutations per app, each asserting the exact failure: `302` to `${origin}/?error=auth_failed`, no session cookie, no pending-entry leak.
5. **Hostile JWKS documents were never fed to the keyset loader.** A JWKS that advertises a duplicate `kid`, `use: "enc"`, `alg: "HS256"`, a private member (`"d"`), wrong `key_ops`, an RSA-1024 modulus or `e: 1` had no coverage — an accept-anything loader stayed green. New "hostile JWKS documents fail closed" tests feed each document to the BFF through `driveEvilFlow`/`driveBoEvilFlow` and pin `auth_failed` with no exchange (`hits.token === 0`).
6. **Flow-binding pins were absent on both apps.** The tx-cookie nonce binding, duplicate/empty `code`+`state` parameters, a tampered callback `state`, the per-initiator pending cap (2 — chained logins evict the oldest), the global 256 bound and the 600 s pending TTL each stayed green when broken — proven per mutation. Both files now carry a "flow binding and session contract" describe pinning every one.
7. **Session-minting contract was under-specified.** The minted session's derived subject (`SC-DEV-<suffix>` for miniapp, `syn_oper_` + `customerApiSubject` for backoffice), rotation on login (presented session token killed — and for the backoffice, the `loginStartSessionToken` AND the callback-presented token revoked independently), preserve-on-failed-callback, hardened-cookie flags (HttpOnly/Secure/SameSite/Path/Max-Age, tx cleared on success) and the #321 device-binding ordering (401 without the device cookie, 401 with a foreign-uuid device, 200 + bound `syn_oper_` subject with the approved digest) were each proven green when broken — now pinned per app, with the two bo revocations verified as independent mutations.
8. **The simulator's own contract was uncovered end-to-end.** `packages/provider-simulators/src/oidc.mjs` is the oracle the whole arm trusts; its `/token` bindings (wrong verifier → `invalid_grant`, wrong `redirect_uri`/`client_id`, duplicate `code` parameter → `invalid_request`, non-form `Content-Type`, oversized body, `unsupported_grant_type`), `/authorize` guards (foreign client → `unauthorized_client` JSON, unregistered `redirect_uri` → 400 JSON, `response_type`/`scope`/method rejects redirecting with the error + `state` echo, short challenge / over-length nonce, duplicate parameter → 400, 128-char `state` boundary, over-length `state` NOT reflected), `OIDC_MAX_PENDING_CODES` oldest-first eviction (mint 257 — entry 0 evicted and non-redeemable while entries 1 and last redeem), the discovery document's field set and the `idTokenClaims` bounds (reserved claim, 4096 accepted / 4097 rejected boundary, non-JSON, deep-nesting, top-level array) all stayed green when mutated — now pinned in a dedicated "oidc issuer contract" describe driving `issuer.handle` directly.
9. **The exchange-side code-expiry check was unreachable through the BFF flow** (`pending.expiresAt <= clock.now()` in `oidc.mjs`). Breaking it stayed green because the full-flow test's clock advance (+121 s on the issuer) puts the minted token's `iat` past the verifier's `iat > now + 60` guard — the callback fails on stale claims before code expiry is ever consulted. New tests assert `invalid_grant` at `/token` directly on both issuers — verified red.
10. **The backoffice stale-pending test overclaimed** (found while fixing #9). `ExpiringStore` captures `Date.now` by reference at construction, so patching `Date.now` after server start never expired the pending entry — the test was green for the wrong reason (token-claim staleness again). The reworked test constructs a BFF while a controllable fake clock is installed, then steps it past 600 s — with `boNow` advanced in step so the minted token stays valid and pending expiry is the only failing guard. Store-expiry-off mints a session → verified red.

## Verified clean

- **`state` echo exactness.** A callback `state` the pending map doesn't hold answers `auth_failed` before any exchange (`hits.token === 0`); the reflected `state` round-trips byte-exact on the success redirect; over-length `state` is refused rather than reflected; duplicate `state` parameters answer 400, never a first-match.
- **Missing tx cookie.** A callback without `solidchange_ma_oidc_tx` / `solidchange_bo_oidc_transaction` answers `auth_failed` with no exchange and no session — pinned per app.
- **Replayed code.** The same `code`+`tx` callback a second time after a successful mint answers `auth_failed` (pending entry consumed) and the issuer itself returns `invalid_grant` on a fresh `/token` for it — single-use at both layers.
- **Unconfigured BFF.** Without OIDC config the auth routes 404 outright — a BFF that half-registers routes on missing config goes red.
- **Role mapping ambiguity.** Two groups mapping to different roles fails the flow closed rather than picking first-match; unmapped subjects mint no operator session.
- **Failure-matrix exactness.** Every denied path asserts the exact contract: `302` (never `500`), `location` byte-equal to `${origin}/?error=auth_failed` (no inner-reason parameter leaks), zero session cookies, `hits.token === 0` where no exchange is contracted.
- **Device gate ordering (#321 pin).** The gate evaluates before the exchange — proven by `hits.token === 0` on the denied paths — and the approved-digest path stays device-bound across the follow-up reads.
- **Lifecycle hermetics.** No subprocesses in this arm (issuer and BFFs run in-process through `node:http`), no `EADDRINUSE` surface (all `listen(0)`), no wall-clock sleeps — clock-sensitive paths advance injected `now`/`boNow` or a `Date.now` fake, restored in `finally` so a mid-test failure can't poison a later file.

## Observations (recorded, not defects in this slice)

- `ExpiringStore` binds `Date.now` at construction: the backoffice pending store takes no injected clock, so staleness is only exercisable by installing a fake before construction (done in the fixed test) or waiting out the real 600 s. The miniapp store is clock-injected and the same class underlies both — the miniapp arm covers the shared code path cheaply.
- `sweepExpiredCodes` on the authorize path is belt-and-braces: disabling it stays green because the exchange-side expiry check and the 256-cap eviction cover every observable outcome (a swept-away code behaves identically to an evicted/expired one). Recorded, not a defect — the exchange-side check is the enforced boundary and is now pinned.
- The `iat > now + 60` guard and code expiry share the issuer clock: any clock-advance test larger than 60 s through the BFF lets `iat` mask `exp`/code-expiry defects. Issuer-contract assertions therefore drive `issuer.handle` directly rather than the full flow — the same lesson the wave-70 envelope oracle applied.
- `matchingKeys.length > 1` ambiguity is a compensating control: mutations that merely widen the `kid` filter fail closed on their own. Kid tests must target the wrong-selection semantic (first-key pick), not the filter predicate — the pattern is documented for future audits.
- `OIDC_MAX_PENDING_CODES` eviction is oldest-first by Map insertion order; the 257-mint test pins the boundary exactly (entry 0 evicted, entries 1 and 256 redeem).
