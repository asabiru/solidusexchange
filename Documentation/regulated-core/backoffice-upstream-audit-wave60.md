# Backoffice Upstream Adapter Audit — Wave 60 — Proposed

- Status: Proposed
- Scope: `backoffice/src/server/customer-api-client.ts` (the signature-envelope upstream client and every operator read — `operatorAdmin`, `operatorSubjects`, `operatorSubject`, `operatorQueue`), the browser-side verification layer in `backoffice/src/data/client.ts` (`getSigned`/`postSigned`/`getAuditExport`/signing-keyset fetch, `assertEnvelopeShape`, `verifyEnvelope`), the strict camelCase adapters in `backoffice/src/data/operator.ts`, and the `operator-subject`/`operator-queue` signing call sites in `backoffice/src/server/server.ts`. Everything is dev-only and synthetic — no production paths, no live upstream, no real operator data.
- Production effect: none

Hunt list applied: hostile upstream envelopes (wrong audience/kid, expired and not-yet-valid `issuedAt`, oversized and non-JSON bodies, error envelopes carrying upstream field names, success envelopes with prototype keys/huge arrays/deep nesting/control characters), status-code mapping determinism (every non-2xx → a closed status union member; 200-with-error-body and error-with-200-shape both fail closed), signature verification (key/version/algorithm coherence, active-key consistency, freshness window, retired-key issuance cutoff, tampered `payload` vs `signature`), device-id propagation (`X-Device-Id` only when a real UUIDv4 exists, never synthesized, never on non-operator routes), response bounds (bodies capped before JSON decode), abort/timeout wiring (a hung upstream cannot hang the route), per-kind parsers (aml/tickets/kyc item-shape discrimination; a kind echo that lies about its contents), degrade consistency (unconfigured vs configured-unavailable vs configured-denied — each serving the documented error object, never a partial view).

## Defects found and fixed

1. **Operator subject detail was not bound to the requested member (`server/customer-api-client.ts`, `data/operator.ts`).** `parseOperatorSubjectDetailView` admitted any well-formed `syn_cust_*` record, so an upstream answering `/api/v1/operator/subjects/{id}` with *another* subject's detail passed straight through to the rendered view — proven on main, where the parser admitted a record whose `subject_id` differed from the requested id. The same gap existed in the browser-side adapter `parseOperatorSubjectView` (`data/operator.ts`), which had no expected-subject parameter at all. Both parsers now take the requested ref and reject a view carrying any other `subject_id` — the same convention `parseOperatorAdminView` already used for the operator subject echo. `App.tsx` passes `selected.subjectId` through, and `server.ts` calls the bound parser with the route id.
2. **The capability echo was not vocabulary-checked (`server/customer-api-client.ts`).** `validGrantedCapabilities` bounded item count, uniqueness and length but not membership, so a view could claim any capability id — upstream rejects anything outside `OPERATOR_CAPABILITY_POLICY`. The parser now pins every entry to the five-name operator vocabulary (`operator.session.read`, `operator.capabilities.read`, `operator.admin.read`, `operator.subjects.read`, `operator.queue.read`), mirroring the upstream validator.
3. **Browser-side fetches consumed `response.json()` unbounded (`data/client.ts`).** `getSigned`, `postSigned`, `getAuditExport` and the signing-keyset fetch materialized arbitrary bodies as JSON — proven on main, where a 17 MB envelope body parsed and resolved. A shared `readBoundedJson` now enforces a 262,144-byte cap on the declared length *and* the streamed body (cancelling the reader on overflow), mirroring the server client's `readBoundedJson`/`maxCustomerApiResponseBytes` pattern; the same bound now covers `getHealth` and `getAuthStatus`.
4. **The canonical-JSON check had no depth bound (`data/client.ts`).** `assertCanonicalJson` validated number canonicality only, so a payload nested hundreds of levels deep kept a valid signature while exhausting serialization — proven on main with a 20-level payload. The check now pins depth ≤ 16, mirroring the signer's `MAX_PAYLOAD_DEPTH`.
5. **The signing keyset admitted an unbounded keys array (`data/client.ts`).** `isValidKeyset` checked structure, active-key coherence and `keyId` uniqueness but not `keys.length` — a hostile keyset grew the verifier's memory and lookup cost without bound — proven on main with a 66-key keyset. The keyset now caps `keys` at 8 (the signer never advertises more than 1 active + `maximumRetiredKeys` = 3).
6. **`operator-subject`/`operator-queue` resources were not bound to the request (`data/client.ts`, `server.ts`).** `getSigned` expected the flat resource names `operator-subject`/`operator-queue`, so an envelope minted for *another* subject or kind under a valid signature satisfied this read — proven on main, where an attestation for `operator-subject:{otherId}` would have verified had the convention stayed unbound; sibling reads (`check:${id}`, `withdrawal:${id}`, `support:${id}`, `subject-timeline:${ref}`, `report:${id}`) already bind their member ref. The client now expects `operator-subject:${subjectId}` and `operator-queue:${kind}`, the server emits the same bound resources at all four call sites (configured and unconfigured arms), and the absent `kind` resolves to `kyc` on both sides, matching the route's documented default.
7. **Error `detail` fields passed JSON through untyped (`data/client.ts`).** `postSigned` and `createDevSession` read `detail.error`/`detail.state`/`detail.attemptsRemaining`/`detail.deviceDigest` straight from `response.json()` — an upstream-shaped error body could inject objects and wrong types into `ApiError` fields and the device-binding message — proven on main, where `{error:{nested:true}, state:42, attemptsRemaining:"three"}` surfaced verbatim. `parseErrorDetail` now requires every present field correctly typed (non-negative integer `attemptsRemaining`); a single hostile field discards the whole detail rather than leaking.
8. **`getOperatorQueue` interpolated `?kind` unencoded (`data/client.ts`).** `?kind=${kind}` passed the raw value into the query string — a kind containing `&`/`=`/`#` injected extra query parameters into the upstream request path — proven on main with `aml&debug=1`, which produced `?kind=aml&debug=1`. The kind is now `encodeURIComponent`'d on the wire while the resource binding keeps the raw ref.
9. **Browser `parseOperatorSubjectView` lacked the member binding (covered with defect 1).** Counted separately in the repro suite because the fix is a second, independent adapter: the server parser and the browser adapter both bind `subject_id`/`subjectId` to the requested ref, so neither layer can pass a cross-member view through.

## Verified clean (with negative pins)

- **Status-code mapping is deterministic.** Every non-2xx upstream status (401/403/404/429/5xx/malformed) maps to `"unavailable"`; a member-read 404 maps to `"not-found"`; a 200 carrying an error-shaped body fails the view parse → `"unavailable"` — never `"ok"` with an error payload.
- **Non-JSON bodies and content types reject before decode** (server client), and streamed bodies without `content-length` are bounded at `maxCustomerApiResponseBytes` by the streaming reader — no reliance on the declared size.
- **Prototype-pollution keys fail closed** on both layers: `__proto__`/`constructor` members inside subject, device and queue structures trip the exact-key-set checks (server and camelCase adapters alike).
- **Timeout wiring fires.** `AbortSignal.timeout(timeoutMs)` aborts a hung upstream inside the default 2 s window → `"unavailable"` — the BFF route does not hang.
- **Non-contract subject ids never reach the wire**: a malformed or non-`syn_cust_*` id is answered locally with the uniform not-found and zero upstream requests (served-request list asserted empty).
- **Degrade arms stay distinct**: unconfigured → `not-configured`/`{error}` demo fallback, configured-unreachable → `unavailable`, upstream member 404 → `not-found` — each serves its documented object, never a partial view.
- **Envelope freshness is enforced both directions**: `issuedAt` more than ±5 min from now rejects (`RESPONSE_MAX_SKEW_MS`), covering expired and not-yet-valid envelopes.
- **Signature coherence**: tampering `payload` under a valid signature fails verify; wrong `keyId`/version/algorithm/active-key mismatches reject; retired keys cannot attest envelopes issued after `retiredAt`.
- **Per-kind discrimination**: aml/kyc/tickets item key-sets are disjoint, `queue.kind` must equal the requested kind, and the summary must tally the item set exactly — a view declaring `kind:"aml"` while carrying kyc or ticket items rejects.
- **Device-id propagation**: `X-Device-Id` is forwarded only when the session presents a real UUIDv4 id; malformed ids never reach the wire and no device header is synthesized upstream; the header is emitted only on operator routes.

## Observations (recorded, not defects in this slice)

- The unconfigured degrade arms intentionally emit null upstream-only fields (`subjectId`, `contactHash`, `sessions`, `limits`, …); the strict adapters reject them so the demo fallback renders — consistent by design, pinned by the existing degrade tests.
- `operator-subjects` (the list read) stays an unbound resource by design: a collection has no member ref to bind — unlike `operator-subject:${id}`/`operator-queue:${kind}`.
- `assertCanonicalJson` is intentionally lighter than the signer's `isCanonicalJsonValue`: `JSON.parse` output is already plain-prototype, dense and symbol-free, so only the depth bound (now added) was a wire-reachable gap.
- `server/customer-api-client.ts` interpolates `?kind=${kind}` into its upstream URL too, but `kind` is enum-gated to `aml|kyc|tickets` before the call — no injection surface; left as-is.
- `postSigned`'s non-2xx `detail` parse tolerates a non-JSON body (falls back to `{}`), matching the previous behavior — error bodies are best-effort metadata, never trusted.
