# Operator Subject-360 Composed View Audit — Wave 64 — Proposed

- Status: Proposed
- Scope: `packages/customer-api/src/operator.mjs` (the composed `GET /api/v1/operator/subjects/{id}` view — the #294 base detail, the #306 recent_activity page and the #312 kyc dossier as one response) plus the two adapter chains it feeds (`backoffice/src/server/customer-api-client.ts` fail-closed snake_case parsers, `backoffice/src/data/operator.ts` camelCase view parsers) and the BFF render path in `backoffice/src/server/server.ts`. Everything is dev-only and synthetic — no production paths, no live data.
- Production effect: none

Hunt list applied: cross-block coherence (recent_activity instants vs the dossier history vs queue items vs sessions/devices — can two blocks disagree about the same instant or state); subset-semantics validator gaps (the ≤8 activity page and the ≤4 dossier history — can a view pass the subset check while dropping an item that must be on the page, tie-break determinism on boundary instants); universe derivation (subjectsDigest/subjectsUnits jitter — derived-id collisions across subjects, bound violations, impossible instants such as submission after decision or activity before registration); the backoffice adapters (partial-drift poisoning — one bad field in the kyc block silently nulling just that block while serving stale siblings, the `kyc:null` fallback vs an absent upstream key, a degrade-tolerant catch masking real drift); and serve-time cost (per-request derivation boundedness, the #281 no-cache invariant, response-size bounds).

## Defects found and fixed

1. **Feed items could precede the account entirely (`deriveSubjectRecentActivity`, `operator.mjs`).** The customer feed recipe pins its `created_at` to the shared epoch (`BASE_MS + index * 6h + jitter`), and the recent_activity projection copied the instant verbatim — so for a late-registered subject every re-mapped feed item predated `registered_at` (probe: up to 7 items before registration on the served universe). A composed view showed the subject acting before its account existed. Feed instants are now re-anchored onto the subject's own registration (`occurred_at = registered_at + (created_at - BASE_MS)`), keeping the relative spacing inside the account window; the upstream validator and both adapters reject any item that precedes registration.
2. **`last_active_at` could sit before the subject's own instants (`buildSubjectRow`, `operator.mjs`).** The row computed `last_active = registered + jitter` with no regard for the instants other blocks derived from the same roster — the probe found up to 8 recent_activity items and dossier submissions postdating `last_active_at` on one subject. `last_active` now covers the newest subject-side instant (the re-anchored feed maximum and the shared submission instant when an application exists), taking the maximum with the original jitter draw; every attempt submission and every subject-side activity item is bounded by it.
3. **Live sessions floated on no device and on closed accounts (`deriveSubjectDetailFields`, `operator.mjs`).** `sessions`, the device count and `account_status` were three independent draws: the served universe carried subjects with `sessions > 0` and `devices = []` (six subjects) and closed accounts with live sessions. Sessions are now clamped to zero when the device draw is zero or the account is closed; the upstream validator and both adapters pin the same rule.
4. **The adapter layer missed the cross-block roster checks entirely (`customer-api-client.ts`, `operator.ts`).** Both adapters validated each block's shape but never the composed view's claims: a fabricated `kyc_transition` on an unverified subject, a decision transition on a pending one, more `flag_added` rows than the roster's open flags, a transition instant diverging from the dossier's newest submission, and instants outside the account window all parsed cleanly. Both adapters now reject on the same subset discipline the upstream validator applies — transition vocabulary per roster `kyc_status`, `flag_added` count ≤ `flags`, transition↔dossier instant equality when the submission survives the page bound, dossier submissions inside the account window, and the sessions/devices/account coherence rule.
5. **The front-end adapter poisoned partial drift into a fake no-dossier state (`operator.ts`).** `parseSubjectKyc(item.kyc) ?? null` degraded a malformed dossier block to `kyc: null` while the sibling blocks still served — one bad field silently rewrote the view's meaning (a rejected application rendering as "no application"), and a test even pinned the behavior. A malformed block is now drift like every other axis: the whole detail view fails closed, matching the BFF adapter and the upstream validator. The `kyc: null` fallback itself stays correct — null is the contract's no-dossier marker; an absent upstream `kyc` key still breaks the pinned shape.

## Verified clean (with negative pins)

- **Cross-block instants agree where they must**: the kyc queue item's `submitted_at`, the dossier's newest `submitted_at` and the `submitted` transition's `occurred_at` derive from one shared salt, and the decision transition equals the newest attempt's decision instant — verified equal across all 24 subjects, and now pinned as adapter- and validator-level rules whenever the transition survives the page bound.
- **The subset windows cannot silently drop a must-be item**: the upstream validator re-derives the whole view verbatim (row, derived fields, recent_activity, dossier) so a shortened page fails byte-for-byte; the sort is a total order (`occurred_at` desc, `activity_id` asc) so the boundary item at position 8 and same-instant ties are deterministic. The new adapters mirror the presence-as-subset discipline (no invented events) rather than re-deriving.
- **No derived-id collisions**: across all 24 subjects and three queues — `kys_*` sessions, `opact_*`/`act_*` activity ids, `qml_*`/`qtk_*`/`qky_*` queue ids, `evd_*` evidence refs, `dev_*` devices, `cth_*` contact hashes — 0 collisions in 447+ ids (each digest mixes the subject id into its salt).
- **Impossible instants stay impossible**: each attempt's decision instant sits at or after its `submitted_at` (the decision draw adds a 1d base + jitter to the submission); the queue `sla_due_at` sits after `submitted_at` by the SLA window; the decision field stays null inside the review window; queue items for unverified no-application subjects carry no dossier contradictions.
- **No unbounded work**: `subjectFor` runs a fixed 24-row scan plus constant-bound derivations (feed ≤ 9 items, transitions ≤ 2, flags ≤ 7, history ≤ 3, devices ≤ 6); no per-subject cache was reintroduced — every read recomputes from the digest recipe (#281 invariant). The served payload stays ~8 KB, inside the BFF's 16 KB bound.
- **Queue↔detail state divergence is semantic, not drift**: the queue's `pending`/`in_review`/`escalated` state and the aml `alert_type` derive from independent salts on purpose — the work item's triage state is the operator-side claim, not the dossier status, so an `in_review` queue item beside a `submitted` dossier records operator work-in-progress, not a contradiction. Recorded as intentional divergence.
- **The BFF route stays deny-by-default**: unconfigured upstream renders all derived blocks null (nothing invented); upstream 404 maps to the uniform `operator_subject_not_found`; contract drift fails closed to 503 — exercised end-to-end in `operator-subject-upstream.test.ts`.

## Observations (recorded, not defects in this slice)

- **`last_active` is now the max of the jitter draw and the newest subject-side instant** — for most subjects it equals a feed or submission instant rather than the raw jitter, which is the correct composed meaning (the subject's own records define when it last acted).
- **Feed items cluster in the account's first ~54 hours** because the feed recipe spaces items 6h apart from its epoch; re-anchoring preserves that shape, so "recent activity" for a dormant account still shows old feed rows below the newer operator events — consistent, deterministic, and honest about age.
- **The operator-side/subject-side instant split is the one semantic rule the adapters must share**: `act_*` feed items and the `submitted` transition belong to the subject (bounded by `last_active_at`); `flag_added` and the decision transition belong to the operator (unbounded except by the roster's pinned as-of instant). The rule is now documented at all three layers.
- **Serve-time cost grew slightly**: `buildSubjectRow` now derives the feed's newest instant per roster row (24 rows × ≤ 9 digest draws) to bound `last_active_at` — still a fixed constant per request, no stored state.
