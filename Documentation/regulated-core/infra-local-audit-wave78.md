# Local Dev Stack Audit — Wave 78 — Proposed

- Status: Proposed
- Scope: `infra/local/` — the Docker development stack (~1400 lines): `compose.yaml`, the five Dockerfiles (`customer-api`, `miniapp`, `backoffice`, `tools`, `postgres`), `postgres/pg_hba.conf`, `postgres/10-backoffice-runtime.sh`, `scripts/{dev-material,x509,loopback-edge,healthcheck}.mjs`, `scripts/with-dev-material.sh`, `.env.example`, the four `*.dockerignore` files, `tests/`, `README.md`, and the static policy checker `.github/scripts/check-dev-stack.mjs` that is supposed to keep all of it dev-only.
- Production effect: none

Hunt list applied: secrets/material handling, `.dockerignore` completeness vs. what `COPY` pulls, `pg_hba.conf` + runtime script fail-closed-ness, compose port bindings/credential env/service isolation/volume sources, Dockerfile hygiene, and whether the tests actually prove the safety claims. Method: every candidate defect was proven as a live mutation against the real tree before being counted — each case below names the mutation that stayed green on `origin/main`'s checker and now fails.

## Defects found and fixed

All defects were coverage gaps in `.github/scripts/check-dev-stack.mjs` — the audited artifacts themselves were already sane (see "Verified clean"); the checker just could not see the failure modes, so a future edit could silently break them.

1. **`pg_hba.conf` was scanned only for secrets, never parsed.** Four live mutations stayed green: `local all all trust`, `hostssl ... 0.0.0.0/0 scram-sha-256`, a non-TLS `host ... scram-sha-256` auth line, and an `@/etc/other.conf` include directive pulling auth config the checker cannot see. A new `checkPgHba` parses every non-comment line: `local` lines must be exactly `local DB USER peer`; `host` lines may only `reject`; `hostssl` lines must name a concrete database and role (no `all`/`replication`), a loopback address (`127.0.0.1/32` or `::1/128`), and `scram-sha-256` — options (`clientcert=verify-ca`) and every other entry type (`hostnossl`, `hostgssenc`, `include`/`@file` directives) reject outright.
2. **Service hardening was present but not required.** Live mutants removing `read_only: true`, `cap_drop: - ALL`, or `security_opt: - no-new-privileges:true` from a service stayed green — the stack happened to set them, nothing enforced them. Every service must now set all three (`security_opt` must list `no-new-privileges` entries only, so `seccomp=unconfined` fails).
3. **Privilege/namespace/egress keys went unchecked.** Live mutants `cap_add: [SYS_ADMIN]`, `devices: /dev/sda`, `pid: host`, `extra_hosts`, remote `logging`, `ipc`, `sysctls`, `userns_mode`, `volumes_from`, `secrets`, `configs`, `dns*`, `group_add`, `uts`, `cgroup_parent`, `device_cgroup_rules` all stayed green; each is now rejected as a key the dev stack fixes rather than exposes.
4. **`volumes:` list items were unvalidated.** Live mutants `/etc:/host-etc:ro` (host filesystem into the container), a repo bind without `:ro`, and `${HOME}/.ssh` (interpolated path) stayed green. Entries must now be literal (no `$`-expansion) `src:/abs/target[:mode]` triples; a named volume may carry any single mode, a `./`/`../` bind mount must resolve inside the repository and must be `:ro`. Absolute host paths, `~`, and anything outside the repo reject.
5. **`EDGE_ROUTES` and `ports` were independently unbounded.** A live mutant publishing `127.0.0.1:5432:8174` with `EDGE_ROUTES: "8174:5432"` stayed green — postgres reachable on host loopback through the edge, scram-protected but off-design. Two checks now bind them: every `EDGE_ROUTES listen:target` pair must match a published `127.0.0.1:target:listen`, every published port must match a route when routes exist, and route targets may not be datastore ports (postgres/redis/mysql/mongo/oracle/mssql/cassandra/cockroachdb). Malformed route entries (`8183`, `8183:4183:extra`) reject.
6. **`environment` flow-style and `build` children were unvouched.** A flow map `environment: {EDGE_ROUTES: "8183:5432"}` hid routes from the parser entirely — flow style now rejects (block mapping or list only, which is what `composeNodeEnvValue` can audit). `build.args`/`build.ssh`/any build child outside `context`/`dockerfile`/`dockerfile_inline` rejects — the checker only vouches for the two it inspects.
7. **`.env` variants could be committed.** A live `infra/local/.env.local` mutant stayed green — `trackedEnvErrors` only matched the exact basename `.env`. `.env.*` files (except `.env.example`) now take the same tracked-file rejection.
8. **`.dockerignore` existence and content were unenforced.** Two live mutants stayed green: deleting `miniapp.Dockerfile.dockerignore`, and a file whose first pattern was not `*`. Worse, a real-pattern simulation showed `packages/customer-api/src/.env` *was* included by the miniapp ignore — `src/**` re-includes while the deny list only covered top-level `miniapp/.env*`. Every dev-stack Dockerfile (including ones compose builds outside `infra/local`) now requires a sibling `.dockerignore` whose first pattern is `*`, plus a fixed deny set (`**/.env`, `**/.env.*`, `**/*.key`, `**/*.pem`, `**/*.p12`, `**/*.pfx`, `**/.git`, `**/.git/**`) positioned after every `!` re-include. The four real files gained that deny tail.
9. **Literal secrets in `.sh`, `.conf`, and `Dockerfile` slipped past `checkAssignment`.** Live mutants `POSTGRES_PASSWORD=letmein` in a shell script and `ENV API_TOKEN=abc123` in a Dockerfile stayed green — the committed-literal check only ran on `.env.example` and `compose*.yml`. It now runs on `ASSIGNMENT_FILE` (plus `ENV`/`ARG` lines in Dockerfiles), still allowing empty values, `$(...)` command substitution, `${VAR}`/`$VAR` lookups, `@file` material references, and `${VAR:-}` placeholders.
10. **`with-dev-material.sh` had no test coverage** despite being the loader every app service's material env flows through. A new suite (6 cases) exercises it end-to-end: `NAME=@file` export with multi-line values, arguments after `--` passing through unmodified, invalid variable names rejected with status 64, traversal/hidden/bare `@` file names rejected, the `NAME=@file` form and a command required, and fail-closed on a missing material file.
11. **`audit-db-runtime.password` was written `0444`.** The runtime password file is consumed only by `10-backoffice-runtime.sh` (postgres init) — world-readable was wider than needed. It is now `0400`, grouped with the superuser password and server private key; the token key, DB URL, CA, and server cert stay `0444` because app services read them from the shared volume.

## Verified clean

- **`dev-material.mjs` + `x509.mjs` are genuinely dev-only material.** Subjects/CNs say `(synthetic)`; the server cert pins SANs `IP:127.0.0.1` + `DNS:localhost` with `serverAuth` EKU only; validity is 30 days; the token key regenerates every run, passwords keep existing files, and the CA is a fresh P-256 ECDSA self-issued root. `SOLIDCHANGE_DEV_MATERIAL_DIR` is honored by `main()` only — imported paths stay fixed. All writes are atomic (`writeAtomically` temp+rename) with tight modes.
- **`.env.example` carries no real-looking values.** All three secret fields are empty; comments say never to put real credentials; scenario values are dev defaults.
- **Dockerfiles are hygienic.** All five pin `node:24.19.0-bookworm-slim@sha256:…` by digest, multi-stage, `ENV NODE_ENV=development`, final `USER node`, `npm ci --omit=dev --ignore-scripts`, no `curl|sh`, no `ARG`/`ENV` secrets, no `HEALTHCHECK` instructions (compose drives `healthcheck.mjs` probes). Base-image pinnings were already enforced.
- **`pg_hba.conf` itself was already correct** (`local peer` + one `hostssl scram` + `reject` catch-alls on `0.0.0.0/0` and `::/0`); the defect was that nothing stopped it drifting — now pinned.
- **`10-backoffice-runtime.sh` fails closed.** `set -eu`, reads the runtime password from the material volume, `ON_ERROR_STOP=1`, least-privilege rights on `backoffice_control` (schema usage, audit `SELECT`+`INSERT`, `schema_migrations` `SELECT`, `operator_sessions` full DML).
- **`loopback-edge.mjs` fails closed.** Refuses to start without a default gateway; admits peers only on loopback/`::1`/the exact gateway IP; `parseRoutes` validates distinct ports 1–65535 and unique listeners; tests pin loopback forwarding and `EADDRINUSE`.
- **`healthcheck.mjs` requires exact `127.0.0.1` URLs** (so `127.0.0.1.evil.com` fails), `http:`/`tcp:` only, HTTP must return 200 and redirects fail — already covered by its tests.
- **`dev-material` service is the tightest container in the stack** — `network_mode: none`, `read_only`, `cap_drop: ALL`, `no-new-privileges`, `user: "70:70"`, and `command:` is set explicitly in the checked compose file, so a `.env` file cannot redirect it.
- **Port bindings are all `127.0.0.1`-published**; the audit DB gets no published port and is reachable only inside its netns via the edge's routes.
- All 22 live mutations that stayed green on `origin/main` now fail the checker (re-run after the change; the one `trust` "green" in the harness was a no-op mutation — `replace("peer", "trust")` hit a comment first — and `checkPgHba` was verified to flag `local all all trust` directly).

## Observations

- **`networks:`/`network_mode: service:EDGE` topology is policy-shaped, not parser-shaped.** The checker constrains `network_mode` values and the shared-netns pattern, but does not model which service *should* sit behind which edge — that stays a human design constraint, noted rather than checked.
- **Published ports without `EDGE_ROUTES` stay legal.** The pairing requirement only fires when a service declares routes; a future service could publish `127.0.0.1:H:C` without an edge. That is a deliberate allowance — a direct loopback publish is still host-loopback-only and may be right for a one-off service.
- **`command:`/`tmpfs:`/`healthcheck:` values are not schema-checked.** `command` is what makes `.env` tampering unable to redirect services (it is set inline), and `healthcheck` already runs only `healthcheck.mjs` in the tools image — observed, not enforced.
- **`security_opt` permits only `no-new-privileges` entries** — the list exists purely for that pin; adding `seccomp`/`apparmor` profiles would need a checker revision, which is the point (fail-closed on new surface).
- **Datastore-port ban is a denylist, not a topology proof.** It catches postgres/redis/mysql/etc. targets by port number; a future datastore on a non-standard port would pair cleanly. Combined with the volume/user/network pins it still removes the realistic leak path.

## Test additions and checker changes

- `.github/scripts/check-dev-stack.mjs`: new `checkPgHba` parser wired into `checkDevStack` for any `pg_hba.conf`; hardening trio required on every service; dangerous-key denylist; `volumes` item validation; `EDGE_ROUTES`↔`ports` bijection + datastore-target ban; flow-style `environment` rejection; `build` child-key allowlist; `.env.*` tracked-file collection; `checkDockerignore` (sibling file, leading `*`, required deny tail) for stack and external Dockerfiles; `checkAssignment` extended to `ASSIGNMENT_FILE` + Dockerfile `ENV`/`ARG` lines with `$(`/`${VAR}`/`$VAR` exemptions.

- `infra/local/tests/with-dev-material.test.mjs` (new, 6 cases): the loader's full contract end-to-end.
- `infra/local/tests/dev-material.test.mjs` (+1 assertion): runtime password now grouped with the `0400` files.
- `infra/local/scripts/dev-material.mjs`: `audit-db-runtime.password` mode `0444` → `0400`.
- The four `*.dockerignore` files: appended the fixed deny tail (`**/.env`, `**/.env.*`, `**/*.key`, `**/*.pem`, `**/*.p12`, `**/*.pfx`, `**/.git`, `**/.git/**`) after the `!` re-includes.
