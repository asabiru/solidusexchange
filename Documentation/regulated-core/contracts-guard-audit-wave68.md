# Contract Guard Machinery Audit — Wave 68 — Proposed

- Status: Proposed
- Scope: `packages/api-contracts/scripts/check-contracts.mjs` + `packages/api-contracts/openapi.yaml` ↔ `packages/customer-api/src/contract.mjs`/`src/app.mjs` dispatch ↔ `packages/customer-api/tests/contract-validator.mjs` + `contract-conformance`/`contract-coverage`/`routing`/`served-reads-meta-audit-wave67` tests. Everything is dev-only and synthetic — no production paths, no live data.
- Production effect: none

Hunt list applied: coverage symmetry across the three registries (openapi paths, `OPERATIONS`, dispatch arms, observed statuses) and TOCTOU between them; schema depth (pinned response bodies vs. presence-only checks); the error contract (envelope shape vs. per-status code binding); capability binding (route→capability mapping); parameter grammar (declared `{id}`/cursor/kind schemas vs. the dispatcher's own admission); and evasion (unversioned prefixes, unlisted operationIds, path normalization, namespace-tag abuse). Each drift class was first reproduced as a passing mutation, then pinned closed.

## Defects found and fixed

1. **Two canonical path-parameter bodies were never pinned (`check-contracts.mjs`).** Six of the eight canonical path parameters (`CheckId`, `ScreeningId`, `OperationId`, `OrderId`, `Instrument`, `SubjectId`) get exact `canonicalJson` schema pins; `QueueKind` and `QueueItemId` only appeared in `canonicalPathParameters`/`pinnedParameterNames` as `$ref` requirements — their component bodies drifted free. Repro: `QueueKind.schema.enum += ["audit"]` and `QueueItemId` with `pattern` deleted both passed `check-contracts` cleanly (exit 0). The two parameters now get the same pin block as the other six (`required`, `in`, `name`, exact schema).
2. **Declared query parameters were completely unpinned (`check-contracts.mjs`).** The non-canonical-parameter arm of `verifyCanonicalHeaderParameters` tolerates any `in: "query"` parameter whose `required !== true` — schema content unchecked. The `kind` param on `getOperatorQueue` and `cursor` on `getOperatorAudit` are exactly the served query grammars: repro mutations that all passed the checker include gutting `kind`'s enum+`default`, loosening `cursor`'s pattern to `^.*$`, renaming the parameter, dropping it entirely, and adding a sibling query key on the served ops. A new `pinnedQueryParameters` map pins each served-query operation to exactly its declared parameter (name, optional flag, exact schema via `canonicalJson`); canonical header parameters forced into a query position keep their dedicated rejection instead of being counted. The deliberate `assertAccepted` tolerance for an optional query param on a non-serving operation is preserved — contract noise there is a documented boundary, tightened below at the harness layer instead.
3. **The status→error-code binding was never asserted (`contract-validator.mjs`).** `conformanceErrors` validated the error envelope's shape, `request_id` echo and `details === {}` but never bound `body.code` to the status — the Error schema enums every code, so a valid-but-wrong code slipped. Repro: `401 + VALIDATION_FAILED`, `404 + RATE_LIMITED` and `500 + AUTHENTICATION_REQUIRED` all returned `[]` from `conformanceErrors`; only scattered per-op tests pinned codes per path, so the binding held by convention rather than by the harness every `checkedRequest` runs through. `STATUS_ERROR_CODES` now pins `400→VALIDATION_FAILED`, `401→AUTHENTICATION_REQUIRED`, `403→CAPABILITY_DENIED`, `404→CAPABILITY_DENIED`, `409→IDEMPOTENCY_CONFLICT`, `429→RATE_LIMITED`, `500→INTERNAL_ERROR`; a `>=400` response outside the map fails too.
4. **Declared path-parameter grammars were never cross-checked against the dispatcher's admission (`contract-guard-audit-wave68.test.mjs`).** The contract's `{param}` schemas and `matchOperation`'s `PATH_PARAMETER_PATTERN`/`INSTRUMENT_PATH_PATTERN` are two independent grammars; a declared superset documents URLs that can never route — every contract-valid request 404s. Repro: `QueueItemId` pattern `^[a-z0-9_-]{0,127}$` (admits short/digit-leading segments the router rejects) passed both `check-contracts` and the full customer-api suite (54/54). The new test mirrors `matchOperation` exactly, reads the runtime regexes out of `app.mjs` source (and fails if they change), then proves every declared path-param grammar admissible: `enum` values each admitted on the wire, `pattern`s either equal to the runtime grammar or a verified `^literal[class]{m,n}$` subset shape. It also asserts each templated path declares exactly its own placeholders.
5. **Declared query parameters were not bound to the served-query operations (`contract-guard-audit-wave68.test.mjs`).** A `?param` declared on an operation the dispatcher refuses documents input that always 404s — tolerated by the checker's optional-parameter arm (deliberate boundary) but real drift on the served surface. The new test requires declared query parameters to exist only on `getOperatorQueue` (`kind`) and `getOperatorAudit` (`cursor`), each optional, each a `type: "string"` schema, and pins the grammars to the runtime allowlists: the `kind` enum equals `OPERATOR_QUEUE_KINDS` (imported from `src/operator.mjs`) with `default` equal to the first served kind, and `cursor`'s declared pattern equals `AUDIT_CURSOR_PATTERN` extracted from `operator.mjs` source, cross-checked behaviorally against `isOperatorAuditCursor` on edge probes.
6. **Per-operation tags were unpinned (`check-contracts.mjs`).** Only the global tag-name set was enforced; a served op's tags were bound to its namespace only in coverage tests, and an *unserved* op's tags were bound nowhere — a `/api/v1/customer/...` op tagged `Operator` (or the reverse) drifted through `check-contracts` and silently mis-drove the harness's header choice for unserved-404 checks. Repro: retagging `claimCustomerCheck` to `["Operator"]` passed exit 0. Every operation's `tags` now must be exactly the single namespace tag for its path (`Metadata`/`Customer`/`Operator`).

## Verified clean (with negative pins)

- **Coverage symmetry holds fail-closed.** `sameSet(operationIds, pinnedOperationPaths)` pins opId→path exactly; `servedPairs` must equal declared pairs (every served op documented, every documented op served — a missing dispatch arm `throw`s to a 500 the 2xx assertion catches); `OPERATIONS.length` equals the non-unserved declared count; every declared status on every served op must be *observed* on the wire, not merely declared. Registration cannot outrun documentation or routing.
- **Response depth is real.** `pinnedResponseSchemas`/`successSchemas` pin exact schema bodies; the live validator walks `required`, nested `properties`, `items`, `pattern`, `format`, `enum`, `uniqueItems`, bounds — an empty `{items:[]}` violating a nested `minItems`/`pattern` fails, and a directory emitting a non-conforming view answers the 500 envelope (view guards + wave-67 drift pins).
- **Capability binding is pinned twice.** The wave-67 `dispatch consistency` check slices each `operationId ===` arm in `app.mjs` source and requires `granted.includes("PATH_DERIVED_CAPABILITY")` in the slice (the capability literal derived from the path) — a same-tier swap fails the arm — plus the `capability gate` test asserts unverified subjects 403 exactly the `requiresVerifiedKyc` set derived from `CAPABILITY_POLICY`.
- **Error envelope internals are uniform.** Every failure class emits exactly `{code, message, request_id, details}` with empty `details` and `x-request-id` echo; the uniform `Allow`-less 404 for non-GET methods, `CONNECT`, `OPTIONS *`, malformed request lines, oversized/duplicate headers and request-body-on-GET are all pinned in `routing.test.mjs`.
- **Evasion surfaces are closed.** `pathName.startsWith("/api/v1/")` pins versioning; duplicate opIds/paths, unknown opIds and unknown paths fail via `sameSet`s and the unknown-path list; `matchOperation` is exact-string with no normalization — double slashes, dot segments, percent-encoded variants, case flips, suffix junk and the 400-probe seeded sweep all answer 404 (`routing.test.mjs`); queries on non-query ops fail the same way.
- **Boundary checks are structural, not grep.** `verifyUniqueParameters` dedupes by resolved `in:name`; canonical refs must be pure `{$ref: canonical}` with no siblings; `assertNoDuplicateKeys` rejects shadowed JSON; non-canonical parameters must be explicitly optional and confined to header/query locations.
- **Header contract is fully bound.** RequestId/ClientVersion/Platform presence, DeviceId on exactly the operator namespace, Idempotency-Key on exactly the command ops, auth on every non-meta op, and response-side `X-Request-Id`/`Retry-After` echoes are all asserted per operation and on the wire.

## Observations (recorded, not defects in this slice)

- **Optional non-canonical parameters remain tolerated on non-serving operations** (the `assertAccepted` boundary fixture): OpenAPI generators routinely add optional params the runtime ignores. On this API they are also *refused* — the strict single-key query allowlist 400s them on the two served ops and the query gate 404s any `?` elsewhere — so the noise is harmless but visible; it is kept at the checker layer and now pinned away on the served surface by the wave-68 test.
- **`conformanceErrors` treats a response with an undeclared status as InternalError** and validates it against that component: a `409` on an unserved command or a `405` on `/metrics` fails "undeclared status" first — correct layering, recorded so the new code pin reads correctly.
- **`unserved()` in `contract-conformance.test.mjs` is a namespace predicate** (`/api/v1/customer/checks/` + operator-minus-list), not an opId pin — fail-closed either way: a new unserved op outside those prefixes shifts the `OPERATIONS.length` balance and fails loudly, and `check-contracts` pins every opId+path anyway.
- **A duplicate test block sat in `contract-conformance.test.mjs`** — the wrong-audience principal rejection case appeared twice with identical bodies — removed; the single copy still covers the case.
- **`operationFor` (validator) iterates paths in document order while `matchOperation` (server) iterates `OPERATIONS` order.** No two served templates overlap today, so resolution is unambiguous; a future pair of same-prefix templates could diverge — worth a deterministic-order check if the templated surface grows.
