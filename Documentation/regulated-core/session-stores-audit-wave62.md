# Postgres Session Stores Audit — Wave 62 — Proposed

- Status: Proposed
- Scope: `packages/customer-api/src/auth-session-store.mjs` + the auth-session additions in `packages/customer-api/src/postgres-store.mjs` + `packages/customer-api/migrations/0002_auth_sessions.sql` (landed at #304), and `backoffice/src/server/session-store.ts` + `session-store-contract.ts` + `backoffice/src/server/postgres-session-store.ts` + `backoffice/migrations/0002_operator_sessions.sql` (landed at #307), plus the cross-store claims against the third session stores (`miniapp/src/server/session.ts` HMAC handles and the `miniapp/src/server/postgres-session-store.ts` + `miniapp/src/server/session-store*.ts` + `miniapp/migrations/0001_customer_sessions.sql` Postgres seam landed at #309 while this audit was in flight — the cross-store pass covers it too) and the device-digest namespace (`backoffice/src/server/device.ts`). Everything is dev-only and synthetic — no production paths, no live data.
- Production effect: none

Hunt list applied: memory/pg parity gaps the contract suite misses (eviction ordering ties on equal `issued_at_ms`, boundary expiries `issued+1`/exact-instant/`MAX_SAFE_INTEGER`, empty-subject bounds, concurrent rotations on one session, digest reuse across different records); lifecycle correctness (expired-but-not-evicted rows vs lookups, refresh/revoke/bind on dead rows, double-bind, sweep under concurrency, `revoked=true` + `revoked_at_ms NULL` impossible states); the SQL layer (parameterization, index usage in eviction scans, atomicity of issue=insert+sweep+evict, advisory locks, `StoreError` vs `StoreUnavailableError` mapping and failure latching); migration correctness (trigger edge cases, UPDATE touching only `revoked_at_ms`, DELETE policy, TRUNCATE, CHECK symmetry, REVOKE coverage, catalog sequence validator races, idempotent re-apply); digest handling (rotation collisions, null-then-set device bypass, grammar enforcement at the store boundary); bounds enforcement (correct oldest evicted, bounds inside the same serialized op, cap vs concurrent issues); startup/close lifecycle (double-initialize, close-then-reinit, pool leaks, `query_timeout`, idle-client error listener); and cross-store consistency (id grammars, TTLs, `TOKEN_DOMAIN` collisions across the three packages).

## Defects found and fixed

1. **A no-op `revokeSession` evicted the subject's tombstones (`postgres-store.mjs`, `postgres-session-store.ts`).** The `evicted` CTE ran unconditionally: `revokeSession` on an already-revoked, absent or expired record still evaluated the tombstone bound and deleted rows, destroying history the memory backend preserves (its bound only applies when a new tombstone actually appears). Pre-fix repro failed on the postgres arm and passed on memory: issue two records, revoke both, then issue a third `revokeSession` against the already-revoked id — the oldest tombstone vanished. The `evicted` CTE is now gated on the target actually transitioning (`EXISTS` a live target `AND NOT EXISTS` a stale one), and the shared contract pins the no-op-revoke case on both backends.
2. **Session-table triggers ran only at ORIGIN replica role (`0002_auth_sessions.sql`, `0002_operator_sessions.sql`, `0001_customer_sessions.sql`).** `ENABLE TRIGGER` leaves triggers in `origin` mode, so a connection holding `session_replication_role = replica` could mutate `session_id`/`subject`/`issued_at_ms`, un-revoke a row, regress `expires_at_ms`, and `TRUNCATE` the table — bypassing every append-forward guard. `schema_migrations` already used `ENABLE ALWAYS TRIGGER`; the six session triggers now match it (the miniapp seam at #309 carried the same gap — its two session triggers were origin-mode too), and the shell assertion suites pin replica-mode immutability, terminality and TRUNCATE rejection on all three tables. The customer `reject_auth_session_mutation()` also gained `SET search_path = pg_catalog`, matching the backoffice and audit functions (the unpinned `session_id`/`subject`/`issued_at_ms` references resolve only in `pg_catalog` — without it a hostile `search_path` could shadow the catalog).
3. **`initialize()` could resolve on a pool that was already being torn down (all three stores).** `close()` while `openOnce()` was in-flight marked `closed` only after the probe resolved: `initialize()` returned successfully, the orphan drain then ended the pool, and every subsequent op threw `StoreUnavailableError` permanently despite the resolved promise — the inverse of the documented contract. Pre-fix repro raced `initialize()` and `close()` and observed the resolved-then-dead pool. `close()` now flips `closed` synchronously at entry and single-flights its teardown through `closing`; `openOnce()` re-checks `closed` after its probe and throws `StoreUnavailableError`/`SessionStoreUnavailableError` (draining the orphan pool first); `initialize()` awaits any in-flight `closing` before starting a new `openOnce()`. The miniapp store had the same shape — it drained the orphan but still resolved `initialize()` — and gets the identical fix. Pinned by the initialize/close-race and close-during-writes pg-arm tests on all three packages.
4. **Subject bounds ghosted past the cap across store instances (all three stores).** The per-subject active cap on issue and tombstone cap on revoke were evaluated inside a single statement whose MVCC snapshot cannot see siblings' uncommitted writes, while `tail` only serialized ops within one store instance. A probe running three store instances issuing 30 sessions each on one subject with `maxPerSubject = 2` ended with 3–4 live records (bound: 2) on both packages. Writes now run in an explicit transaction that takes `pg_advisory_xact_lock(hashtextextended(subject))` before the op — the bound evaluates after the lock serializes all same-subject writers on the shared database, and the lock cannot deadlock row locks because it is taken first and held to commit. Refresh/bind/touch/verifyKyc keep their per-row `FOR UPDATE` serialization; they enforce no subject bound. The miniapp store ran the same single-statement model with no advisory lock and gets the identical fix. Pinned by cross-instance pg-arm tests asserting `live = 2` after 30 concurrent issues and `tombstones <= 3` after 8 issues + concurrent revokes from three instances on all three packages.

## Verified clean (with negative pins)

- **Parameterization is total**: every subject/id/digest/timestamp reaches the wire as a `$n` parameter; no interpolation into statement text on either store. Eviction scans use the `subject` column index (per-subject `ORDER BY ... OFFSET` in a CTE), never a seq scan, and issue/refresh/revoke/bind are each one atomic statement.
- **Error mapping holds**: SQLSTATE 22xx/23xx (constraint, datatype, integrity) maps to `StoreError`/`SessionStoreError` with **no** failure latch — a deterministic conflict never takes the store down — while every other failure latches `StoreUnavailableError`/`SessionStoreUnavailableError`. Pinned on both arms (conflict → `StoreError`, dead DSN → unavailable).
- **Eviction ordering is bit-parity with memory, ties included**: `(revoked_at_ms ?? issued_at_ms) DESC, session_id ASC` for tombstones and `issued_at_ms DESC, session_id ASC` for live, so equal timestamps evict the *same* record on both backends — pinned by the tie cases.
- **Boundary expiries**: `expires_at_ms = issued_at_ms + 1` issues and expires one tick later; `now == expires_at_ms` is dead; `MAX_SAFE_INTEGER` never expires inside `bigint`; `last_used_at_ms > expires_at_ms` still expires on `expires`; revoked rows never expire from reads. All pinned.
- **Refresh semantics**: `expires_at_ms`/`last_used_at_ms` only move forward (`GREATEST`), a refresh presenting the session's own current digest is not a conflict, and a rotated-out digest becomes reclaimable by a *new* issue while a different live session's digest stays a conflict. Pinned on both arms.
- **Concurrent rotations on one session serialize**: `FOR UPDATE` takes the row lock; the second refresh sees the first's committed row — both resolve, last write wins. Pinned.
- **Digest grammar is enforced at the command layer** identically for both backends (shared `assert*` functions reject wrong length/case before any backend work); the DDL `CHECK` mirrors it. Pinned by the grammar case tables in both audit files.
- **Device binding is one-time and never retrofits**: `device_digest` starts `NULL`, binds exactly once on a live record, and every second bind — on bound, expired or revoked records — answers `null`, not a silent overwrite. Backoffice's login displacement (a new issue on a bound device deletes the device's other live sessions) is identical on both backends. Pinned.
- **Impossible states are closed symmetric**: `revoked = true, revoked_at_ms IS NULL` and `revoked = false, revoked_at_ms IS NOT NULL` both reject at the `CHECK`, on both tables, under `origin` *and* `replica` roles. Pinned in the shell suites.
- **Trigger edges hold under replica**: identity columns immutable, `expires_at_ms`/`last_used_at_ms` never regress, revocation terminal, device rebind rejected, `TRUNCATE` blocked — each rejected with the trigger's own error under `session_replication_role = replica`. Pinned.
- **The catalog sequence validator has no residual race**: concurrent catalog inserts serialize on the `(version, migration_name)` primary key — one wins, the rest surface `23505`. Re-applying an applied migration fails loudly (pinned: replay exits non-zero and the catalog stays at exactly two rows).
- **Startup/close lifecycle is single-flighted**: double `initialize()` shares one pool probe, double `close()` shares one teardown, `close()` then `initialize()` reopens cleanly, and the pool-leak test asserts `pool.end` exactly once. `query_timeout` is set on the pool config and an idle-client error listener absorbs pool-level failures instead of crashing the runtime. The miniapp `reject_session_mutation()` already pinned `SET search_path = miniapp_control, pg_catalog` — verified, no change needed.
- **Token digest namespaces cannot collide across the three stores**: customer `solidchange-customer-api-auth-session-token-v1`, backoffice `solidchange-backoffice-operator-session-token-v1`, miniapp `solidchange-miniapp-session-handle|{id}` (HMAC, not the sha256 token domain), device `solidchange-operator-device:v1:{id}`. Distinct domains and distinct id grammars (`sess_` x2 vs `ses_`) — a digest minted in one store can never address a session in another. Pinned by the namespacing cases in both audit files.

## Observations (recorded, not defects in this slice)

- **Subject CHECKs diverge deliberately**: customer pins `^syn_(cust|oper)_[a-z0-9]{8,32}$` (its own subject grammar) while backoffice pins the generic `^[a-zA-Z0-9_.+:@|-]{1,128}$` — each matches its own command-layer validator. A caller bypassing the stores would face different grammar per table; that is recorded divergence, not inconsistency.
- **`DELETE` is allowed on the session tables by design**: the store's own evictions and the expiry sweep delete rows, so the append-forward model is enforced by `REVOKE ALL ... FROM PUBLIC` and the trigger's column guards — not by a DELETE trigger. Pinned as an explicit allowance in both shell suites.
- **`last_used_at_ms` is the sweep/issue expiry clock on both backends** (a refresh moves expiry forward and keeps the session live at its own `last_used` tick) — odd-looking but mirrored bit-for-bit from memory.
- **The advisory lock covers only bound-enforcing ops** (issue, revoke). Refresh and bind take row-level `FOR UPDATE` only: they carry no subject bound, so serializing them per subject would be pure contention — same separation the memory backend draws.
- **Backoffice's seam exposes `countSessions`; the customer seam does not** — a real surface difference a shared caller must not assume, kept as an observation because each seam is internally consistent and the contract suites are per-package.
- **The miniapp seam is a different op vocabulary and ordering model**: it names its touch op `touchSession`/`verifySessionKyc` (the other two refresh/bind), adds `deleteSessionByTokenDigest` for logout, and orders eviction by `store_seq` (insertion order) rather than `issued_at_ms`. Within miniapp the Postgres column mirrors its own memory backend's sequence counter bit-for-bit, so parity holds inside the package — but a shared caller comparing stores sees `sess_` ids evicted by arrival order in miniapp and by declared issue time elsewhere. Also different: miniapp's first Postgres session store *is* its durability story — the HMAC `ses_` handles in `miniapp/src/server/session.ts` are a separate per-process mechanism, not the same seam.
