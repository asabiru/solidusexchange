# Customer-API client audit — wave 75

- Status: Proposed

Wave 75 line-audits `miniapp/src/server/customer-api-client.ts` (~3.5k lines — the BFF's upstream client to the dev customer-api: served-view parsing, request lifecycle, capability negotiation, error mapping). Prior waves audited the api.ts surface (#305) and the backoffice adapter (#303); this file's per-endpoint internals had never been audited end-to-end. The customer-api channel serves plain JSON views — no signed envelopes — so the audit oracle is the upstream `valid*View` guard set in `packages/customer-api/src/*.mjs`: every contract pin upstream enforces when it mints a view must fail closed client-side when a served body drifts. Each defect below was reproduced as a failing test before the fix landed in the same change.

## Defects found and fixed

1. **Wallets trusted a subset or superset of the minted set.** `parseWalletsView` let through any non-empty list of wallet-shaped entries. The upstream view always carries exactly one wallet per supported asset (RUB/USDT/TON) with `syn_wal_[a-z0-9]{8,32}` ids and no repeated asset. The parser now requires the exact asset set, the id pattern and per-asset uniqueness.
2. **Deposits trusted incoherent lifecycle totals.** `parseDepositsView` validated field shapes but not the per-status invariants upstream mints: `expected > 0`, `updated_at >= created_at`, and per-status received/reversed arithmetic (`awaiting_payment` ⇒ untouched; `payment_received` ⇒ received == expected; `partial_payment` ⇒ 0 < received < expected; `duplicate_payment` ⇒ received == 2×expected; `payment_reversed` ⇒ 0 < reversed ≤ received == expected; `expired_no_payment` ⇒ 0/0 with `updated > created`). Any violation now fails closed.
3. **Withdrawals trusted wrong TTL and incoherent status touches.** `parseWithdrawalsView` now pins `expires_at − created_at == INTENT_TTL (300_000ms)`, `updated >= created`, `draft ⇒ untouched`, `expired ⇒ updated == expires`, `confirmed ⇒ updated > expires`, and every other status strictly inside the intent window.
4. **Market exchange orders let a non-rejected status through.** Upstream rejects every market order at intake, so `order_type === "market"` implies `status === "rejected"`; the parser let through any enum status for any order type.
5. **Checks trusted arbitrary counterparty refs and fiat checks.** `parseChecksView` required only string refs and `isAssetCode`. The check directory mints `syn_cust_…` or `syn_peer_…` refs on both sides and USDT/TON checks only — the parser now enforces the ref patterns and the {USDT, TON} asset set.
6. **Activity trusted a re-declared local status word and an unbound detail.** The status rule was a generic slug pattern and detail a generic printable pattern. Upstream pins per-kind status vocabularies (the sibling collections' lifecycle enums; quote → indicative; kyc → the application states minus not_started; security → login|revoked) and requires each domain-kind detail to cite that collection's id prefix (`dep_`/`wdr_`/`qte_`/`ord_`/`pay_`/`crd_`/`chk_` + 24 hex) while kyc/security cite none. Also enforced: 1..9 items, unique ids and kinds, strictly decreasing `created_at`.
7. **Operations trusted per-kind-invalid statuses, zero fees, wrong leg direction, empty notes and an unbounded timeline.** `parseOperationItem` now mirrors the upstream vocabulary (exchange → order statuses, deposit → deposit statuses, withdrawal → withdrawal statuses, qr → payment statuses), requires `fee_amount > 0` at the fee asset's scale, a single leg directed `out` for withdrawals and `in` otherwise, `note` bounded 1..256, and `channel`/`title` at the upstream 64/128 bounds. Timelines cap at 4 steps with recorded `at` non-decreasing and never later than `created_at`.
8. **Operations feed trusted an unbounded, duplicate or unsorted list.** `parseOperationsView` now requires 1..4 items, unique `operation_id` and `kind`, strictly decreasing `created_at`.
9. **Notifications trusted non-canonical timestamps.** The check was `Date.parse`-only, which normalizes `2026-02-31` into March and `T24:00` into the next day — drift the served contract rejects. It now uses `isIsoTimestamp`, requiring the stamp to reserialize to itself.
10. **Support tickets trusted an arbitrary expiry and monotone-but-free timeline steps.** Upstream mints `expires_at == created_at + 86_400_000` exactly and stamps timeline entry i at `created + i·3_600_000`. The parser let through any later expiry and any increasing steps.
11. **Deposit addresses and screenings trusted partial or duplicated target sets.** Both views now require exactly one record per allowlisted (asset, network) pair — the fixed three-pair custody-dev-v1 set — and addresses must match the network's own syntax (`kQ…` TON-friendly-form, `T…` TRON base58check) rather than a generic base shape.

## Verified clean

- **Error-path fidelity.** Every endpoint's catch arm maps to the documented union (`ok`/`denied`/`unavailable`/`not-configured`/`not-found`/`missing`); no internal error text, provider detail or stack reaches the client. Subject binding is by construction (minted token subject is echoed by the session view and compared), so a non-string subject can never throw or leak.
- **Body/stream bounds.** `readBoundedJson` requires `application/json` (case-insensitive), fails closed on bodies over the 16 KiB cap whether the limit is exceeded by `content-length` or discovered mid-stream on chunked lies, cancels the reader on failure, and treats invalid UTF-8 as fatal.
- **Request lifecycle.** One fetch per call with `AbortSignal.timeout` (no retries anywhere — read-only GETs fail closed into `unavailable`), canonical request headers (bearer `Authorization`, `X-Request-Id` as uuidv7, `X-Client-Version`, `X-Platform`, the pinned JSON content type), no `X-Device-Id`, and DNS/connection/timeout failures map to `unavailable` — never a 500 or a thrown internal.
- **Capability/auth.** Token is minted per call with a fixed 300 s TTL; the served session view must echo the exact minted expiry and the pinned scope pair, and capabilities must be a unique non-empty subset of the vocabulary with `commands_enabled === false`.
- **Member-read binding.** `marketDepth`, `addressScreening` and `operation` re-check that the served record's id equals the requested id — the #303 cross-record echo class is closed on every member endpoint.
- **Concurrency/caching.** No client-side caches exist (token minted per call, every read a fresh fetch), so there is no stale-while-revalidate or dedup surface to drift.

## Observations

- The client intentionally performs **no retry machinery**: every read is a single GET and any failure maps to `unavailable`. For dev-only synthetic upstreams this is a deliberate fail-closed simplification, noted rather than fixed.
- `parseDepositsView` does not pin the deposit intent TTL — upstream bounds `updated >= created` only; the client mirrors that exactly. Any future upstream TTL pin lands here in the same shape as the withdrawal pin.
- `check` assets exclude RUB by contract (the fiat rail has no claim-code surface); the pin lives next to the ref patterns with a comment explaining why.

## Test additions

Fourteen new cases in `miniapp/src/server/customer-api-audit.test.ts` under `customer-api client served-view contract audit (wave 75)`, each written to fail on the unfixed parser: wallets exact-set, deposits per-status totals/lifecycle, withdrawals TTL/lifecycle, market-order status pin, checks ref/asset pins, activity per-kind status and ref binding, activity bounds/dedup/ordering, operation item rules (status/direction/fee/timeline), operations feed rules, notifications canonical ISO, support fixed-step/TTL, deposit-addresses exact set with network syntax, screenings exact set, and a throw-mapping union sweep. One legacy fixture in `customer-api-client.test.ts` was contract-invalid (an in-flight withdrawal status stamped with `updated == created`) and was brought to the contract-faithful shape.
