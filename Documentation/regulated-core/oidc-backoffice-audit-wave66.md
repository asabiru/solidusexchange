# OIDC Backoffice Port Adversarial Audit — Wave 66 — Proposed

- Status: Proposed
- Scope: `backoffice/src/server/oidc.ts` (the operator-BFF verifier and code exchange), the login/callback wiring in `backoffice/src/server/server.ts`, `backoffice/src/server/config.ts` env-pair validation, `backoffice/src/server/session.ts` pending-login lifecycle, session mint/rotation for the pseudonymized `syn_oper_*` principal via `customerApiSubject(sub)`, and the backoffice arm of `packages/e2e-dev/tests/oidc.test.mjs`. Everything is dev-only and synthetic — no production paths, no live IdP traffic.
- Production effect: none

Hunt list applied: every wave-65 defect class re-checked against this separate verifier port (non-canonical JWK `n`/`e` and weak exponents, `at_hash` required-when-issued, `token_type` pinning, duplicate JSON members in fetched documents, last-wins cookie lookup), plus backoffice-specific surfaces: `sub`→operator-role derivation (unmapped → `auth_failed`, role confusion across remapping), the device-binding gate interleaved with the OIDC mint (can a login bypass pending-device review; is `previousSessionToken` rotation single-flight under parallel callbacks), the audit sink's coverage of auth events, session binding to the `syn_oper_*` directory grammar, and config refuse-start semantics.

## Defects found and fixed

1. **The verifier admitted weak RSA exponents and non-canonical JWK members (`backoffice/src/server/oidc.ts`).** Same unported class as wave-65 defect 4. `n`/`e` were checked only for `typeof string`, so `e: "AQ"` (exponent 1) imported into a working key — and with `e = 1` a PKCS#1 v1.5-encoded message is its own signature, so a forged `id_token` verified end to end with no private key at all — proven on pre-fix code at unit level and through the wired hostile-issuer arm. `e: "Ag"` (exponent 2) and non-canonical member spellings (`"AQAB="`, whitespace-padded `n`) were likewise normalized and admitted silently. `n`/`e` must now round-trip exactly through base64url decode/encode, and the exponent must be an odd `bigint` of at least 3 (the ≥ 2048-bit modulus floor is unchanged).
2. **`at_hash` was optional even when an `access_token` had been issued (`oidc.ts`).** Wave-65 defect 5, unported: the hash compared only when the claim was present, so a hostile issuer could strip `at_hash`, keep the `access_token`, and the exchange still verified — proven on pre-fix code at unit level and wired end-to-end. `at_hash` is now required whenever an access token is present and must equal `base64url(SHA-256(access_token))[0:16]` exactly.
3. **The token response was not pinned to `token_type: "Bearer"` (`oidc.ts`).** Wave-65 defect 6, unported: `token_type: "MAC"` or a missing member resolved into a verified exchange — proven on pre-fix code at unit level and wired end-to-end. The response must now declare `token_type` exactly `Bearer`.
4. **Duplicate JSON members in fetched documents passed silently via last-wins `JSON.parse` (`oidc.ts`).** Wave-65 defect 7, unported: `readBoundedJson` bounded the byte count but never scanned for repeated members, so the token response and the JWKS document both parsed last-wins — `{"e":"AQ","e":"AQAB"}` kept the honest member, `{"kid":"decoy","kid":"k1"}` selected the attacker-chosen `kid` — proven on pre-fix code at unit level and wired end-to-end. `readBoundedJson` now runs the existing raw-text duplicate-member scanner before parsing and rejects on a repeated member.
5. **Cookie lookup was last-wins, letting a broad-path forgery shadow the transaction or session cookie (`backoffice/src/server/server.ts`).** Wave-65 defect 8, unported: browsers order cookies most-specific-path first, so a `Path=/` `solidchange_bo_oidc_transaction` forgery appended after the real `Path=/bff/auth` cookie won the lookup and sank a valid callback, while a trailing forged `solidchange_bo_session` shadowed a live session — proven on pre-fix code wired end-to-end. A forged session cookie captured at login time also landed in `previousSessionToken`, so the real login-time session escaped revocation — a rotation bypass beyond the miniapp's version of this defect. Lookup is now first-wins, matching the user's actual cookie order, with `__proto__` skipped and malformed percent-encoding recorded as an empty value so it still counts as the first occurrence.
6. **A denied callback discarded the freshly minted device cookie (`server.ts`).** `oidcAuthFailed` replaced the whole `set-cookie` header with the transaction-cookie clear, clobbering the `solidchange_bo_device` cookie `admittedDevice` had just minted: under `BACKOFFICE_DEVICE_BINDING=enforce`, every denied callback minted a *different* device id that never reached the browser, so a pending device could never be named for review against a stable digest — proven on pre-fix code wired end-to-end. The failure redirect now appends the clear instead of replacing, preserving the minted device identity.

## Verified clean

- **Issuer-side wave-65 classes 1–3 (shared component).** The backoffice arm runs against the same `provider-simulators/src/oidc.mjs` mount the miniapp audit hardened: origin + path-prefix dispatch (foreign-authority absolute-form refused `404`), exact media-type matching, `Symbol`-typed duplicate-parameter sentinel, bounded `state` reflection on error redirects, and `405` + `Allow` on wrong methods. Verified via the existing issuer pins re-run alongside the new backoffice arm.
- **Role mapping fails closed (`oidc.ts` `mapRole`).** A `sub` with zero mappable groups throws "no mapped backoffice role" → `auth_failed` with no session — proven wired with `groups: ["nobody"]`; two or more distinct mapped roles throw "ambiguous backoffice roles" → fail closed; unmapped group names are skipped via `Object.hasOwn`; each login re-derives the role from the current `roleMap`, so there is no cross-login role carryover. Mapping runs inside `verifyIdToken`, so an unsigned role outcome cannot be reached.
- **Device gate runs before the token exchange (`server.ts`).** `admittedDevice` executes ahead of `exchangeAuthorizationCode`, so no OIDC mint can bypass pending-device review: under `enforce` with an unlisted digest the callback folds to `auth_failed` — already pinned by the wave-52 suite — and the device cookie minted for that attempt now survives (defect 6). The pending-login entry is consumed by `take` before the gate, keeping denial single-use.
- **Rotation is single-flight under parallel callbacks (`session.ts`/`server.ts`).** `pendingLogins.take` atomically removes the pending entry; two concurrent callbacks sharing one transaction resolve to exactly one minted session and one `auth_failed` — pinned under `Promise.all`. `createSession` revokes both the callback-presented and the login-start session tokens, so a re-login retires the prior session even though the Strict cookie is not sent cross-site.
- **Session binding is coherent (`customer-api-client.ts`/`session-store.ts`).** `customerApiSubject(sub)` always yields `syn_oper_<24 lowercase hex>` — a namespaced HMAC-style derivation that fits the store's subject grammar and the upstream `syn_oper_` pattern; claim characters never reach storage verbatim. There is no path by which a `sub` maps to an unknown or non-operator principal.
- **Config refuse-start and scoping (`config.ts`).** The `BACKOFFICE_OIDC_ISSUER_URL` + `BACKOFFICE_OIDC_CLIENT_ID` pair must arrive together or startup throws; the issuer URL needs HTTPS unless every allowed origin is loopback HTTP, rejects queries, and normalizes trailing slashes; the client id must match `^[A-Za-z0-9._:-]{1,128}$`; `redirectUri` is derived from `allowedOrigins[0]` (never the issuer); `roleMap` JSON is validated against the roles set with a `"groups"` default claim. The transaction cookie `Path=/bff/auth` matches the `/bff/auth/*` route layout exactly.
- **Callback/input hygiene (already pinned, re-verified).** Duplicated `code`/`state` → fail; `?error=` (including CRLF payloads) folds into the generic `auth_failed` redirect with no reflection and no marker leakage in body or `Location`; unconfigured auth routes answer a byte-identical `404` to unknown routes; the post-auth `Location` is always `allowedOrigins[0]`; each login mints a fresh `state`/`nonce` pair; `PendingLogin` entries are per-initiator bounded (2) and globally bounded (256), newest retained.
- **Verifier header/segment rules (already in the port).** Canonical unpadded base64url on all three segments; the duplicate-member scanner on header and claims; `alg` pinned `RS256`; `kid` non-empty and exactly-one match; `crit` refused; `jku`/`jwk`/`x5u`/`x5c`/`b64` rejected; private JWK members refused; `use`/`key_ops`/`alg` pins; `iss`/`aud`/`azp`/`nonce`/`exp`/`iat`/`nbf` checks; `sub` printable ASCII, 1–255 characters; 16,384-character token cap; bounded 65,536-byte fetches with `redirect: "error"` and an 8-second deadline, no JWKS cache.

## Observations (recorded, not defects in this slice)

- **No login-audit append exists — confirmed.** `auditStore.append` fires only on the data view/export/command routes; `/bff/auth/login`, `/bff/auth/callback`, `/bff/auth/logout` and `/bff/auth/dev-session` append nothing. The access-control model lists authentication success, failure, factor recovery and risk response among auditable event families, and the miniapp BFF records `activity.recordLogin` plus an outbox row. Whether operator auth events belong in the backoffice's bounded synthetic chain is a docs decision — recorded, not changed.
- The `X-Device-Id` request header is ignored on this BFF (the miniapp 400s it uniformly); device identity here derives from the `solidchange_bo_device` cookie only, so an ignored header confuses nothing — noted for parity, not changed.
- No Host-header guard on the BFF (the miniapp 421s non-loopback hosts); cookies are host-scoped and POSTs already need an exact loopback `Origin`, so the gap is cosmetic — noted.
- Store bounds `email ≤ 320` / `name ≤ 200` make oversized claims fail closed at mint; a `sub` of 201–255 characters carrying no `name`/`email` can never log in — deny-by-default behavior, consistent with the subject grammar.
- `iat`/`nbf` still have no lower bound, matching the wave-52 posture — recorded as consistency, not an auth hole.
- The `Secure` flag on the session, transaction and device cookies appears only when every allowed origin is HTTPS; dev loopback omits it by design.
