# Miniapp BFF Server Route-Table Audit — Wave 68 — Proposed

- Status: Proposed
- Scope: `miniapp/src/server/server.ts` — the single `handle()` dispatch monolith carrying the `/bff/*` route table (the frozen `routeTable`, the health/session/account reads, every subject-scoped collection and member read, the two preview endpoints, the POST command tier, the OIDC login/callback dispatch, the metrics scrape gate) plus the seams it delegates to: `customer-api-client.ts` upstream binding, `readBoundedJson`/`readJsonBody` bounds, `observability.ts` route-label machinery, `security-headers.ts`, `session.ts`, `oidc.ts` pending-flow store, `support.ts` local desk, `sessions.ts` upstream-session mapping, and the app-side client `src/app/api.ts`. Everything is dev-only and synthetic — no production paths, no money movement, no real customer data.
- Production effect: none

Hunt list applied: dispatch order and prefix shadowing, method-mismatch uniformity, trailing-slash/case/double-slash and percent-decode normalization, the `knownGet` gate's route recognition, `?query` rejection parity across collections and member reads, session/cookie scoping and KYC-gate application per route, upstream subject binding and response-id pinning, fallback arm coherence (documented degrade vs fabricated success), response/body/timeout bounds per call, error taxonomy (`*_unavailable` family, catch → generic never fabricated), and the sec-fetch/Origin/CSRF posture including the CORS-free guarantee.

## Defects found and fixed

1. **The `knownGet` gate recognized POST-only paths as known GET routes, answering 401 instead of 404 to unauthenticated callers.** The gate iterated `routeTable` and returned `route.path === path` for *any* literal match — including the seven POST routes whose paths have no GET handler (`/bff/auth/logout`, `/bff/auth/dev-session`, `/bff/session/telegram`, `/bff/kyc/applications`, `/bff/sessions/revoke`, `/bff/sessions/revoke-others`, `/bff/notifications/read`). Repro-failed on main: `GET /bff/auth/logout` unauthenticated → `401 {"error":"unauthenticated"}` while `GET /bff/never-registered` → `404`. The 401 was both a route-existence oracle (an unauthenticated probe could distinguish real POST paths from absent ones — the exact information the gate exists to hide) and internally inconsistent: the same request with a session answered 404 because no GET dispatch arm exists. The fix restricts the gate's literal and prefix arms to `GET` routes, so a POST-only path answers 404 like a never-registered one regardless of caller session state.
2. **`?query` rejection was not uniform across GET surfaces: about fifteen no-input routes silently ignored arbitrary parameters while their siblings rejected them.** Repro-failed on main: `GET /bff/wallet?x=1`, `/bff/session?x=1`, `/bff/account?x=1`, `/bff/profile?x=1`, `/bff/kyc/status?x=1`, `/bff/markets?x=1`, `/bff/quotes?x=1`, `/bff/deposits?x=1` (and `withdrawals`, `operations`, `exchange-orders`, `trades`, `payments`, `cards`, `health`) all answered 200 with the parameter silently dropped, while `/bff/notifications?x=1`, `/bff/sessions?x=1`, `/bff/support/requests?x=1`, `/bff/address-screening?x=1`, `/bff/checks?x=1` and every member read answered 400 `invalid_request`. A silently ignored parameter reads as applied input — the same failure mode the member reads and the upstream contract reject outright. The fix replaces the eight scattered per-route checks with one gate after session resolution driven by `queryInputGetRoutes`, the exact declared key sets of the only three query-taking routes (`/bff/activity` pins `?limit` itself, `/bff/quotes/preview` declares `{from,to,amount}`, `/bff/checks/preview` declares `{asset,amount}`); undeclared keys inside those three are now rejected too (`?from=…&junk=1` → 400, previously served). `/bff/health` gets the same rejection inline because it answers before the session tier. Ordering is preserved: unauthenticated still resolves the session first (401 before 400).

## Verified clean (with negative pins)

- **Dispatch order has no shadowing.** Every exact path arm is tested before the `startsWith` member prefixes; inside the combined checks block `/bff/checks/preview` is handled before the `/bff/checks/:reference` member arm, and `/bff/support/requests` splits list/member on the full path — no longer-prefix route is swallowed by a shorter one.
- **Method mismatch is uniform.** PUT/DELETE/PATCH/OPTIONS/HEAD on every `/bff/*` path answer 404 `not_found`; the metrics scrape alone answers 405 with `Allow: GET`, and only when `MINIAPP_METRICS=loopback` (a deliberate scrape posture, not dispatch drift).
- **Path normalization is strict where it matters.** `/bff//session`, `//bff/session`, `/bff/session/`, `/BFF/session` all answer 404 — no case folding, no trailing-slash equivalence, no double-slash collapse. WHATWG `URL` normalization resolves `\` and dot-segments before dispatch (`/bff\session`, `/bff/./session`, `/bff/x/../session` serve the named route) — consistent because the normalized pathname is the routed key; the metrics gate pins the raw `request.url` exactly so aliases never reach the scrape.
- **Percent-decoding is single-pass and re-validated.** The markets member decodes `%2F` once into the `{base}/{quote}` instrument, then `marketInstrumentPathPattern` (`^[A-Z0-9]{2,8}/[A-Z0-9]{2,8}$`) re-validates the decoded value before any upstream call — `%252F` double-encoding, lowercase sides, bare `%2F`, and raw `/` all answer 404 without reaching the directory. Single-segment member ids (`ope_*`, `scr_*`, `sup_*`, check references) are passed raw and validated by their own contract patterns; the upstream path is re-encoded per segment via `encodeURIComponent` — no path smuggling either direction.
- **Member `?query` parity was already uniform.** `/bff/operations/:id`, `/bff/markets/:instrument`, `/bff/support/requests/:id`, `/bff/address-screening/:id`, `/bff/checks/:reference` each answer 400 on any non-empty search; the new gate lifts that same contract to every remaining GET surface.
- **Session scoping is uniform.** Every session route funnels through the one `currentSession` call (cookie parse → store lookup → lazy KYC sync → 60s touch) — no sibling misses the touch/rotation side effects; the dev-login cookie is `Path=/bff; HttpOnly; SameSite=Strict` and `Secure` exactly when the request origin is https; the OIDC transaction cookie is `SameSite=Lax` and binds the flow to the initiating browser. KYC gating applies identically per surface family (local `kyc_required` 403 on screening; degrade-in-place on money reads; never-gated reads have no `denied` arm).
- **Upstream binding is per-subject with response pinning.** Every `customerApi` call passes the caller's `session.subject` → `customerApiSubject` → a fresh `mintSyntheticCustomerToken` per request (300s TTL) — the audit-feed shared-reader pattern does not exist anywhere in the subject-scoped surface. Member reads bind the upstream response id to the exact request parameter (`response.instrument !== instrument`, `operation_id !== operationId`, `screening_id !== screeningId` → `unavailable`); contract-id shapes are pre-flight short-circuits (`not-found`/`missing` without a network call).
- **Bounds are uniform per call.** Every upstream GET runs through the single `get()`: `AbortSignal.timeout(2_000)`, `redirect: "error"`, and `readBoundedJson` under `maxCustomerApiResponseBytes` (16_384, declared-length and streamed-count both enforced). Inbound bodies are bounded at 4 KiB with `application/json` (+optional `charset=utf-8`) required. The app-side seam (`src/app/api.ts`) mirrors it: all 40 `api.*` calls funnel through `call()` → `readBoundedJson` (262_144 bytes, the streamed-JSON seam the hunt list names) → `assertCanonicalJson` depth ≤ 16 — no call path bypasses the bound.
- **Fallback coherence holds.** Upstream `denied` maps to the documented degrade-in-place arms (gated views, zero-affordability preview — fail closed, never fabricated data); all other upstream failures map to the `*_unavailable` 503 family; never-gated reads collapse 403 to `unavailable` by contract comment. No route swallows an exception into a fabricated success shape.
- **CSRF posture is uniform with no CORS surface.** `customerFetchAllowed` admits only `undefined|same-origin|none` before any route; every POST requires an exact `Origin` match against `config.allowedOrigins` (dev-session additionally demands loopback origin *and* loopback socket); OIDC login/callback sit outside the fetch-site gate by design (the tx cookie re-binds the flow). `apiSecurityHeaders` carries no `Access-Control-Allow-Origin` — CORP `same-origin` on every response.

## Observations (recorded, not defects in this slice)

- The support member read is local-only by design and pinned in `fallback-arms.test.ts`: the list serves upstream `tck_*` tickets while the member route only resolves local `sup_*` drafts — an upstream ticket id 404s on detail. Same shape as `contractAuthSessionsView`, where the upstream `session_id` is exposed as a handle but `POST /bff/sessions/revoke` resolves only local `ses_*` handles — upstream ids cannot be revoked, commands stay local.
- `/bff/auth/dev-session` answers 404 (not 403 `origin_rejected`) on a wrong origin — the hidden-route posture differs from sibling POSTs deliberately so the dev-only endpoint is indistinguishable from absent surface.
- Anonymous OIDC initiation can evict legitimate pending logins through the global 256 pending bound: the per-initiator cap keys `flow:${state}` and is therefore toothless for cookieless flows, where every request self-roots a new initiator key. Dev-only posture; noted for a future rate-limit pass.
- POST routes uniformly ignore `?query` (the pin applies to GET contract parity; local commands are not upstream-bound reads). The body is parsed before session resolution on every POST — uniform ordering: origin → fetch-site → body → 401.
- `/bff/notifications/read` mixes two provenances in one write path (upstream `mark:*` handles vs local drafts) — documented in the route comment; the marked-id grammar is enforced before either arm runs.
- Local fixture operation ids (`op-*`) are unreachable while the upstream is configured because the member space resolves in the upstream `ope_*` namespace — the intended seam semantics: configured upstream replaces the view entirely rather than overlaying it.
- Method-mismatch answers 404 rather than 405 outside metrics — a deny-by-default choice, uniform across the table.
- The dispatched hunt list referenced a "256KB streamed-JSON seam" and `smt_*` bearer scoping; the repo's upstream bound is 16_384 bytes (`maxCustomerApiResponseBytes`), 262_144 is the app-side BFF client cap, and sessions are cookie-based (`solidchange_miniapp_session`), not bearer — audit applied to the actual seams.

## Test additions

- `src/server/route-table-audit-wave68.test.ts` (6 cases): the two defect regressions — unauthenticated GETs on every POST-only path answer 404 like a never-registered path (authed control keeps 404, real GET routes keep 401), and the uniform `?query` pin over every GET collection and instantiated member path (`?audit=w68` → 400 `invalid_request`), including `/bff/health` pre-session and undeclared-key rejection inside the three query-declaring routes — plus the positive controls that the declared inputs (`?limit=5`, full preview parameter sets) and query-free routes still serve. Both defect cases fail on main (`401`/`200` actuals) and pass on this branch.
- `src/server/kyc-routes.test.ts`: the client-supplied-status case now asserts the strict 400 rejection for `/bff/kyc/status?state=…` plus the unchanged query-free view — the test's intent (a client can never supply its own KYC state) is strengthened, not relaxed.
- `src/server/observability.test.ts`: the secret-bearing `/bff/session?initData=…` request now expects 400; the non-leak assertions over logs and metrics are unchanged — secrets in the URL never reach either surface.
