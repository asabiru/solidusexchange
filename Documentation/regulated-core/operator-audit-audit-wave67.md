# Operator Audit Feed Adversarial Audit — Wave 67 — Proposed

- Status: Proposed
- Scope: `GET /api/v1/operator/audit` (landed #322) end to end — `packages/customer-api/src/operator.mjs` feed derivation (`expectedAuditEntries`, `auditFor`, `validOperatorAuditView`), `capabilities.mjs` `operator.audit.read`, `app.mjs` route and cursor parser, `backoffice/src/server/customer-api-client.ts` upstream reader, `server.ts` `/bff/api/operator/audit`, `backoffice/src/data/operator.ts` adapter, `App.tsx` Audit section, and `packages/e2e-dev` coverage. Everything is dev-only and synthetic — no production paths, no live data.
- Production effect: none

Hunt list applied: capability-registry role matrix vs the 34-name customer + operator vocabularies; `auc_*` cursor tamper classes (wrong prefix, oversized, non-monotonic, cross-`as_of`, beyond-end, duplicate key, cross-param-set); feed determinism, `au_*` uniqueness, actor role/subject coherence, action/target-kind pairing, `detail_hash` opaqueness, newest-first tie-breaks, dangling target refs; fixed-reader `AUDIT_READER_SUBJECT` leakage and real per-user authZ; envelope-resource binding, `?query` rejection parity, degrade path, hostile-echo adapter checks, i18n ×3; cross-checks against the sibling queue/subjects reads.

## Defects found and fixed

1. **`actor_role` was drawn from the wrong digest domain (`packages/customer-api/src/operator.mjs`).** The entry builder read `OPERATOR_ROLES[subjectsUnits(actor, "role", ...)]` — the customer-roster domain — while the admin view and the capability gate derive the same actor's role from `operatorRoleFor` (the staff `units` domain). The two domains disagree on 60 of the 72 feed entries, so the feed attributed a role that contradicted what the operator directory reports for that actor — an incoherence exactly of the auditor-acting-as-supervisor class the audit prompt names. Proven failing on pre-fix code (new pin asserts `entry.actor_role === operatorRoleFor(entry.actor_subject_id)` over every page). The feed now records `operatorRoleFor(actor)`, matching the role gate the route consults.
2. **The BFF route did not reject a repeated `cursor` parameter (`backoffice/src/server/server.ts`).** The query allowlist looped `url.searchParams.keys()` and passed `get("cursor")` — first-wins — while the upstream `operatorAuditCursor` allowlist rejects any duplicated key. `?cursor=auc_a&cursor=auc_b` therefore reached upstream (or the local ledger) with the first token silently winning, a divergence an ambiguity attacker could hide inside. Proven failing on pre-fix code (three duplicate spellings all answered `200` upstream of the fix; now `400 operator_audit_query_invalid` before any read).
3. **The unconfigured degrade path ignored the cursor entirely (`server.ts`).** With no upstream configured the route sliced the demo event ledger for every request, so `?cursor=auc_0011223344556677` answered page-1 rows inside an envelope bound to `operator-audit:auc_0011223344556677` — a verifiable page bound to a boundary that does not exist, replayable across bindings. Proven failing on pre-fix code; any cursor now answers the same uniform `404 operator_audit_not_found` the configured path reports for a never-minted token, since the local feed is a single page that mints nothing.
4. **Both fail-closed feed parsers skipped ordering and horizon checks (`customer-api-client.ts` `parseOperatorAuditView`, `data/operator.ts` `parseOperatorAuditView`).** Every sibling feed parser and the upstream `validOperatorAuditView` pin newest-first order with the feed's id tie-break and reject entries postdating `as_of`; the audit parsers checked shape/grammar/unique ids only, so a misordered, tie-broken-wrong, or future-dated page passed both gates and rendered. Also missing: the derivational action↔target-kind pairing (`flag.reviewed` always targets `flag`, never `queue_item`), which grammar checks alone admit. All three checks are now pinned in both parsers, plus `at ≤ as_of`; proven failing on pre-fix code in each position (reversed page, ascending ids under equal instants, beyond-horizon instant, mismatched action/kind all degrade to `unavailable`/`undefined`).

## Verified clean

- **Capability registry.** `operator.audit.read` sits in `OPERATOR_AUDIT_READ_ROLES` exactly `[auditor, compliance-lead]`; the roleless `evaluateOperatorCapabilities` call projects the full vocabulary by design (a capability dictionary, not a grant — pinned by existing tests); the `capabilities` read advertises only the caller's own capability set; `support-l1`, `aml-investigator`, `fraud-investigator` draw no `audit:read` anywhere (denied upstream with the uniform `403 CAPABILITY_DENIED` and at the BFF with `403 capability_denied` — the e2e arm pins the latter).
- **Cursor handling upstream.** `operatorAuditCursor` rejects any non-`cursor` key, any duplicated key, and any non-`auc_[0-9a-f]{16}` value before the role gate; a well-formed but never-minted token answers the same `404 CAPABILITY_DENIED` as an unminted subject (uniform denial, no oracle); there is no param set for a cursor to cross (the feed takes none); `as_of` is a single pinned instant (`QUEUE_SNAPSHOT_MS`), so cross-`as_of` cursors cannot exist; a token beyond the feed end was never minted → `404`; the page bound `≤ 32` is enforced at build time and re-verified inside `validOperatorAuditView`; existing pagination pins confirm all 72 entries across 3 pages with no overlap.
- **Feed derivation.** Byte-deterministic and fully frozen (existing pin re-run); all 72 `au_*` ids unique; no dangling refs — the new pin collects every `queue_id` of the three queue kinds, every roster `subject_id`, and every `flag_id` reachable through `queueItemFor`, and asserts each `target_kind`-consistent membership; `detail_hash` is an `adh_*` digest slice of the roster-domain HMAC — an opaque commitment, no reversible PII; newest-first ordering with descending `audit_id` tie-break is pinned in both the derivation sort and the upstream validator (note: the audit feed's tie-break is *descending* id, opposite the queue feed's ascending `activity_id` — each parser pins its own convention).
- **Fixed-reader deviation.** `AUDIT_READER_SUBJECT` (`syn_oper_…002`) deterministically draws `auditor`; the feed never varies by reader (derivation inputs are constants, not the principal); the BFF mints the byte-identical `sodev1.syn_oper_0000000000000002.*` bearer for every caller subject — pinned across `dev:auditor`, `dev:support`, `dev:compliance-lead`; `audit:read` runs before any upstream call, so a session without the capability can never reach it (the new client test reads the real dev API behind a non-oversight caller and still succeeds through the fixed principal).
- **Backoffice surface.** The `operator-audit:${cursor ?? "first"}` envelope resource binds the page boundary exactly like `operator-queue` binds `kind`; the `?query` allowlist + `auc_*` grammar now match upstream including duplicate rejection (defect 2); upstream `404` → `operator_audit_not_found`, anything else → `operator_audit_unavailable`; adapter/parsers reject cross-record extras, wrong shapes, grammar drift, duplicated ids — and now ordering/horizon/pairing drift (defect 4); the three `audit.operatorFeed*` keys exist in `en`/`ru`/`ky` with identical sets; `App.tsx` fetches only when `hasCapability(session, "audit:read")` and degrades to demo rows on any failure; `auditSource()` demo ledger caps at 32 rows.
- **Sibling parity.** The audit route is GET-only like every `/bff/api/operator/*` read — non-GET falls through to the uniform `not_found` (the `405 Allow: GET` pattern applies only to the path-patterned read routes); entries acting on roster subjects (`subject.viewed` → `syn_cust_*`) are the feed's stated purpose, not a leak — the dangling-ref pin proves every referenced id exists in its target universe.

## Observations (recorded, not defects in this slice)

- The upstream `404` for a well-formed-but-unminted cursor reuses code `CAPABILITY_DENIED` — deliberate uniform denial (a distinct `not_found` code would let a caller distinguish "token grammar ok but never minted" from "not allowed at all"). The BFF maps it to `operator_audit_not_found`, which exposes nothing upstream didn't already: cursor minting is deterministic, not secret.
- `AUDIT_READER_SUBJECT` is visible in the upstream `Authorization: Bearer sodev1.syn_oper_…` header — the fixed-principal design trades per-user upstream attribution for one oversight identity; per-user authZ lives exclusively in the BFF `audit:read` gate, and upstream observability (rate-limit bucket + request log keyed on the bearer subject) records that single identity. Consistent with the sibling reads' pass-through pattern; noted, not changed.
- `as_of` pins the feed to the roster's snapshot instant (`2027-01-29T00:00:00Z`), not request time — pages are stable across calls, so a reader polling during a scan always sees one coherent universe. The unconfigured local path substitutes `new Date(0).toISOString()` for `asOf` since the demo ledger has no snapshot semantics.
- The audit feed's equal-instant tie-break sorts descending `audit_id` where the queue activity feed sorts ascending `activity_id`; both are self-consistent conventions pinned by their own validators — recorded so a future port doesn't copy the queue's direction onto the audit feed.
- 72 entries over 24 subjects × 3 events each; `OPERATOR_AUDIT_EVENTS_PER_SUBJECT` is a constant like the sibling feeds' densities — the universe is intentionally small enough to exhaust in three pages.
