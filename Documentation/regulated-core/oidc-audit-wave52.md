# OIDC Flow Internals Audit — Wave 52 — Proposed

- Status: Proposed
- Scope: `backoffice/src/server/oidc.ts` (authorization request, code exchange, JWKS fetch, ID-token verification, claim and role mapping), the login/callback issuance path in `server.ts` (`pendingLogins`, the transaction cookie, `createSession`, logout), `session.ts` (`ExpiringStore`), the OIDC block of `config.ts` parsing, and the existing coverage in `oidc.test.ts` / `oidc-session.test.ts` / `server.test.ts`. Everything is dev-only and synthetic — no production paths, no live providers, no real IdP traffic.
- Production effect: none

Hunt list applied: state/nonce binding (replay, cross-subject rebind, TTL, exact comparison against the stored authorization request), PKCE (S256 only, `plain` ever emitted, verifier charset and length bounds, method-mismatch downgrades), `redirect_uri` (exact-match vs prefix, `javascript:`/scheme confusion, trailing-slash and Unicode-normalization bypasses, open-redirect construction), ID-token validation (`iss`/`aud`/`azp`/`exp`/`iat`/`nonce`/`typ` trusted without comparison, `alg=none`/`kid` confusion, JWKS key confusion between declared and used algorithms, `at_hash`/`c_hash`), session issuance post-callback (fixation, step-up and device-binding interplay, replayed callback producing duplicate sessions, token material leaking into logs, responses or the audit store), token storage and transmission (tokens returned to the browser, logged, held beyond TTL, refresh-token handling), config parsing (env validation — trailing whitespace, case, URL parsing, `http://` issuers), logout and revocation paths (partial revocation, logout CSRF), and timestamp handling (clock injection vs `Date.now` drift, `exp<=now` boundary off-by-ones).

## Defects found and fixed

1. **OIDC HTTP clients followed redirects, leaking the exchange secrets and substituting keys (`oidc.ts`).** Both outbound fetches used the default `redirect: "follow"`. On the token endpoint a 307/308 re-POSTs the full form — `code`, `code_verifier` and `client_secret` — to whatever `Location` says: proven on main with a local redirector and collector, where the complete form arrived at the collector and the exchange resolved with the collector's injected `id_token`. On the JWKS endpoint any redirect silently swaps the verification keys: proven on main, where a token forged with an attacker key behind a 302 passed signature verification and only the (unrelated) role map stopped issuance. A redirecting OIDC endpoint is a configuration error, not a feature: both fetches now send `redirect: "error"` and fail closed. This matches the existing `customer-api-client.ts` precedent, which already refused redirects on upstream calls.
2. **OIDC responses were buffered without a bound (`oidc.ts`).** Both endpoints consumed `response.json()` with no size limit, so a hostile or broken endpoint could stream an unbounded body into the BFF process — proven on main, where a 70 KB token response and a 70 KB JWKS document both parsed and resolved. A shared `readBoundedJson` now streams the body with a 65,536-byte cap (`id_token` itself is already capped at 16,384, and realistic envelopes and JWKS sets sit far below the bound), cancels the reader and rejects on overflow.
3. **`sub` admitted control characters (`oidc.ts`).** The claim check rejected only characters above `0x7f`, so `\n`, `\u0007`, `\u001f`, `\u0000` and `\u007f` sailed through — proven on main — and the value was stored verbatim into `session.subject` and downstream audit events. `sub` is now restricted to printable ASCII (`0x20`–`0x7e`), still 1–255 characters.

## Verified clean

- **State, nonce and transaction binding.** `pendingLogins` records `(nonce, verifier, previousSessionId, expiresAt)` under a 32-byte opaque `state`; the callback requires the transaction cookie to equal `state` exactly before `pendingLogins.take(state)` — a single-use read — so replay, cross-subject rebind (the pending entry is keyed by state, never by the caller's claims) and expired entries all fail closed. The stored `nonce` is compared with `!==` against the claim; pins cover case changes, trailing whitespace, empty and absent nonce.
- **PKCE.** The authorization request always emits `code_challenge_method: "S256"`; `plain` is never generated or reachable. The verifier is a 48-byte `createOpaqueValue` — 64 characters inside the RFC 7636 `unreserved` charset (43–128 bound); the challenge is `base64url(SHA-256(verifier))`, deterministic and unequal to the verifier.
- **`redirect_uri` and the post-auth target.** `redirect_uri` is the exact configured value pinned in `authorizationUrl` and echoed verbatim in the exchange form; it is never built from request input, so there is no prefix/scheme/normalization surface. After issuance the callback 302s to `config.allowedOrigins[0]` — a fixed list entry — and config requires that entry's path to be exactly `/bff/auth/callback` on an allowed origin. Config parsing additionally rejects userinfo, fragments, query strings on the issuer, and non-HTTPS endpoints anywhere except loopback origins.
- **ID-token validation.** `alg` must be `RS256` literally (none, symmetric, EC, EdDSA, and casing/padding confusions rejected); `kid` must be a non-empty string matching exactly one JWKS entry; `crit` is refused wholesale and key-carrying headers (`jku`/`jwk`/`x5u`/`x5c`/`b64`) are rejected; the JWK must be RSA with `n`/`e` strings, no private members, `use` ∈ {absent, `sig`}, `key_ops` ∈ {absent, [`verify`]}, `alg` ∈ {absent, `RS256`}, modulus ≥ 2048 bits. Claims require typed `iss`/`sub`/`aud`/`exp`/`iat`/`nonce`, exact `iss` and `aud` membership, the spec-correct `azp` rule, `exp > now`, `iat`/`nbf` ≤ now + 60s, finite NumericDates, strict UTF-8, canonical unpadded base64url segments, a duplicate-member scanner on the raw JSON, and a 16,384-character token cap.
- **Session issuance.** The session id is a fresh server-minted opaque value created only after the identity verifies (no fixation surface); `createSession` deletes the previous session id captured at login and every session sharing the device id; device admission runs before the code exchange, so an unapproved device never reaches the IdP. Callback hygiene is pinned: replay → 400 with no cookie, `error=` and unknown state → 400, failed upstream exchange → 500 `request_failed` with no session cookie and no token material in the body, success → 302 to the configured origin with only the session cookie.
- **Token storage and transmission.** The `id_token` is consumed server-side only; nothing is returned to the browser, written to the audit store, or logged — log lines carry route templates and status only. No `access_token` or `refresh_token` is requested or stored.
- **Logout and revocation.** Logout requires `exactOrigin` (CSRF-safe) and deletes the presented session; re-login deletes the earlier session and step-up material bound to it dies with the session.
- **Timestamps.** All comparisons use seconds against `Math.floor(Date.now() / 1000)` with `exp <= now` rejecting the exact boundary and a 60-second skew allowance on `iat`/`nbf`; store TTLs use a single injectable clock internally with lazy eviction.

## Observations (recorded, not defects in this slice)

- `pendingLogins` and `sessions` are in-memory `ExpiringStore`s pruned lazily on `set`/`take`; unauthenticated `/bff/auth/login` inserts one entry per call so a flood grows the map until the 5-minute expiry. Dev-only, loopback-only — recorded, not a defect in this slice.
- `createPublicKey` on a malformed `n`/`e` and `JSON.parse` on a malformed body can throw a raw error; both still reject through the same closed path (callback → generic 500), so only the error text differs.
- `nonce`, `iss` and the transaction-cookie compares are plain string `!==` — exact-match requirements on non-secret values; constant-time comparison adds nothing for these and is recorded rather than changed.
- `iss` is compared to the raw env string (trimmed), which `new URL` validation does not normalize (host case, default port, trailing slash). The compare fails closed — a mismatched spelling rejects a real token rather than admitting a forged one — recorded as an operational note, not an auth hole.
