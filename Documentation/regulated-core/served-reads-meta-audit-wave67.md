# Served Reads Meta-Consistency Audit — Wave 67 — Proposed

- Status: Proposed
- Scope: every served read in `packages/customer-api` — all 36 contract operations in `src/contract.mjs` (`getApiMetadata`, 26 customer reads, 9 operator reads), the dispatcher in `src/app.mjs`, the capability registry in `src/capabilities.mjs`, and every `valid*View`/`isIsoTimestamp` validator across the 18 served-read modules. One systematic sweep rather than a per-surface pass: each of the eight audit checks was applied to every operation, and a missing matrix cell counted as a finding. Everything is dev-only and synthetic — no production paths, no money movement, no real customer data.
- Production effect: none

Hunt list applied: method/content-type uniformity (GET only, body rejected, `?query` refused on non-query routes and on member routes), id-shape grammar before lookup (wrong-prefix id indistinguishable from a well-formed-but-unknown id), capability gating (route → registry mapping, the capabilities read mirroring the evaluated capability set exactly, 403/404 discrimination), pagination/cursor hygiene (bounded pages, foreign-cursor rejection, stable `as_of`), timestamp hygiene (`isIsoTimestamp` reserialize-equals-self in every validator, impossible instants rejected without throwing), envelope uniformity (same `{code,message,request_id,details}` error shape, no internal fields), determinism (byte-identical repeat fetches), and subject isolation (a foreign subject's member id never serves).

## Defects found and fixed

1. **`isIsoTimestamp` was non-total in all 18 served-read validator modules.** The reserialize-equals-self pattern (`new Date(Date.parse(value)).toISOString() === value`) throws `RangeError` on instants `Date.parse` cannot decode — month 13, day 32, hour 24, minute or second 60 — so a directory that ever emitted an impossible instant crashed the request into a 500 instead of the validator answering `false` and failing closed. Verified on main: `validActivityView` threw on `2026-13-01T00:00:00.000Z`. The fix inserts `Number.isFinite(Date.parse(value))` before the reserialize check in every copy — the same total guard `validPrincipal` already used — across `activity`, `address-screenings`, `auth-sessions`, `cards`, `checks`, `deposit-addresses`, `deposits`, `exchange-orders`, `kyc`, `notifications`, `operations`, `operator`, `payments`, `profile`, `quotes`, `support`, `users` and `withdrawals`. `wallets` carries no instant fields and needed no guard (pinned by the control case).
2. **Three operations were not dispatched by explicit operationId arms like their siblings (`src/app.mjs`).**
   - `getApiMetadata` was dispatched on the `!operation.authenticated` property — a second unauthenticated operation declared in the contract would have been silently served the metadata view. It is now an explicit arm that also requires `!operation.authenticated`, so a contract flip falls into the credential checks instead of being served open.
   - `getCustomerSession` had an arm but never consulted the capability registry — every sibling arm asserts the evaluated capability list contains the route's capability so a served route cannot drift from the capabilities the service exposes. The arm now evaluates `evaluateCapabilities({ kycStatus })` and requires `customer.session.read` (present for every authenticated customer, so wire behavior is unchanged).
   - `getCustomerCapabilities` had no arm at all: it was served by the implicit fallthrough `send(...)` after the last `if`, so any newly declared unhandled customer operation would also have been answered with the capabilities view. It is now an explicit arm requiring `customer.capabilities.read`, and the pipeline ends in `throw new Error(...)` — fail closed into the 500 envelope — instead of an implicit response.
   - The regression test statically asserts every one of the 36 contract operations has an explicit `operation.operationId === "..."` arm whose body consults the registry for its derived capability (the dotted `namespace.tail.read` form), and that the pipeline terminates in a throw past the last arm.

## Verified clean (with negative pins)

- **Method gate is uniform.** POST/PUT/DELETE/PATCH/OPTIONS on all 36 operations answer 404 `CAPABILITY_DENIED`; HEAD answers 404 with an empty body — deny-by-default routing reaches every read.
- **Body gate is uniform.** A `content-length` or `transfer-encoding: chunked` header on a GET answers 400 `VALIDATION_FAILED` on every operation, authenticated or not.
- **Query gate is a consistent two-tier contract.** `?unexpected=1` answers 404 on the 34 non-query reads; the two declared query reads (`operator/queue?kind`, `operator/audit?cursor`) answer 400 `VALIDATION_FAILED` for undeclared or extra parameters (a strict single-parameter allowlist) and serve only the declared parameter. Member routes refuse query strings uniformly.
- **Id grammar holds with no existence oracle.** Wrong-shape and wrong-prefix ids (`not_an_id`, `usr_*` against `ord_*`/`syn_cust_*` routes) answer byte-identical 404s to well-formed-but-never-minted ids on every member read; a `qml_*` item requested under `/queue/kyc/` answers identically to an unknown `qky_*`; an out-of-enum `{kind}` answers 404; every malformed instrument shape (`USDTRUB`, empty side, lower-case, `not_an_id`) answers identically to an unknown pair. The grammar is enforced at the directory boundary: non-minted ids resolve the same `null` regardless of shape.
- **Capability gating matches the registry exactly.** For an unverified subject the 403/200 boundary follows `CAPABILITY_POLICY` per operation — ungated reads (session, capabilities, kyc, profile, support, auth, users) serve, KYC-gated reads 403 `CAPABILITY_DENIED`; the gate runs before lookup (a real member id with an unverified subject still 403s). The capabilities read advertises exactly the evaluated capability set for verified and unverified customers and per operator role — never more, never fewer.
- **Audience isolation holds.** A customer token on every operator route (with the mandatory device header present) and an operator token on every customer route (in the customer header shape, since customer surfaces refuse `X-Device-Id` itself) answer 401 `AUTHENTICATION_REQUIRED` — neither direction reaches 403/200.
- **Audit pagination is bounded and replayable.** The 72-entry feed pages at ≤ `OPERATOR_AUDIT_PAGE_SIZE` entries with `as_of` pinned across all three pages; every minted `auc_*` cursor replays byte-identically; no `audit_id` repeats across pages; the walk terminates at `next_cursor: null`. Malformed cursors answer 400, a well-formed never-minted token answers 404, and foreign-family or wrong-length tokens answer 400.
- **The error envelope is uniform.** Sampled 400/401/403/404 classes all emit exactly `{code, message, request_id, details}` with `details` an empty object — no `stack`, `_meta`, `error` or derivation fields leak onto the wire.
- **Every read is deterministic.** Double-fetching all 36 operations returns byte-identical status and body.
- **Subject isolation holds.** `SUBJECT`'s real order, operation and screening ids requested as `VERIFIED_SUBJECT` answer 404 — a member read only ever resolves the requester's own minted records; a wrong-prefix id on the operator subject read never resolves.

## Observations (recorded, not defects in this slice)

- The 400/404 split is deliberate and consistent: request-shape violations (body on GET, bad headers, malformed query parameters, malformed cursor tokens) answer 400 `VALIDATION_FAILED`, while authorization/routing/miss conditions answer 404 `CAPABILITY_DENIED`. Both statuses are declared `CONTRACT_GAP_STATUSES`; the discrimination leaks no existence information because a 400 always fires before any lookup.
- The dispatched task inventory listed `checks/{id}` as served; the repo serves only the `getCustomerChecks` collection — `previewCustomerCheck`, `getCustomerCheckStatus`, `claimCustomerCheck` and `cancelCustomerCheck` stay contract-only, consistent with the served-read map. The audit matrix covers the 36 operations actually served.
- The `getCustomerSession` and `getCustomerCapabilities` capability checks are satisfied unconditionally by policy (both reads are ungated), so the added capability-membership assertions change no wire responses — they exist so a future policy change cannot silently un-gate a served route, the same convention `getOperatorSession`/`getOperatorCapabilities` already used.
- `wallets` and the operator capabilities view carry no instant fields; they are pinned as the no-instant control set so the corruption sweep provably only mutates instant-shaped strings.
- The `isIsoTimestamp` fix also covers instants that parse but normalize (`2026-02-30` → March 2): the reserialize-equals-self check already answered `false` for those; the guard adds totality for instants that do not parse at all.

## Test additions

- `tests/served-reads-meta-audit-wave67.test.mjs` (13 cases): eleven matrix pins covering method, body, query, id grammar, capability gating, capabilities echo, audience isolation, audit pagination/cursor hygiene, envelope uniformity, determinism and subject isolation — plus two defect regressions: timestamp totality across 29 instant-bearing views and 2 no-instant control views (each `valid*View` must answer `false`, never throw, on `2026-13-01`, `2026-02-30` and `T24:00` corruptions), and the explicit-arm/capability-consultation dispatch pin over all 36 operations.
- Both defect regressions fail on main and pass on this branch; the eleven clean-class pins pass on both by design.
