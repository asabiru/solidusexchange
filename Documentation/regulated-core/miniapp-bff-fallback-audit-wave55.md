# Mini App BFF Fallback Arms Audit — Wave 55 — Proposed

- Status: Proposed
- Scope: `miniapp/src/server/server.ts` (every route arm that still touches `syntheticData.*`, the local service stores, or a local command while a customer-api is configured), `miniapp/src/server/customer-api-client.ts` (the read adapters those arms call), and the fallback-facing helpers (`synthetic.ts`, `checks.ts`, `notifications.ts`, `support.ts`, `address-screening.ts`, `operations.ts`, `account.ts`, `sessions.ts`, `activity.ts`, `kyc.ts`, `profile.ts`). Everything is dev-only and synthetic — no production paths, no money movement, no approval or decision-register changes.
- Production effect: none

Hunt list applied: fallback correctness (whether a degrade arm can serve rows the upstream would never return for that subject, or a shared fixture set under an upstream-owned namespace), gate symmetry (whether upstream-unreachable answers more than upstream-reachable would, KYC/device-id/session/capability parity per arm), status-code drift (`404` vs `not_found` vs `domain_unavailable` parity between the two arms of one route), empty-vs-degraded confusion (whether a client can still distinguish "no data" from "upstream down"), local POST submit arms (validator round-trip of locally created entities, malformed-row crash safety, id namespacing against upstream `*_`-prefixed ids), data freshness (stale derived fields such as affordability and unread counts against recomputed contract fields), and session/device binding on the degrade path.

## Defects found and fixed

1. **`GET /bff/checks/:id` ignored the upstream contract entirely (`server.ts`).** Four drift forms in one route:
   - A verified session with a configured customer-api got `404` for upstream `chk_*` ids that the just-rendered list itself showed — click-through broke.
   - The five shared fixture ids rendered `200` with local fixture data although the contract list (the surface's only owner upstream — there is no member read) did not contain them: the detail resurrected rows the list would never show.
   - With the upstream down, the list answered `503 checks_unavailable` while the detail happily answered `200` fixture data — the fallback arm answered strictly more than the reachable upstream would.
   - On an upstream `denied` the list degrades to `checks.list("kyc-gated")` (gated statuses), but the detail used `session.kyc` — so a verified-but-refused session saw `created` where the list showed `awaiting_recipient_kyc` for the same reference.
   The detail now walks the same four-way as the list: `ok` resolves against the adapted contract entries by reference (`404` when absent), `denied` degrades to the gated fixture detail, and every other non-ok upstream outcome fails closed as `checks_unavailable`. Gated and unconfigured sessions keep the fixture detail.
2. **Quote and check previews judged affordability against the frozen shared fixtures (`server.ts`).** `/bff/quotes/preview` and `/bff/checks/preview` computed `insufficientBalance` from `syntheticData.available(session.kyc, asset)` even when the wallet surface served the subject's real balances from the contract — a subject with an empty upstream wallet got `insufficientBalance: false` against the `482.180000` USDT fixture. `previewAvailability` now follows the wallet read: `ok` uses the served balance for the asset (`0` when the asset is absent), `denied` degrades to the gated zero balance (the fail-closed answer), and any other upstream failure answers `503 quote_unavailable` / `503 checks_unavailable`. Gated and unconfigured sessions keep the fixture balance; an unknown asset code skips the read and lets the provider's own `invalid_*` validation fire.
3. **`POST /bff/notifications/read` was arm-blind (`server.ts`).** With the contract feed owning the displayed list (verified + configured), the response reported the local outbox `unread` — a count the client cannot see — while upstream `ntf_*` ids silently marked `0`. The marks stay local either way (no upstream write exists; local drafts are the only marks the command can take), but under `ok` the response now reports the served `unread` count, under `denied` it degrades to the local response, and any other upstream failure answers `503 notifications_unavailable`. Gated and unconfigured sessions keep the local response.
4. **`addressScreening()` lacked the pre-flight id guard `operation()` already had (`customer-api-client.ts`).** `operation()` short-circuits ids that cannot parse upstream to `not-found` without a request; `addressScreening()` encoded any string into the path and spent a call on the shared upstream rate limit (40/min globally — every malformed id cost real quota). It now resolves `missing` locally for ids failing `screeningIdPattern`; locally minted `scr_*` ids still match the pattern, reach upstream first, and fall back to the local store on `missing` exactly as before.

## Verified clean

- **Subject scoping on every degrade arm.** Every local fallback view is subject-scoped (`support.view`, `addressScreening.view`/`list`, the notification outbox, the activity log) or deliberately shared-fixture-by-design (`syntheticData.*`, `checks.ts` fixtures, deposits/withdrawals/quotes/orders/trades/payments/cards views — emptied for gated). Dev logins share one deterministic `dev-` subject and upstream ids derive from `syn_cust_*`, so no cross-subject leak path exists; pinned by the per-domain upstream tests plus this wave's pins.
- **Gate symmetry on GET routes.** Every upstream-capable read applies the identical `session.kyc !== "verified" || !customerApi.configured` fork before consulting upstream, so gated sessions never reach upstream at all (`calls.length === 0` pins). `X-Device-Id` stays a 400 on customer routes (operator-only) and `sec-fetch-site`/origin/session guards run before any arm — no fallback arm skips them.
- **`/bff/address-screening/:id` "missing → local" fallback.** Deliberate and pinned: locally minted `scr_*` ids (POST submits stay local) render through the local store when upstream 404s; the lookup is subject-scoped, so another subject's `scr_*` still 404s.
- **`/bff/support/requests/:id` local-only detail.** The upstream read owns the list; the detail resolves only locally minted `sup_*` drafts — upstream `tck_*` ids answer `404` without an upstream call. Pinned in this wave.
- **`/bff/operations/:id`.** `denied` degrades to `local("kyc-gated")` which is always empty → `404`, matching the gated list; upstream `not-found` → `404`; malformed ids short-circuit client-side before a request.
- **Id namespaces.** `sup_*` vs `tck_*` and `op-*` vs `ope_*` are disjoint by prefix; `scr_*`, `ntf_*`, `act_*`, `chk_*` share patterns across stores but different digest domains (BFF `dev-`/`tg-` subjects vs upstream `syn_cust_*`) make collisions unreachable — local ids still resolve through their own store only.
- **Empty-vs-degraded.** Unconfigured → deterministic `200` synthetic; configured+down → `503` `surface_unavailable`; configured+denied → in-place degrade. A client can always tell "no data" from "upstream down": the error contract, not an empty list, carries the outage. Load-burst semantics preserved — the fallback never invents a 200 during an upstream outage.
- **Freshness of derived fields.** Contract adapters recompute (`total` = `amount` + `fee` parity between `contractChecksView` and the fixture view; `walletView` recomputes `valueRub`/`totalRub`/`availableRub`/`holdRub` from served balances; upstream `unread` is recomputed from `read` flags and now reported verbatim by the mark-read response).
- **Local submit arms.** Support create returns `sup_*` ids that render through the subject-scoped local detail; screening submit mints subject-bound `scr_*` digests; `activityId` on support create is checked through the subject-scoped `kindOf`. Validator round-trip: locally created records reuse the same view serializers the reads serve.
- **Denied-arm parity.** `notifications` and `activity` degrade to the subject's local records (non-empty by design — the stores hold real local events); the asset/activity-tier reads degrade to emptied gated views. Both forms are subject-scoped and documented per route.

## Observations (recorded, not defects in this slice)

- `localAccountView` and `contractAccountView` report different `id`/`subject` namespaces for the same session (`usr_`-of-`dev-*` hash/`dev-*` vs upstream `usr_*`/`syn_cust_*`). Documented per-arm derivation, harmless in dev; a uniform account handle would need fabricating an upstream-looking id.
- POST routes parse the body before the session check, so an unauthenticated caller can distinguish `400 invalid_*` from `401`. Uniform across all POST routes and the body schema is public in dev; recorded, not changed.
- Empty-query strictness differs across GET routes (`notifications`, `sessions`, `support`, `address-screening`, `checks` reject `?x=1`; `wallet` and the other list reads ignore it). Pre-existing surface contract, not a fallback-arm issue; recorded for a future consistency pass.
- Local writes under an upstream-owned read (support POST's `outbox.record`, quote preview's `activity.recordQuote`, session-login drafts) land in stores the contract feed does not show — deliberate: commands and event recording stay local, and the records surface again whenever the read degrades to the local arm.

## Test additions

- `miniapp/src/server/fallback-arms.test.ts` (17 cases): 12 defect regressions — contract-id vs fixture-id resolution on the checks detail, `checks_unavailable` under outage, gated-status parity on `denied`, upstream-balance affordability on both previews, missing-asset-as-zero, `denied`-as-zero, `*_unavailable` on preview outage, served unread count and `marked: 0` for upstream ids on the mark-read route, `notifications_unavailable` under outage, and zero upstream calls for a malformed screening id — plus 5 pins for clean arms: gated/unconfigured fixture detail and fixture balances with zero upstream calls, the local mark-read response on `denied`/gated, and the local-only support detail that 404s a `tck_*` id the list serves.
- Every new case fails on main and passes on this branch, except the pinned-clean cases which pass on both by design (proven via a detached worktree at the merge base: 12 fail, 5 pass there).
