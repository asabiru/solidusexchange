# Miniapp Envelope Client Audit — Wave 61 — Proposed

- Status: Proposed
- Scope: `miniapp/src/app/api.ts` (browser fetch layer), `miniapp/src/server/customer-api-client.ts` (BFF→customer-api contract client), and the adjacent trust boundaries `miniapp/src/server/init-data.ts`, `miniapp/src/server/request-body.ts`, `miniapp/src/server/session.ts`. Member-read routes `miniapp/src/server/server.ts` (`/bff/operations/:id`, `/bff/address-screening/:id`, `/bff/checks/:id`) traced end to end.
- Production effect: none

Architecture mapping (recorded for reviewers): the miniapp carries no Ed25519 envelope-signing layer. The browser↔BFF leg is an unsigned same-origin cookie channel guarded by `Sec-Fetch-Site` checks, and the BFF↔customer-api leg authenticates with per-request HMAC synthetic dev tokens and fail-closed contract adapters. #303's envelope classes therefore apply here as: bounded/typed response decoding on the browser leg, and token-echo binding + adapter strictness + degrade-arm discipline on the upstream leg.

Hunt list applied: member reads serving a different subject's record, unbounded `response.json()`, missing canonical-depth bound, unbounded/unvocab'd capability and scope echoes, echo fields that must equal the minted request, derived counters and lifecycle fields trusted as asserted, proto-key/confusable-key injection, unencoded path or query params, error bodies shaping the error surface, degrade arms leaking partial views, freshness-window gaps.

## Defects found and fixed

1. **Browser fetch layer consumed `response.json()` unbounded and silently (`app/api.ts`).** `call()` materialized arbitrary bodies and, on parse failure, substituted `{}` — a 200 carrying a 17 MB body or malformed JSON resolved into an empty view. The layer now enforces a JSON content-type gate, a 262 144-byte bound on both declared length and the streamed body (mirroring the backoffice client's `MAX_BFF_RESPONSE_BYTES`), and a depth-16 canonical-JSON check (`MAX_PAYLOAD_DEPTH`, finite non-`-0` numbers) on success payloads. Malformed success bodies now reject instead of serving `{}`. Error bodies keep `ApiError` semantics: a bound- or type-violating detail collapses to `request_failed` without masking the HTTP status.
2. **`operation()` echoed a member record without binding it to the request (`customer-api-client.ts`).** The member read validated the served `OperationView` item but never required `item.operation_id === operationId` — a well-formed view minted over a *different* operation resolved `{status:"ok"}` and the BFF detail route displayed that other record (the #303 different-subject class). The read is now bound to the requested id; a mismatched echo fails closed to `"unavailable"`.
3. **`addressScreening()` had the same member-read echo gap (`customer-api-client.ts`).** `parseAddressScreeningRecord` validated the record's shape but never required `record.screening_id === screeningId`. Bound identically; a mismatched echo fails closed to `"unavailable"` rather than rendering another screening's verdict.
4. **`access()` session echo was only partially bound (`customer-api-client.ts`).** `subject` and `actor_type` were checked, but `expires_at` and `scopes` were never compared — a session view minted over another principal's token (any expiry) or carrying operator/broadened scopes satisfied the check. The echo is now exact: `expires_at` must equal the expiry this request's dev token was minted with and `scopes` must be the upstream `CUSTOMER_SCOPES` pair in order.
5. **`access()` capability echo was pattern-only (`customer-api-client.ts`).** Any `customer.*`-shaped name was admitted — including unvocab'd names like `customer.withdrawals.execute` — and duplicated names were admitted too. The echo is now bound to the declared 34-name customer capability vocabulary (the customer half of upstream `CAPABILITY_POLICY`) and names must be unique.
6. **`parseNotificationsView` trusted the asserted unread counter and allowed duplicated ids (`customer-api-client.ts`).** Upstream pins `unread` to the flag recount and `notification_id` to uniqueness; the client did neither, so a feed could lie about unread state or replay one notification as many. The view now recounts unread itself and rejects duplicated ids.
7. **`parseSupportView` skipped the contract's lifecycle invariants (`customer-api-client.ts`).** It checked the last timeline step equals `status` but not the strict status prefix (`received → in_review → answered → closed`), the `complaint_acknowledged === (category === "complaint")` mirror, `expires_at > created_at`, `timeline[0].at === created_at`, or strictly increasing step times. All are now pinned, mirroring the upstream `validTicketsView` semantics.
8. **`parseKycStatusView` skipped session/status coherence and derived-field pins (`customer-api-client.ts`).** It applied only loose "if any application field is present" checks: an `unverified` session could echo the terminal pass status upstream reserves for `verified` sessions, `can_submit` could contradict the resubmittable set, and optional fields (`application_id`/`submitted_at`, `review_deadline`, `reason_codes`, `requested_items`) could appear or disappear independently of `status`. The parser now mirrors the upstream validator: session_kyc bounds status, `can_submit` is derived, each optional field pair exists exactly when its status demands it, and `submitted_at <= updated_at`.

## Verified clean (with negative pins)

- **Upstream body bounds already held**: `readBoundedJson` in the BFF client requires a JSON content-type, gates declared `content-length` at `maxCustomerApiResponseBytes` (16 384) and enforces the cap while streaming chunked bodies; fatal UTF-8 decoding, malformed `content-length` spellings and stream errors all reject — pinned by the existing negative suite, kept green.
- **`/bff/checks/:id` member read was already bound**: the detail resolves inside the upstream checks collection with `reference === requested`; a collection without the reference answers not-found, never a foreign record.
- **Subject binding held on the identity views**: `parseUserView` requires `value.subject === expectedSubject`, `parseAuthSessionsView` requires exactly one `current: true`, and `parseChecksView` binds each entry to the subject on exactly one side (sender or recipient).
- **Error surface mapping is deterministic and never parses error bodies**: non-200 statuses raise `CustomerApiHttpError`; member reads map 404 → `not-found`/`missing`, capability-gated reads map 403 → `denied`, every other failure → `unavailable` — no code, message or view field is read off an error body.
- **Degrade arms serve only their documented objects**: unconfigured client → `{status:"not-configured"}` on every read; unreachable → `unavailable`; denied only where the upstream capability is KYC-gated — a 403 on an un-gated read is contract drift and maps to `unavailable`, never a partial view.
- **init-data verification is complete**: 4 096-char bound, key pattern, duplicate `hash`/`key` rejection, `timingSafeEqual` HMAC, `auth_date` integer format, 60 s future-skew rejection and `maxAgeSeconds` staleness — all pinned in `init-data.test.ts`.
- **Request-body discipline is complete**: 4 096-byte bound, duplicate-key rejection, allowed-key allowlists, string-only strict objects and charset checks in `request-body.ts`.
- **Wire hygiene**: `redirect: "error"`, `AbortSignal.timeout` aborts stalled upstreams, `x-request-id` is a fresh uuidv7 per call, `x-device-id` is never sent upstream, member ids go through `encodeURIComponent` and preview queries through `URLSearchParams` — the captured-path pin asserts `/bff/operations/a%2Fb%2F..%2F..%2Fetc`.
- **Proto-key and hostile-field content fails closed**: every view parser requires an exact key set before typing, so `__proto__`/`constructor` members and extra carriers reject on entry; deep nesting inside typed fields fails the field check.

## Observations (recorded, not defects in this slice)

- Freshness/skew windows do not apply to upstream views: the synthetic customer-api feed is a deterministic `BASE_MS` projection, not wall-clock data — a served-time staleness bound would break every legitimate read. Freshness is enforced where it exists: the dev token TTL (300 s, minted per request) and the init-data `auth_date` windows.
- `expires_at` is pinned to the *exact minted instant* (not merely ISO-shaped) because upstream echoes the presented token verbatim; this is verified against `auth.mjs`/`app.mjs` rather than assumed.
- The `capabilities` vocabulary is the customer half of upstream `CAPABILITY_POLICY`; if upstream declares a new `customer.*` capability, the client's vocabulary must be updated in the same change — the fail-closed direction is toward `unavailable`, never toward admitting an undeclared name.
- Browser-leg views are not schema-validated past the canonical-JSON bound (the BFF is a first-party same-origin server); upstream-leg views carry the strict adapters where the untrusted boundary actually is.
